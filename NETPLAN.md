## 0. Read this first — three rules that override habit

**Rule 1 — never edit `client/gauntlet.html`.** Line 1 of that file says
`GENERATED by tools/build.py from web/template.html -- DO NOT EDIT`. All
client work goes in `web/template.html`, then `python tools/build.py`. The
line numbers quoted in this plan are from the *generated* file and are
there to help you locate the corresponding region in the template; they
will not match the template exactly.

**Rule 2 — protocol changes go through `shared/protocol.json` first.**
Order is: `shared/protocol.json` → the constants block at the top of
`server/relay.cpp` (lines ~53–90) → `python tools/protocheck.py` to verify
the two agree → `python tools/build.py` (the client reads its constants
from `A.protocol`, which is the JSON baked into the assets blob — a
client built before the JSON change will silently use stale numbers).

**Rule 3 — the relay never learns what the game is.** It relays bytes,
owns seats and the pass counter, and holds one `buildSeed`. It must not
parse a snapshot, model the sim, or acquire game state. Every proposal
below is written to preserve this. If an implementation seems to need
the relay to know something about the game, the design is wrong — stop
and say so rather than reaching into the sim.

## 1. Why this plan exists (the history — do not re-tread it)

The exchange is stop-and-wait over TCP/WebSocket: one direction byte per
tick, one INPUT in flight, the tick steps when PASS returns. The unit is
`Game.stepTick`; `tickSeconds()` is `PASS_SECONDS ≈ 80 ms` in `play` and
`1/FRAME_HZ ≈ 20 ms` in `attract`/`over`/`rewind`.

**Pipelining was already built and rejected on play-test.** Two bugs,
both real, both instructive:

1. *The pipe had no drain.* The level-entry pause charges `simT` ~4 s.
   The display clock correctly sat it out; the send clock kept firing
   until depth hit its 4-tick cap, and once inflated it never deflated —
   each applied pass freed a slot the banked send-time surplus refilled
   the same frame. Depth pinned at 4 from the first level intro onward.

2. *The adaptive ceiling was a ratchet.* The cap rose toward 8 based on
   measured "turnaround" (send of a tag → arrival of its echo). But
   turnaround includes the time your own tag spends queued at the relay
   behind your earlier sends, so a deeper pipe produced a longer
   measurement, which justified a higher cap, which allowed a deeper
   pipe. One-way positive feedback to maximum: input sampled ~640 ms
   before it acted.

Neither bug was reachable by any gate in the suite, because every test —
headless, e2e, LAN bench — ran at sub-millisecond turnaround where the
cap never lifted. **This is the single most important lesson in this
document and §2.3 exists because of it.**

The user's verdict after play-testing: *a slow-but-obedient character
beats a fast one that ignores your fingers.* Any design that samples an
input long before it acts will be rejected again, however good its
throughput. Treat that as a hard requirement, not a preference.

**One correction to carry forward.** The 640 ms was the bugs, not the
inherent price. In a correctly anchored pipeline, depth is *computed*
(⌈RTT/τ⌉) rather than *accumulated*, so it cannot inflate through a pause
or ratchet on its own queueing; at 120 ms RTT that is depth 2 and ~120 ms
of lead. But the physics that remains is real and applies to the
deadline-advance design too: **any full-rate scheme without rollback uses
a remote seat's byte roughly one-way-latency after it was sampled**,
and the visible overshoot after a key release is about `RTT/τ + 1`
steps. Deadline-advance moves the waiting from the client's queue to the
relay — which makes the *inflation class of bug structurally impossible*,
a genuine win — but it does not repeal the latency. Do not let anyone
(including this document) claim it gives a one-tick sampling lead for
remote seats.

## 2. Phase 1 — measurement (the only phase currently authorised)

We are choosing between designs whose costs are all functions of the far
seat's round-trip time, and we do not know that number. The pipelining
measurements are contaminated (see bug 2). Everything in Phase 2 is
gated on the numbers this phase produces.

### 2.1 Task A — clean RTT via PING/PONG

**Protocol.** Add to `shared/protocol.json`, then to the relay constants
block, then rebuild:

```
MSG_PING = 14   // client → relay: [type][u32 tag]
MSG_PONG = 15   // relay → client: [type][u32 tag] echoed verbatim
```

**Relay** (`server/relay.cpp`, in `onMessage`, near the `MSG_FP` case at
line ~869). Answer immediately, before any other work, in the same
`onMessage` call — the whole point is that a PONG never waits behind the
advance gate, the sync flow, or anything else. Do not require a seat: an
unseated connection may ping. Do not touch `passStartMs`.

```cpp
case MSG_PING: {
  if (n < 4){ drop(c, "bad PING"); return; }
  std::vector<uint8_t> m; m.push_back(MSG_PONG);
  m.insert(m.end(), p, p + 4);          // tag, verbatim
  queueMsg(c, m);
  break;
}
```

**Client** (template region matching generated lines ~11305–11560). Send
one PING per second from `netFrame` while `net.phase === 'live'`, tag =
a monotonically increasing counter, keep `{sentAt}` in a small map
(cap it at ~8 entries and drop the oldest, so a dead link cannot grow
it). On PONG, compute `netNow() - sentAt` and fold into:

```js
net.rtt = { min: Infinity, med: 0, worst: 0, samples: [] }  // last 30
```

Median over the retained samples; `min` is the most useful single number
(it is the floor the link can do, free of transient queueing).

**Do not** send PINGs from `netPump` — a hidden tab is not a
representative sample and will pollute the window.

### 2.2 Task B — per-seat relay wait, reported in PASS

This is what separates "the wire is slow" from "one seat is slow" from
"the phases are misaligned", and it is the number bug 2 lacked.

**Relay.** Add `uint64_t inAtMs` to `Conn` (set it in the `MSG_INPUT`
case alongside `hasInput`). In `advanceOnce` (line ~714), when the PASS
message is built, append one byte per seat after the existing direction
bytes: `min(255, (emitMs - inAtMs) / 4)` — quarter-tick units at the
80 ms play tick, 0 for an empty seat. Emitting *extra trailing bytes* is
safe for old clients (they read `count` directions and ignore the rest),
but bump the protocol version anyway and record the wire format in
`shared/PROTOCOL.md`.

**Client.** In `netOnMessage`'s PASS branch (line ~11423), read the
trailing bytes if present and keep the worst per seat over a 5 s window
alongside the existing `net.stat`.

### 2.3 Task C — the test shim that would have caught both bugs

**This is not optional and it is not last.** Build it before Phase 2,
because Phase 2 is where it earns its keep.

`netStart(url, cfgLocal, tpFactory)` already accepts a transport factory
(generated line ~11354) — tests drive the handlers directly. Add a
delay/jitter/loss shim implementing the same three wires:

```js
function netLagTransport(opts){        // {rttMs, jitterMs, lossPct, seed}
  // returns a tpFactory; deterministic PRNG from seed, never Math.random
  // queues both directions through a virtual clock the test advances
}
```

Requirements:

- **Deterministic.** Seeded PRNG. A failing run must reproduce exactly.
- **Virtual clock, not `setTimeout`.** The test drives time; otherwise a
  CI box under load produces flaky results and slow suites.
- **Loss and reordering** as separate knobs from delay.

Then add a scripted session to the existing headless/e2e gates that runs
at **`rttMs = 120` and includes a level-entry pause**. That combination —
real RTT plus the ~4 s `simT` charge — is exactly what neither bug could
survive and no existing gate produced. Assert:

- the exchange rate over the session matches `1/tickSeconds()` within a
  tolerance;
- **the sampling lead never exceeds its design bound** (for stop-and-wait,
  one tick; for any Phase 2 design, whatever that design claims). This
  assertion is the one that fails on both historical bugs. Write it so
  it *would have* failed on them — if it passes on a deliberately
  reintroduced 4-tick pin, it is not testing the right thing.

### 2.4 Task D — rollback feasibility numbers

Ten minutes, no code shipped. In the console on a live game:

```js
// with the game in 'play', mid-level, actors alive
console.time('snap'); for (let i=0;i<100;i++) game.snapshot(); console.timeEnd('snap');
// and a restore that SKIPS reset() — reset() is the expensive part and
// rollback does not need it (same cfg, same level build)
// and:
console.time('tick'); for (let i=0;i<100;i++) game.stepTick({netDirs:[0,0]}); console.timeEnd('tick');
```

Record all three per-call figures in the report. The threshold that
matters: **save + restore under ~2 ms and a tick under ~1 ms** makes a
4-tick rollback window cost <10 ms per confirmation at 12.5 Hz, which is
affordable. Well above that and rollback is off the table for the JSON
snapshot and would need typed-array state — a much larger job.

### 2.5 Task E — the rAF fix (ship this regardless)

Independent of everything above and worth doing now: PASS currently sits
in `net.pendDirs` until the next animation frame, and the reply goes out
in that same frame. That is ~8 ms average, ~17 ms worst at 60 Hz and
double on a 30 Hz laptop, added to *every* round trip.

Apply in the message handler — `netPump` already does exactly this for
hidden tabs, so the code path is proven — and let rAF do rendering only.
Keep sends on a timer/clock derived from `simT`, never on the frame.

Verify `sound.flush(game.sound.log, game.simFrame)` still runs on the
same cadence; the hidden-tab path flushes explicitly for this reason and
the visible path must not lose it.

**Acceptance:** no behaviour change on LAN, measurable drop in
INPUT→PASS turnaround under the lag shim at `rttMs = 40`.

## 3. Phase 2 — the decision tree (do not pre-empt it)

Read off the measured far-seat RTT (`r`) against the play tick
(τ ≈ 80 ms).

### 3.1 If `r < ~60 ms` — do nothing more to `play`

Stop-and-wait is already at or near full rate in `play` once §2.5 lands.
The slowness lives in the 50 Hz modes, where τ ≈ 20 ms and break-even is
single-digit RTT. Targeted fix:

**Exchange one byte per four frames in `attract`/`over`/`rewind`**, i.e.
make the wire's tick uniform at `PASS_SECONDS` while the sim keeps
stepping video frames. The client applies the echoed byte to all four
frames of the group. Safe because the join latch is a held-key model
(`netLocalDir`'s `autoFire` rides every byte until `q.inGame`), so a
four-frame hold changes nothing about how a join is detected.

Touches `netFrame`/`netPump` pacing and nothing in the relay. Cheapest
real win available and it makes the lobby as latency-tolerant as the game.

### 3.2 If `r ≈ 80–150 ms` — relay deadline-advance

The relay emits PASS(N) on a deadline rather than waiting for every
seat; a missing seat is substituted with its **previous byte**. No input
is ever queued client-side, so the inflation class of bug is structurally
impossible.

Determinism is preserved: every client — the late one included — steps
the echoed byte. The late player loses those inputs; because Gauntlet
directions are held keys, "repeat last" is mostly invisible.

**The traps, which are the same ones that bit pipelining:**

- **Cadence floor, or the relay free-runs through a level pause exactly
  as the send clock did.** The sim-ignorant way: INPUT carries the sim
  cost of the last pass this client applied (2 bytes: ~80 normally,
  ~4080 on a level entry) and the relay refuses to emit before
  `prevEmitMs + cost`. The relay still knows nothing about the game — it
  is relaying a number the client computed. This one rule also replaces
  the hidden-tab free-run guard in `netPump`.
- **A byte tagged for an already-emitted pass must update the seat's
  slot, never be dropped.** The current `if (ip != pass) break;` in the
  `MSG_INPUT` case (line ~861) would make a routinely-late far seat
  permanently mute. This is the single highest-risk line in the change.
- **Grace window.** Start the deadline on the *first* fresh byte of the
  pass, so a LAN seat is never substituted. A seat substituted `k`
  passes running opts out of setting the cadence, so one dead seat stops
  slowing everyone.
- **PASS carries a used/substituted mask** so the client can display it
  and the gates can assert on it.

Nothing changes in determinism, fingerprints, or snapshots. The client
side is a handful of lines. **Expected cost at r = 120: host gets
offline-grade latency (~45 ms, vs ~48 ms offline); far seat pays about
one extra step of overshoot on release.** At r = 300 the far seat pays
three or four steps — if the measurements land there, expect the same
verdict pipelining got, and go to §3.3 instead.

### 3.3 If `r > ~150 ms` and §2.4's numbers allow — rollback

The only design that satisfies the user's verdict *at full rate*. Local
input applies immediately; remote seats predicted as "same as last
tick"; a disagreeing PASS restores tick N and re-steps. **Your own byte
is echoed verbatim, so your own character is never mispredicted** —
obedient and full-rate at once — and pipe depth becomes a CPU cost
rather than a feel cost.

Foundations already exist: a deterministic sim, the SNAP_GAME/SNAP_PLAYER
manifest ("one manifest, walked by both directions, so a field cannot be
saved and not restored"), and `fingerprint()` to catch mistakes.

Unsolved piece, decide before starting: **audio.** Either flush only
confirmed ticks (sound lags video by the window) or flush predicted
ticks and tolerate the rare rolled-back beep. Do not start the
implementation without picking one — the sound bridge is clocked off
`game.simFrame` and will not tolerate ambiguity here.

This is a seam rewrite, not an adjustment. Scope it separately.

## 4. Working agreements

- **One PR per phase.** Phase 1 lands and is read before Phase 2 starts.
- **Every new mechanism gets a gate at `rttMs = 120` with a level pause
  in it** before it is called done. If a proposed change cannot be
  tested that way, say so in the PR rather than shipping it untested.
- **Never widen the relay's knowledge of the game** (Rule 3).
- **Report contradicting numbers loudly.** If Task D shows `snapshot()`
  at 20 ms, or Task A shows a 15 ms RTT that makes this whole plan
  moot, that is the most valuable output of the session — lead with it.
- **The verdict stands.** If a design's sampling lead exceeds one tick
  for the local player, it needs an explicit decision from the user, not
  an assumption that the throughput justifies it.
