## The dungeons — 307 of them, off the tape

`build/packdata.json` (written by `tools/packexport.py`) carries the **307
dungeon records of tape side 2** — 125 distinct byte-strings, 35,697 bytes —
and the engine expands them with a transcription of the original's own
`$97CB`. What ships is the original's DATA and the original's ALGORITHM, not
a captured picture of one map, and that is what makes the closure test below
a test of the decoder rather than of a copy.

### The container

A side-2 block is a **pack**, and there are 31 of them.

```
+$000  2   the pack's total length, little-endian
+$002  4   constant filler (FD 35 3C C8 in all 31; dead -- see below)
+$006  179 THE PACK'S OWN STUB, byte-identical in all 31 packs, EXECUTED
+$0B9  20  ten 16-bit sub-block lengths (0 = unused)
+$0CD  3   the stub's scratch
+$0D0  ..  the sub-blocks, back to back
last   1   $FF
```

`$0D0 + sum(lengths) == len(pack) - 1` for all 31 packs, exactly; every
record's own length byte agrees with the pack's table; every byte of every
pack is accounted for. `tools/packexport.py` asserts all of that on the way
past, so a corrupt extraction fails the build rather than the gate.

**The loader executes what it loads.** `$9278 LD HL,$C000 / PUSH HL /`
(zero six bytes) `/ $9283 RET` jumps into the block. The six zeroed bytes are
six `NOP`s; the stub at `+$006` then runs, and it — not the game — decides
which sub-blocks become levels:

* **flag `$80`** (block 0): `$84CC := $80`, `$84CD := $C0`, and all 7 of its
  records go to the stash verbatim. **Dungeons 1–7 are fixed.**
* **flag `$C0`** (blocks 1–30): draw FOUR distinct indices; three become the
  stash and the fourth is played immediately off the raw buffer. `$84CC := 7`.
  **One pack is four levels**, and sub-blocks 8 and 9 are the treasure rooms.

The stub's `pick()` rejects any value equal to the *current* C, D or E, and
`+$019 LD DE,0` zeroes two of them first — so 0 is rejected by the first three
draws and **sub-block 0 can only ever be the fourth**, i.e. stash record 0.

### A record is one dungeon

```
+0  length low byte      (9th bit = bit 7 of +2)
+1  flags   b0 -> SET 5,(IY-1)   b1 -> SET 4,(IY-1)
            b2 -> the "one random $36 survives" pass $9B5F   (114 of 307)
            b3-b5 -> the WALL BANK index ($9AB9, $F524 + n*$210)
            b6 -> suppress the $5A3E attribute clear         (7 of 307)
            b7 -> suppress the $423E bitmap clear AND walk the fixed border
                  for 3 bytes instead of 4, i.e. NO LEFT WALL COLUMN
                                                             (52 of 307)
+2  b7 = the 9th length bit;  b3-b5 = the colour scheme ($7D9C[n])
+3  the vector table's length IN BYTES
+4 .. the vector table, then the RLE cell stream
```

`$97CB` builds it in this order — read off the machine at `$9880..$98A7`,
not paraphrased:

```
$981A clear $8000..$83FF      $9827 reset the actor list ($8494/$8496)
$9845 the record's vector table    $9855 the fixed border at $7DB4
$9871 the RLE stream
$9893 CALL nz,$9B5F   (flags bit 2)
$9896 CALL $9BB7      the level>=8 extra objects
$9899 CALL $9B0E      the actor-list partition
$989C CP 8 / RET c ; $98A2 CALL $9C06 ; $98A5 JP $9C69     the two mirrors
```

**`$9BB7` runs BEFORE `$9B0E`.** An earlier write-up had them the other way
round.

**The vector table (`$98C6`)** is turtle graphics with two entry kinds told
apart by the top three bits of consecutive bytes: a POINT is two bytes
(`tag<<5|col`, `tag<<5|row`) which sets the pen and moves the cursor
absolutely; a RUN is one byte (`dir<<5|(count-1)`) which steps the cursor by
`$7DA4`'s deltas and paints, keeping the pen. The disambiguation reads up to
three bytes past the entry — safe, because the smallest RLE body over all 307
records is 60 bytes, so the lookahead never leaves the record.

**The RLE (`$9871`)**: `$00..$12` repeat the current tile n+1 more times,
`$13..$7F` set and paint a new one, `$80..$FF` skip `(n&$7F)+1` cells. The
cursor is a plain `INC HL` and does **not** wrap, so a long stream spills past
`$83FF`; the decoder spills with it.

**Walls (`$99BA`)**: the cell value IS the connectivity — bit 0 up, 1 right,
2 down, 3 left, `$10` isolated — and placing one re-connects its neighbours
through `$9A04`, which resets an isolated `$10` to 0 on the way past.

**`$3F` is the player start** and anything above it is an **actor**:
`type = (((t>>1) & $1C) | (t & 3)) * 8`.

### The mirrors move the actors

`$84C7` is drawn from the RNG at `$91B5` on **every** level ≥ 8; bit 1 runs
`$9C06` (rows reversed, then rotated one cell right) and bit 0 runs `$9C69`
(the same down the columns), each with the wall bits transposed.

**Both end in the same tail, `$9C3D..$9C68`, and it transforms the player
start AND EVERY ACTOR:**

```
x := ((x XOR E) + 1) AND $7C ;  y := ((y XOR D) + 1) AND $7C
```

with `DE = $007F` for the horizontal mirror and `$7F00` for the vertical,
stride 4, count `$8496`. **MEASURED HERE, three ways**: write-watching
`$5C00..$5CFF` through a level-8 build with `$84C7 = 3` logs `$9C5B` (x) and
`$9C62` (y) and nothing else; forcing `$84C7` over 0..3 on pack 16 sub 5 moves
all 147 actors exactly as those two lines predict; and the closure test below
compares the actor list in all four orientations. An earlier write-up said
"the actor list is NOT mirrored" — that is **false**, and since a level ≥ 8 is
mirrored three times in four, a port that believed it would spawn every
monster in the wrong place on ~75% of the game.

### THE LEVEL CLOSURE TEST

```
python tools/levelgate.py     -> build/levelcheck.json, from the REAL Z80
node   tools/headless.js      -> 307 + 24 + 7 checks against it
python tools/packgate.py all  -> the same comparison against packdecode.py
```

`levelgate.py` drives the original's own `$97CB` over each record's **tape
bytes** and dumps the grid it leaves in live RAM at `$8000..$83FF`, its player
start and its actor list. The engine then rebuilds each one and the two are
compared cell for cell:

| | result |
|---|---|
| all 307 dungeons, 1024 cells each | **307/307 at 1024/1024** (314,368 cells) |
| player start and actor list, in the original's own order | **307/307** |
| the two mirrors, 6 records × 4 orientations of `$84C7` | **24/24 at 1024/1024**, actors included |
| the whole `$B3D0` path (tape → stub → `$91D7` → `$9175` → `$97CB` → placement), dungeons 1–7 | **7/7 at 1024/1024**, and the player lands on the record's own start every time |
| the four difficulty bytes `$84A0/$84BD/$84BE/$84BF` out of live RAM | **7/7** |

The two RNG-driven passes are switched off on **both** sides for that count —
`$9B5F` through the record's own flags bit 2 and `$9BB7`/the mirrors through
`$8403 < 8` — because `$B575` is `LD A,R`; the mirrors are then tested
separately with the level forced to 8 and `$84C7` forced to each value. The
mirror check has teeth: with the old "actors are not mirrored" rule it scores
9/24.

**An independent corroboration nobody arranged:** `build/assets.json`'s
dungeon-1 grid, captured out of live RAM by the tile-harvest months earlier,
is **1024/1024 identical** to the tape-only decode of pack 1 sub-block 0, and
its 63-object list matches too. That is a headless check as well.

### The sequencing — the game never indexes the tape

There is no pack number anywhere in the code. `$9203` asks the ROM for the
next block whose flag equals `$84CD` and takes whatever arrives; the tape's
physical order is the level order. `$9175` is the whole selector:

```
level < 8   $9184 BIT 7,(IY+$4D)  do we hold the $80 pack?  if not, load it
            $9193 E = 1 << (level-1)      -> record level-1 of block 0
level >= 8  $919C DEC (IY+$3B)            the treasure countdown $84BA
            $91A1 reload 4 + rand&3, SET 6,(IY-1), CALL $915E
            $91B2 $84C7 := rand           THE MIRROR BYTE
            $91B8 mask = $84CC AND $7F ; if 0 -> LOAD (the stub picks)
            $91BF bonus -> E=4, else bit0 -> E=1, bit1 -> E=2, else E=4
            $91D3 $84CC := mask XOR E     <- and this DROPS BIT 7
```

so the mask walks `7 → 6 → 4 → 0` and the fourth level triggers the next load.
`$91D3` writing back the *masked* value is why warping below level 8 after a
stash record has been consumed makes `$9184` demand the `$80` block again,
with no REWIND prompt.

**`$84CC` and `$84CD` are not reset by a new game.** MEASURED two ways: the
whole live image writes `$84CC` at exactly one site (`$91D4`, plus the pack's
own `$C00D`) and `$84CD` at exactly one (`$918A`, plus the pack's `$C010`);
and a write-watch over `$84B0..$84CF` while running `$B35A..$B381` with both
poked to `$A5`/`$5A` logs only `$84C8`, `$84C9`, `$84BA`, `$84CA` and `$84CB`
— the two come out unchanged. They are zero at **cold boot only**, which is
exactly why `$B48F` is `BIT 7,(IY+$4D) / RET nz` and not an unconditional
"REWIND TAPE TO START OF SIDE 2" prompt: die on dungeon 3 and the tape has not
moved.

### The difficulty scalers, `$B401..$B428`

`$B466` is `B += floor(level / C)` with `INC B / JR nz` **saturating at 255**:

| | | |
|---|---|---|
| `$84A0` | `50 + level/2` | the generator spawn threshold |
| `$84BE` | `5 + level/12` | how many extra objects |
| `$84BF` | `25 + level/2` | which type they are |
| `$84BD` | `180 + level` | the drop threshold — and note `$9BCC CP C / JR c` skips when `rand < $84BD`, so the drop gets RARER with depth and is impossible from level 75 on |

All four are checked against the bytes the original leaves in live RAM after
`$B3D0`, for dungeons 1–7.

### The map tiles are per-level, and that is why they were mostly missing

A tile is the **same 33-byte sprite record** as everything else, reached
through the same `$7B00` table with `id = ((cell − 1) & $7F) + 1` — `$9F7A`'s
`DEC A / ADD A,A` has no mask, so an 8-bit index makes `v` and `v+$80` share
an entry and the "second wall graphic" bit 7 draws identically. `$9AB9`
rebuilds sixteen of those pointers at every level start from one of five
16-record banks at `$F524 + n·$210` and stamps them all with `$7D9C[colour]`.

Seventeen tiles sampled off one dungeon's screen covered **89.5%** of the
cells across the 307 dungeons, and on 33 of them more than half the furniture
was invisible. `tools/maptiles.py` decodes the records instead: coverage is
now every value that occurs (63 of them), and the cross-check is that 15 of
the 16 sampled tiles are byte-identical to the record this scheme picks. The
odd one out is `$13`, which is the animated tile `$A31A` repoints — the screen
capture caught one frame of it.

### What is PROVISIONAL here

* **The draws.** Which sub-blocks a `$C0` pack yields, which `$36` survives,
  `$84C7`'s orientation, `$9BB7`'s objects and the actor record's 4th byte are
  all `LD A,R`. The RULES are transcribed and gated; the DRAWS are a
  substitute, and the port keeps them in a **separate stream** from the play
  entropy so that seeding a level cannot move the differentials. That is a
  property of the substitute and it is declared in the code.
* **Running off the end of the tape.** Level 128 leaves the ORIGINAL sitting
  in the ROM loader for ever (the deck reports NOMATCH). A player would rewind
  and the next `$C0` block after a rewind is block 1, so that is what the port
  does. Labelled in `Tape.load`.
* **`$9689`'s placement search.** The port puts the player on the record's own
  start, which is what the original does on all seven measured dungeons; the
  `$B2E3`/`$B2B6` nudge for a start cell that is occupied is read, not driven.
* **Byte +2 bits 0–2** of a record are read by no code on the build path.
  About a third of records set each. Still unexplained.
* **The six bytes at pack offset `+$000..+$005`** are zeroed before the `RET`
  jumps there, so they never execute. Bytes 2–5 are `FD 35 3C C8`
  (`DEC (IY+$3C) / RET z`) in all 31 packs. Dead in the shipped game.

## The level format is closed

The dungeon is a **32×32 grid at `$8000`–`$83FF` that wraps in both axes**.
Recovered from the cursor routines, not guessed:

```
$9A2D  INC L / LD A,L / AND $1F / RET nz / SUB $20    step right, column wraps
$9A3D  LD A,L / ADD $20 / RET nc / INC H              step down,  +32 per row
$9A18  LD A,L / SUB $20 / ... CP $7F / ADD 4          step up,    H wraps $7F->$83
$9A51                                                 step left
$9A27  LD A,C / ADD 4 / AND $7F                       one cell = 4 units
$9A37  LD A,B / ADD 4 / AND $7F
```

One cell = 4 coordinate units = **16 screen pixels**, so the world is 512×512
and the 256×160 playfield is a quarter of it — which is why the game scrolls.
Coordinates are 7-bit (`RES 7,C`), so the world is 128×128 units.

**This replaces the earlier guess entirely.** The object list at `$5C00` that
looked like the map is not it — that is the actor scan list used by `$A97F`,
and the harvest sweep proved it (identical 63 entries from 121 camera
positions, all at y 64..80 while the player sits at y=8).

## The movement and wall rules

`$A8E7` is the cell test:

```
$A8E7  LD A,(HL) / AND $7F
$A8EA  RET z            ; 0            -> free, carry CLEAR
$A8EB  CP $11 / RET c   ; $01..$10     -> BLOCKED
$A8EE  CP $13 / JR nc,$A8FC
$A8F2  LD A,(IX+8) / SUB 1 / RET c     ; $11..$12 -> a DOOR, costs a key
$A8FC  CP $20 / JR c,$A919             ; $13..$1F -> $A919
$A919  LD (IX+$1E),L / LD (IX+$1F),H / LD (IX+$1D),A / AND A / RET
                                       ; records a PENDING INTERACTION and
                                       ; returns carry CLEAR -- it does not block
```

`$A919` is the **recorder**, not a blocker, and the whole chain behind it is
now ported — see *The interaction chain* below.

The four direction handlers were **read, not mirrored** — see below:

```
$A82F right  INC C,INC C  BIT 1,C  $9A2D right   BIT 1,B  $9A3D down   undo DEC C
$A85D left   DEC C,DEC C  BIT 1,C  $9A51 left    BIT 1,B  $9A3D down   undo INC C
$A88B down   INC B,INC B  BIT 1,B  $9A3D down    BIT 1,C  $9A2D right  undo DEC B
$A8B9 up     DEC B,DEC B  BIT 1,B  $9A18 up      BIT 1,C  $9A2D right  undo INC B
```

Two properties that a reimplementation would never produce:

* **The `BIT 1` gate is SET in every direction** — the map is consulted only
  on alternate 2-unit steps, never on the others.
* **The second probe is always down-and-right**, never mirrored to up-and-left.
  That is the player's 16×16 body straddling cells, and it is kept deliberately.

`$A924`/`$A944` are the TWO-PLAYER LEASH — see *Two players* below. This
note used to call them "a stray-distance test which can never fire for the
player himself"; that is **wrong**. They compare the candidate against the
OTHER PLAYER's coordinate (`LD A,IXL / AND $20`) and refuse a move whose
short-way separation would reach `$3D` across or `$25` down, and they fire
constantly in a two-player game. What is true is that they are inert with one
player, and the reason is `$A926`'s `AND $20` clearing carry before the
absent-partner `RET nz` — not the step size. (What this note did get right:
they are never entered on the ACTOR path — the actors have their own probe at
`$ADF8`, and neither they nor `$A8E7` fired in 60 instrumented passes.)
Both are now ported.

## A move passes THREE gates, not one

```
$A5F0  CALL $A97F / JR nc,$A616     ; 3. the ACTOR scan -- a linear walk of the
                                    ;    4-byte records at $5C00 (count $8496)
$A620  LD (IX),C / LD (IX+1),B      ;    commit
```

with the map test (`$A8E7`) and the stray-distance test inside the direction
handlers before it. The actor scan is **not** a grid lookup and **not** the
map: it is a 7×7 box test against live actors, and it is self-modifying — the
Y comparison operand at `$A9B8` is written by `$A991`.

### Correction: the scan is NOT inside the direction handler

This engine used to call the scan from inside `tryStep`, which put it **behind
the `BIT 1` gate** — so on every other 2-unit step no scan happened at all.
The original's shape is different and it is worth writing out, because it is
what the down residual finally turned on:

```
$A58F  LD E,A / LD C,(IX) / LD B,(IX+1) / CALL $AE6D   ; BC = the candidate
$A599  AND 3 / JR z / CP 3 / JR z        ; up+down held together CANCEL
$A5A2  RRA / CALL c,$A8B9                ; up        <-- VERTICAL FIRST
$A5A6  BIT 1,E / CALL nz,$A88B           ; down
$A5AB  CALL $AE6D                        ; recompute the map cursor
$A5BA  AND 12 / CP 12 / JR z             ; left+right held together CANCEL
$A5C1  BIT 2,E / CALL nz,$A85D           ; left
$A5C6  BIT 3,E / CALL nz,$A82F           ; right
$A5F0  CALL $A97F / JR nc,$A616          ; the actor scan, ONCE, on the final
$A616  CALL $AAC4 / RET c                ; a FOURTH gate: the OTHER PLAYER
$A61A  LD A,(IX+$1D) / OR A / JR nz      ; a pending interaction cancels it too
$A620  LD (IX),C / LD (IX+1),B           ; the single commit
```

Four handlers step one shared candidate and undo on failure; the scan and the
commit happen once. Opposite directions cancel (`AND 3 / CP 3`), and the
vertical pair is resolved **before** the horizontal one. `$AAC4` — the other
player's body, a 7×7 box on the candidate square — is a real fourth gate that
nobody had listed. It is now ported: it cannot fire with one player because
the other block's `+$0B` bit 6 is set from the tape, and with two it also
decides, through bit 3 of `(IX+$0E)`, which player's update runs first on the
NEXT pass. See *Two players*.  There are FIVE gates in a two-player game: the
leash, the map, the actor scan, the other player, and the pending
interaction.

## The differential — and the correction that made it mean something

`tools/sim_move.py <dir> <n>` (real Z80) and `node tools/headless.js --table
<dir> <n>` (built engine) print the same table with the same arguments;
`python tools/pointdiff.py` runs both sides for all four directions and
reports the mismatching rows.

| direction | 30 rows | 60 rows | 100 rows | 160 rows |
|---|---|---|---|---|
| right | **0** | **0** | **0** | **0** |
| left | **0** | **0** | **0** | **0** |
| up | **0** | **0** | **0** | **0** |
| down | **0** | **0** | **0** | **0** |

The table now carries a fourth column as well — the pending-interaction slot
`(IX+$1D)` as it stands at the end of each pass — and that agrees too, so the
engine is not merely arriving at the same coordinates, it is spending the same
passes on the same interactions.

### CORRECTION: the down-60 residual was a BROKEN RULER, not a missing rule

This file used to say:

> Beyond 30 rows: right, left and up agree for 60/60; down agrees for 58/58
> and then diverges at pass 59 … The original spends **two** passes on the key
> (`$1F`) at cell (3,31) and this engine spends one.

**That is wrong, and it was wrong in a way that cost three separate
investigations a great deal of effort.** The original spends exactly ONE
refused pass on that key. The two-row disagreement was manufactured by
`tools/sim_move.py`, which advanced the machine by `run_frames(h, 4)` and read
the coordinates afterwards — a four-video-frame window, on the strength of
Q10's "one main-loop pass = four video frames".

Measured here, before anything was changed:

* `$8503` is visited **exactly once per pass**. Counting increments of the
  pass counter `$8491` between consecutive visits gives `{1: 97}` over 97
  passes — never 0, never 2. So "step until PC == `$8503`" is a sound
  one-per-pass sampler *by construction*, whatever a pass costs in frames.
* **A pass is not four frames.** Over the same 97 passes:

  ```
  3.92:1  3.94:1  3.97:38  3.98:1  4.00:3  4.02:1  4.03:45  4.06:1
  4.96:1  4.97:4  5.03:1
  ```

  a mean of 4.0 with a tail out to 5.03. Holding down, pass 58 — the key
  pickup — costs 5.03 frames, so from row 59 onward every 4-frame sample lands
  *inside the previous pass*, and the old table printed y=120 three times
  instead of twice.
* The overrun is **not** the pickup: with the actors disabled (`$8496 = 0`) no
  pass in the run exceeds 4.03 frames, and erasing the key cell leaves the long
  passes in place.

`tools/sim_move.py` now steps to `$8503`. Q10's 12.52 Hz stands as an *average*
and is still the right number for the engine's clock; what does not stand is
using four frames as a **sampler**. `--frames` adds the per-pass cost back as a
diagnostic column, and it is worth keeping: a pass over 4.5 frames is a real,
watchable event (the `$2F` map sweep costs 5.03, an inventory pickup 103.8, a
level reload 271.8).

### What the differential caught, in order

Each of these was found by the tables disagreeing, not by reading:

1. **The wall map was not where I thought.** The engine walked through walls.
2. **Left and up are not mirror images of right and down.** I inverted the
   `BIT 1` gate assuming they were, and the tables reported 18/22 and 20/22
   rows wrong. Manual D3, exactly.
3. **The map cursor sits on the OLD coordinate's cell**, not the new one.
4. **Map value `$13` costs a pass.**
5. **A move has a third gate**, the actor scan — traced to `$A9BE` by diffing
   the PC path of a stalled pass against a moving one *with the same animation
   phase*.
6. **The ruler itself was wrong** (above). The lesson is the manual's G1:
   verify the measuring code before the measured code. Three investigations
   looked for a rule that would make the engine stall twice; the engine was
   right and the tool was not.

## Actors

Tools: `python tools/actorgate.py all` prints every number in this section
(it drives the real Z80 and never loads the engine);
`python tools/actorframes.py` decodes the monster sprite records into
`build/actor_frames.json`, which `tools/build.py` inlines.

The 4-byte records at `$5C00` **are** the whole monster. There is no second,
larger block: count at `$8496`, tail at `$8494` (always `$5C00 + 4*count`),
cap 192 (`$AA0E CP $C0`), which is exactly `$5C00..$5EFF` — the gap below the
sprite bank at `$5F00`.

```
+0  x      7-bit world coordinate, wraps at 128
+1  y      7-bit
+2  state  bits 7:5 CLASS 0..7   bits 4:3 TIER 0..3   bits 2:0 FACING 0..7
+3  flags  bits 7:6 walk phase   bit 5 blocked-last-try   bit 4 wall-follow
           side   bit 3 invisible   bit 2 generator-spawned   bits 1:0 countdown
```

`$8418..$841F` = `01 09 08 0A 02 06 04 05` maps a facing to the **player's own**
direction bits (1 up, 2 down, 4 left, 8 right), so the eight facings are the
same compass slots `$7D0C` gives the player: `0 N, 1 NE, 2 E, 3 SE, 4 S, 5 SW,
6 W, 7 NW`. `$8460..$8468` = `06 02 00 04 02 06 04 00 06` is the wall-follow
deflection table, indexed `[facing + side]`; every entry is a cardinal.

### THE MAIN LOOP ORDER — a correction that four investigations got wrong

Read from the CALL list, `$851E CALL $AB94` (actors) sits before
`$8521 CALL $A43B`, and every earlier report concluded *"the actors move, then
the player moves against their new positions"*. **That is backwards.** `$A43B`
is the player's frame/draw bookkeeping; his **move** is reached from
`$8509 CALL $A38A` → `$A3AF CALL $A4DD`, which is *before* `$850C`. Hooking
`$8503`, `$A5F0`, `$B58C` and `$AB94` on the real Z80 gives, every pass:

```
$8503 TOP  ->  player move + actor scan  ->  $850C camera  ->  ...
           ->  $851E ACTOR LOOP  ->  $8550 -> $9CFB pass counter ++
```

(The stack at `$A5F0` reads `[$A3B2, $850C]`, which names the caller outright.)
So **the player moves first**, the camera is then stepped from his new
position, and the actors run last, culled against that camera. The engine's
`onePass()` is in that order. Getting it the other way round moves the ghost's
step to the wrong side of the player's scan.

The pass counter `$8491` is incremented **at the bottom** of the loop
(`$9CFB`), so everything within one pass sees one value. It is seeded from the
saved state (66), not started at zero — the round robin below depends on it.

### THE UPDATE IS A CALLBACK FROM THE RENDERER

`$ABB1` patches `CALL $ABFF` into a three-NOP hole at `$A21E`, which is inside
the sprite draw routine `$A1DA` **after all four of its off-screen culls**;
`$ABF5..$ABFE` puts the NOPs back. So an actor outside the viewport is not
merely undrawn, it is **frozen** — no move, no retarget, no animation. That is
why nothing in the first dungeon stirs until the camera brings it into view,
and it is the mechanism behind the whole down residual.

The window, read to `$A1DA`'s four `RET nc`: `(x+3-camx)&$7F ≤ $42` and
`(y+3-camy)&$7F ≤ $2A`. **Gated:** predicting "reaches `$ABFF`" from the
record and the camera, matched **pairwise per loop visit** — 1,883/1,883
visits in the down run and 1,768/1,768 with the player warped into the horde,
0 mismatches. (Matching by *slot index* instead invents mismatches: a
swap-remove makes the loop revisit the same IX with new contents.)

### THE UPDATE, `$ABFF..$AD1B`

Transcribed instruction by instruction into `web/template.html` and then
differential-tested: feed the two `LD A,R` coins from a trace, run the model on
the record the real machine had, and compare all four bytes afterwards.
**4,589 updates, 0 mismatches**, over eight drives covering all six classes
(forced by repainting live records) and all four outcomes — moved, blocked,
no-move, walked-into-the-player. The order is:

```
$AC0E  ROUND ROBIN: carry = (slot ^ $8491) & 1.  An actor tries to move on
       ALTERNATE passes, staggered by slot parity, so the rate does not depend
       on how many are alive.  With $ADF8's 2 units that is 1 unit/pass --
       half the player.  Class >= 5 gets an extra go when $8491 bit 1 is set.
$AC25  LD A,R / RRA / JR c   -- 50%: KEEP the current facing, skipping BOTH
       the retarget and the wall-follow block below.
$AC2A  CALL $AD51 -> $AD77   chase player 1: $AD1C's wrapped Manhattan
       distance, $AD9B's sign -> compass slot.
$AC35  class 3 within 12 units: D ^= 4 -- it FLEES.
$AC46  if blocked last time, deflect through $8460[D + side]; the DEFLECTED
       direction is walked, the UNDEFLECTED one is what gets stored on failure.
$AC63  CALL $ADF8  -- step and probe (below).
$AC68  CALL $AEA0  -- a player on the candidate square: class 0 damages him
       and DESTROYS ITSELF, others attack and stay put.
$AC77  CALL $A97F  -- the player's own actor scan, with the actor hidden from
       itself by parking (IX+1) at 0 (self-modified restore at $AC8C).
$AC7C  commit;  $AC8D  revert, set bit 5, flip bit 4 if already blocked.
$ACA8  class 4 blinks (toggles the invisible bit at phase $C0).
$ACCE  the animation tick;  $ACF2  write the state byte back.
```

**`$ADF8` is not the player's `$A8E7`,** and the difference is measured, not
read. Isolation test: plant one value in an empty cell and call both routines
with the saved player block and 9 keys —

| cell | `$A8E7` (player) | `$ADF8` (actor) |
|---|---|---|
| `$00` | pass | pass |
| `$01 $05 $10 $20 $22 $33` | **BLOCK** | **BLOCK** |
| `$11 $12 $13 $15 $1F $30 $36 $38 $40 $7F` | pass | **BLOCK** |

Any non-zero cell stops an actor (`$AE2D LD A,(HL) / OR A / RET nz`): no door
rule, no interaction range. It also steps **2 units on both axes for a
diagonal**, which the player never does, consults the map on *every* step (no
`BIT 1` gate) and probes up to **four** cells — the 2×2 block a 16×16 body
straddles — with its own column wrap (`AND $1F / SUB $20`) and row wrap
(`INC H / SUB 4 / CP $80`).

That table also fixed a *player* bug this file had: `pass1` used to return
"free" for everything `≥ $20`, so the player walked through the twelve
generators in this dungeon. `$A8FC..$A918` is now transcribed in full —
`$20..$2E` block unless `(IX+$14)` bit 5 or `(IX+$15)` bit 3 is set,
`$33..$35` block, the rest are interactions.

### THE ENTROPY, AND THE LIMIT OF THIS PORT

There is no PRNG behind the two branches in the update: `$AC25` and `$AC4C`
read the Z80 **refresh register** directly. `R` counts M1 cycles, so no
reimplementation can reproduce it, and the harness's own `R` is already an
approximation (`_fast_halt` advances it by the refreshes it skipped). What is
measurable is the **consumption pattern**, and that is what the engine
reproduces:

* one draw per actor update, **bit 0 only**. Measured at `$AC25` over 494
  samples: 51.8% ones, uncorrelated with slot parity or pass parity
  (113/127/125/129 across the four cells).
* the second draw is **not independent**. `$AC4C` is reached only when the
  first was even, and the gap between the two samples is a near-constant
  number of M1 cycles: `R($AC4C) − R($AC25) mod 128` = 57 (73×), 59 (61×),
  54 (11×). Two of the three are **odd**, so `A & 3` is almost never 0 and the
  wall-follow deflection is skipped **3.4%** of the time (5 of 145) — not the
  25% the `AND 3` mask suggests. The engine derives the second draw from the
  first with the modal +57, which makes it always deflect: right on 134/145.

**Consequences, stated rather than buried.** The four 30-pass movement tables
are insensitive to the coin — proved by patching *both* `LD A,R` sites in the
real Z80 to `LD A,imm` (same length) and running all four policies: every row
of every table is byte-identical, only the actor count column moves. But actor
motion in general is not: warping the player into the 60-actor horde, every
actor position agrees for **12 passes** and then drifts (55/55 at pass 12,
15/48 by pass 26). In the down run the shipped engine agrees with the original
on **1,802 of 1,816** actor records over 28 passes; the divergences are slots
1 and 2, and they start at the first coin flip slot 1 ever makes.

## The interaction chain — closed

Tools: `python tools/sim_move.py <dir> <n> --frames` prints the per-pass table
with the pending slot and the frame cost; `python tools/doorgate.py plant`
drives a door opening cell by cell. Both drive the real Z80 and neither loads
the engine.

`$A919` is not a blocker and never was:

```
$A919  LD (IX+$1E),L / LD (IX+$1F),H / LD (IX+$1D),A / AND A / RET
```

It records a **cell address and a value** in the player block and returns
carry CLEAR. What costs the move is three instructions later in the pass:

```
$A514  LD (IX+$1D),0        at the top of EVERY move -- so a pending
                            interaction lives for exactly the rest of one pass
$A61A  LD A,(IX+$1D) / OR A / JR nz,$A65D    non-zero REFUSES the commit
$A620  LD (IX),C / LD (IX+1),B               the single commit, skipped
```

so **one item = one refused pass**, and the slot is thrown away next pass
whether or not anything consumed it.

Three details of the lifecycle are measurements, not readings:

* **A door is NORMALISED.** `$A8F8 LD A,$12` runs for a cell holding `$11`
  *or* `$12`, so the consumer never sees `$11`. Confirmed by watching every
  write to `$843D` over a door pickup: the pass writes `$A514:00 $A91F:12`.
* **An EXIT skips the horizontal phase entirely.** `$A5AE CP $36 / JR z,$A5D8`
  — with `$36` planted the pass writes only `$A514:00 $A91F:36`, no `$A5B6`,
  no `$A5D5`. Any other value gets the full save/restore (`$A5B6` clears the
  slot for the horizontal handlers, `$A5CB` re-reads it, and **horizontal
  wins over vertical** when both record).
* **The undo path DISCARDS the record.** `$A856`/`$A884`/`$A8B2`/`$A8E0`
  `LD (IX+$1D),0` sit immediately before the `RES n,E`, so a step whose first
  probe recorded an interaction and whose second probe hit a wall throws it
  away. Without this the player picks things up through a wall corner.

### CORRECTION: a generator costs 4h+1 or 4h+3, and the rule is the arithmetic

An earlier report gave 3/7/11 refused passes for `$20/$21/$22`. Driving it
myself from a different arrival phase gives **1/5/9**, and both are right: the
cost depends on which pass-counter phase the player arrives on. What is
invariant is the arithmetic, so that is what is ported:

```
$A6B5  BIT 0,(IY+$12) / RET z          ODD passes only
$A964  idx = ((IX+$15)>>1)&6, +4 if inventory bit 5; t = $7D70[idx]
       d = t>>1, and +1 only when (t&1) and $8491 bit 1 is set
$A6C2  hp = ((v - $20) & $FF) mod 3    -- the SUB 3 runs BEFORE the CP 3,
                                          so it is a do-while and $1F folds
                                          to hp 0 through the byte wrap
$A6CA  hp < d ? cell = 0 : cell -= d
```

For the elf (`$8435 = $20` plus inventory bit 5) the index is 4, `$7D70[4] =
$01`, and the damage **alternates 0 and 1** with bit 1 of the pass counter.
Combined with the `BIT 0` gate a hit lands only when `($8491 & 3) == 3` — one
per four passes. Measured by hooking `$A6CA`: visits at counters 71, 73, 75,
77, 79 with damage 1, 0, 1, 0, 1, and the cell walking `$22 → $21` (71) `→
$20` (75) `→ $00` (79).

### A pickup can cost TWO passes, and the mechanism is the HUD

This is the only route by which an item costs more than one pass that I could
reproduce, and it is not the actor pre-emption an earlier report proposed
(I could not reproduce that one: the key at (3,31) costs exactly one refused
pass with the actors on *and* off).

`$A790 BIT 2,(IX+11) / RET nz` refuses a key while the "key gained" HUD flag
is still pending, and `$A76D BIT 4` does the same for potions. The flag is
cleared by the redraw round robin, which only reaches the icon block on passes
where `($8491 & 2) == 0` *and* the selected field is not itself dirty.
MEASURED on the original with two `$1F` keys one cell apart and the actors
off, sampled at `$8503`:

```
ctr 70  keys 0 -> 1, f11 = $04       ctr 73  the player is REFUSED
ctr 71  f11 still $04                ctr 74  keys 1 -> 2
ctr 72  f11 still $04
```

so the first key costs one refused pass and the second costs **two**. Drop the
dirty-flag protocol as "just a redraw optimisation" and the pickup rate
changes. It is ported, and it is a headless check.

### The door animation, and a one-instruction idiom that doubles it

`$A6D4` spends the key and arms `$849A`/`$849C`/`$849E`; it never clears the
cell. `$8506 CALL $95AB` does the erasing on the following passes, walking two
cursors out of the opened cell and clearing every adjacent door cell.

```
$95AB  CD AE 95   CALL $95AE
$95AE  FD CB 1F 5E  BIT 3,(IY+$1F)     <-- the body starts HERE
```

**`$95AB` calls the very next instruction**, so the body runs TWICE per pass —
once from the `CALL`, and again by falling through when it returns. That is
the manual's family-C "stack as control flow", it is one instruction long, and
it is worth exactly a factor of two in how fast a door dissolves.

It was caught by the gate, not by reading. With the body run once the port
cleared three cells on the first animation pass and left `$849E = $A9`; the
original clears **four** and leaves `$29`. Two more details fell out of
tracing `$9625`'s entries (A and HL) on the real machine:

* the retry **reloads the cursor** from `($849A)` (`$95BB` is the jump target,
  and it is `LD HL,($849A)`), it does not carry on from where the failed probe
  left HL;
* the direction flip `XOR 2` is **local to A** — `$849E` is never written with
  it.

A first version got both wrong, cleared the right cells in one scenario and the
wrong ones in another, and left `$849E = $1A` where the original had `$3A`.
The port now reproduces two independent door scenarios cell for cell **and**
`$849E` for `$849E` over eight passes each.

### The exit walk, and an odd number that proves a routine exists

`$8537 CALL $94AE → $94E1` takes over once `(IX+11)` bit 6 is set: it nudges

### The exit direction, and exit-on-arrival

`$B1DA..$B1EC` rotates a single bit **clockwise from the player's own facing**
(`(IX+13) & 7`) until it hits the destination pad's free-neighbour mask, and
`$B315` decodes it: bit 0 up, 1 NE, 2 right, 3 SE, 4 down, 5 SW, 6 left, 7 NW
— the same ring `$B2B6` builds. `$B2E3` accepts a neighbour that is `0` *or*
`$36`, because `$B2E5` is a self-modified `CP` operand (`$96DD` writes `$80`
for a placement, `$9715` puts `$36` back), so **an EXIT is a legal teleport
destination**. `$B1FF` then reuses the pending slot as a memo of the cell
landed on, and four passes later `$B232 SUB $36 / JP $A687` **exits the
level**. That only works because `$A4FF`'s `JP` bypassed `$A514`: a port that
clears `pend` per pass during the flight silently loses it.

### The state

All four live in the 32-byte player block, and all four are simulation state,
not display state — every one of them feeds a rule:

| field | | why it is not display-only |
|---|---|---|
| `+2,+3` health | 2-byte packed BCD, big-endian | `$93CD` kills at exactly `0000` |
| `+4..+6` score | 3-byte packed BCD | wraps into `$84C8` |
| `+8` keys | plain binary | `$A8F2` turns a door from a wall into an interaction |
| `+9` potions | plain binary | `$A81D`'s capacity is keys+potions |
| `+11` dirty flags | see below | bits 2 and 4 **refuse a pickup** |
| `+$14` inventory | 6 bits + dead | bit 5 unlocks generator melee, bit 1 raises the cap |

They are kept **packed BCD** in the port rather than converted to integers,
because every operation the original performs on them is a DAA add or
subtract, and the clamps ($9999 on health, the wrap into the million counter)
and the leading-zero rendering all fall out of the packed form. `daaAdd`/
`daaSub` are gated against the original's own `$B7E9`/`$B852`/`$B807` driven
in isolation:

```
$1997 + $0100 -> $2097     $9989 + $0011 -> $9999 (clamped)
$1997 - $01   -> $1996     $0050 - $99   -> $0000 (clamped)
999900 + 000100 -> 000000 with $84C8 = 1
```

### CORRECTION: contact damage by tier is 10/20/30/**20**, not 10/20/30/40

`$A627` chooses the damage byte by testing the actor's TIER bits, and it tests
**bit 3 first**:

```
$A627  LD D,(IX+$18) / BIT 3,(HL) / JR nz,$A638      tier bit 0
$A62E  LD D,(IX+$19) / BIT 4,(HL) / JR nz,$A638      tier bit 1
$A635  LD D,(IX+$17)
```

so tier 3 (both bits) takes the tier-1 arm and a tier-3 monster does **less**
damage than a tier-2 one. `$8437..$8439` hold BCD 10 20 30, so the four tiers
cost 10, 20, 30, 20. MEASURED by repainting slot 0's tier and walking into it:
`$1995 →` `$1985 / $1975 / $1965 / $1975`. This engine gave tier 3 the tier-0
damage; nothing in dungeon 1 is tier 3, so no table caught it — the
disassembly did. And the numbers are **decimal read off the BCD digits**: a
port storing health as a plain integer must subtract 10/20/30/20, never
16/32/48.

### The drain, and the clock it runs on

```
$B6DA  LD A,($8497) / AND $C0 / CP (IY+$20) / JR nz,$B70E
$B6E4  ADD A,$40 / LD ($849F),A / INC (IY+$39)
$B6EC  LD D,1 / BIT 6,(IX+11) / ... / LD HL,$8423 / CALL $B852
```

`$8497` is incremented in the ISR (`$A2A2 INC (IY+$18)`, the only write site in
the game), not by the pass, so the drain is one BCD point per 64 **interrupt
handler invocations**. MEASURED over 5,200 frames: 82 ticks, gap histogram
`{64: 80, 65: 1}`, mean 64.01 = 1.278 s. A player whose bit 6 is set (exiting
or dead) does not drain.

**NO LONGER PROVISIONAL IN ITS RATE — this is the B2b payoff.** The engine now
keeps a T-state clock and advances `$8497` by the pass's own frame cost
(`quantise()`, and see NOTES-battery Q10 for the mechanism). A pass costs what
its work costs, so at a generator cluster the game runs at ~8.5 Hz instead of
12.5 and **the player pays about 40% more health per step taken**, exactly as
the original does. That is not cosmetic and it is what manual B2b is about.

Two measurements make it concrete, both on the real Z80 from
`build/state_48k.pkl`, 61 passes:

* holding RIGHT the pass is 4.13 frames, `$8497` advances 4.00 a pass, and the
  player ends on health `$1993` — three drain ticks.
* holding UP the pass is 5.00 frames, `$8497` advances 5.00 a pass, and the
  player ends on `$1992` — **four**. Same 61 steps, more health, because the
  game was slower.

`tools/headless.js` used to assert `$1993` for UP; that baseline was taken in
the flat-four era and was wrong. It now asserts `$1992` and the engine reaches
it unaided.

**WHAT IS STILL DECLARED HERE.** `$8497` counts handlers, and an interrupt
whose 32-T window lands inside one of the blitter's `DI` spans is lost. The
engine charges one handler per frame boundary, so where the original loses a
lot of them it runs fast: holding LEFT the original advances `$8497` by 4.016
a pass against a 4.525-frame pass, and the engine gives 4.5. Over the 64 ticks
between two drain ticks that is worth one pass, which is why `tools/p2gate.py`
still substitutes the original's `$8497` (0 rows with it, 41 of 289 without,
all of them a one-pass skew of `$842B` bit 0 with the same health either side).

### The redraw is a round robin, and it is load-bearing

`$B717`/`$B726` pick ONE field per pass — bit 1 of the pass counter chooses
the player and bit 0 chooses health or score — and only if that field's dirty
bit is set; otherwise the pass falls through to the icon block, which draws at
most one icon (key gained, key spent, potion gained, potion spent, in that
order). `$B756` cancels both bits of a pair if both are set in one window.

That protocol is why a second key one cell after the first costs two refused
passes rather than one (see the interaction chain above). It is ported, and
the two-key measurement is a headless check — with a companion check that a
lone key costs exactly one, so the first cannot pass for the wrong reason.

### The renderer

The font is 96 glyphs of 8 bytes at `$77B0`; `$B6C0` writes eight bytes down
one character cell and **no attribute at all**, so a digit takes whatever
colour the panel painter left in that cell. The port does the same.

The layout is decoded from the printer's own addresses rather than chosen:
`$B713 LD DE,$50C9` is player 1's field origin, and `$50C9` decodes to row 22
column 9 — where HEALTH starts. `$B74A SUB 8` moves SCORE eight columns left,
to column 1. `$B7B8`'s `ADD A,E / ADD A,$16` carries the icon low byte out of
row 22's band into row 23: with one key, `$C9 + 1 + $16 = $E0`, which is row
23 column 0. Potions come in as `$10 - (IX+9)` (`$B799`), so they walk
*leftwards* from column 14. Player 2's `$50DA` is the same panel 17 columns
right.

`$B6AE` is why the fields show no leading zeros: the first non-zero digit
latches significance, and a leading zero prints as a **space** — which is how
the old digits are erased. `$B7DD SET 0,C` before the last nibble forces the
final digit, so zero renders as `     0`.

The GAUNTLET logo's colour cycle is ported as display-only state:

```
$A2B4  LD A,($8497) / RRCA x3 / CP $E0 / JR nc     1 frame in 8 is skipped
$A2BE  BIT 3,A / CPL                               the ramp REFLECTS
$A2C3  AND 7 / OR $40 / LD ($A2F5),A               always BRIGHT
```

MEASURED by sampling that self-modified operand **inside** the ISR at `$A2CA`
over 400 video frames: 350 samples, 350 agreements, 0 disagreements, the other
50 being the skip. The machine's own ink sequence is `40 41 42 … 47 46 45 …
40 41 …` — the peak is *not* repeated, so the period is 14 steps of 8 frames,
not the 16 a naive "up then down" reading gives. My first headless check
asserted the naive shape and failed, which is the argument for enumerating a
formula's outputs rather than describing them.

## Generators and spawning — ported, with the entropy labelled

Generators are map values **`$20..$2E` and nothing else**. The guard is

```
$A9E4  LD A,(HL) / SUB $20 / JR c,skip / CP 15 / JR nc,skip
```

so map value `$13` is not one, whatever `NOTES-render.md`'s "10 variants —
animated" suggests. `class = (v-$20) div 3`, `tier = (v-$20) mod 3`, and **the
tier is also the generator's health**, so damaging one makes it spawn weaker
monsters before it dies. Dungeon 1 has twelve, all class 0: one `$20`, six
`$21`, five `$22` — which is why all 63 of its live actors are class 0.

### The sweep runs every pass, all at once, and only inside the viewport

`$853D CALL $A9C2` is unconditional. It walks 16 columns — 17 when
`camx & 3` — by 10 rows — 11 when `camy & 3` — from the top-left visible cell,
and gives **every generator in that block one independent roll per pass**. One
outside it is completely inert, exactly like the frozen off-screen actors.

MEASURED against the real routine in isolation, counting the cells it reaches
`$A9E4` with over 1,118 camera positions: **1,118/1,118**.

```
$AA0B  LD A,($8496) / CP $C0 / JR nc        192 live actors -> no roll at all
$AA12  RRA x3 / AND 15 / NEG / ADD A,(IY+$21)   E = $84A0 - ((count>>3) & 15)
$AA1D  CALL $B575 / CP E / JR nc                spawn attempt iff A < E
$AA26  CALL $AA5E    a RANDOM NEIGHBOUR cell must read exactly 0
$AA30  CALL $A97F    the same 7x7 actor box the player's move uses
$AA35  CALL $AA8C    not within 7 units of a player, in both axes
$AA3A  append (x, y, $7CFE[v-$20] | facing, $04) at the tail ($8494)
```

MEASURED with the count poked, in isolation: the threshold matches
`$84A0 - ((n>>3)&15)` on **33/33** counts, including the **AND-15 wrap** — E
falls 50 → 35 as the population goes 0 → 127 and then **jumps back to 50 at
128** — and `n >= 192` produces no roll at all. `$84A0` itself is
`50 + dungeon/2` (`$B401`/`$B466`), 10/10 over poked dungeon numbers.

The facing is `roll & 7` — the *same* random byte as the threshold test — and
the destination is stepped through `$8418[facing]`, one cursor step per set
bit, so a diagonal facing steps twice and a generator can reach any of its
eight neighbours.

### THE LIMIT, stated plainly

```
$B586  LD A,R / SUB L / RET
```

`$B575` is the refresh register again — the same unreproducible source as the
two coins in the actor update. **Whether any particular roll spawns cannot be
reproduced by any port.** The substitute `rand8()` is used; what is faithful
is the *rate* (accept probability E/256) and every deterministic gate around
it. Simulating the seed alone gives a period of 101 and only 88 distinct low
bytes, so a port that transcribes `$B577..$B583` and thinks it has reproduced
the game has reproduced nothing.

MEASURED on the original over the 62-pass down run: the sweep reaches a
generator on 22 of the 62 passes and spawns **once**, at (32,104), state `$00`,
flags `$04`. The engine, with its substitute entropy, spawns twice over the
same run — and **the point differential is unaffected**, which is the same
insensitivity the actor coin already had. That is measured, not assumed: all
four tables agree on every row at 30, 60, 100 and 160 passes with the sweep
live.

### The cull is what actually bounds the population

`$B0FE` (`$853A`, before the sweep) removes a record when it is 14 cells
across or 12.5 down from the camera centre — but **only if flags bit 2 is
set**, i.e. only generator-spawned ones. The dungeon's own monsters are
permanent. At most five go per pass.

Two details that a paraphrase loses, and both are ported:

* the distance is `$AD47`, which is `$AD37`'s fold into a signed `[-64,63]`
  followed by `NEG` — the **short way round** the 128-unit world. With a plain
  subtraction an actor at x=4 with the camera centre at x=124 reads 120 units
  away instead of 8 and gets culled through the wrap.
* after a cull the loop counter is decremented **twice** and the slot is
  **re-examined**, because the swap-with-last has put a different record
  there. `$B152`'s `JR nz` jumps to the `DJNZ` itself.

### One thing found while porting that the investigations disagreed about

`$A9ED EX AF,AF'` stashes `(v-$20)` for `$AA82` **before** the potion damage
block, so a generator damaged but not destroyed on a potion pass still spawns
a monster at its **pre-damage** tier. Not reachable in this engine (no potion
is pickable and shooting is not ported), so it is noted and not modelled — but
a port that recomputes the value after the damage will get it wrong.

### Still open on generators

* **Classes 1–4 exist only by repainting cells.** Dungeon 1 is all class 0, so
  the class arithmetic is the real Z80 answering a synthetic question. Same
  caveat the actor port already carries.
* **The potion sweep arm** (`$A9EE`/`$A9F4`, damage every generator in the
  viewport at once) is transcribed in the comment and not ported.
* **The shot route** (`$8F79`: +10 score per hit, damage from `$7D65`) is not
  ported — there is no shooting in this engine.
* **The 4-frame pass does not survive a busy screen.** Frames per pass against
  live actor count, measured by two investigations independently: ~4.0 at 60
  actors, ~5.9 at 80–89. That closes the open half of battery Q10 — the answer
  is NO — and it means the real-time spawn rate at a generator cluster is
  ~8.5 Hz, not 12.52. The engine's clock is still a fixed 12.52 Hz.

## Shooting, combat and death — ported

### THE CHARACTER: the port now repairs `$FFFF` for the STATS as well

`$BE53 LD A,($FFFF)` picks the character; `$BEE5` indexes a **four**-entry
table at `$BF19` with it and `$BE5D`/`$BE61` write the pair into `$8433` (the
shot tag) and `$8435` (the attribute byte). MEASURED on a fresh boot with
`$FFFF` poked to each index (`python tools/shotgate.py chars`):

| `$FFFF` | `$8433` | `$8435` | shot | fight | magic | armour |
|---|---|---|---|---|---|---|
| 0 | `$00` | `$8E` | 2 | 3 | 0 | 2 |
| 1 | `$08` | `$D8` | 0 | 2 | 1 | 3 |
| 2 | `$10` | `$32` | 2 | 0 | 3 | 0 |
| 3 ELF | `$18` | `$64` | 0 | 1 | 2 | 1 |
| `$2A` | `$20` | `$20` | 0 | 0 | 2 | 0 |

The last row is the CAPTURED STATE and it is **not a reachable game state**:
`$2A` is the stale `$FFFF` this file already blames for the ROM-bytes sprite
bank, and `$BEE5` walks 42 entries past a four-entry table. `$8433`/`$8435`
are its second and third victims. (This file used to say those two "come out
as `($18,$64)`" — they do not; that is what index 3 *would* give.)

**The port repairs the character as a whole — index 3, the elf.** Repairing
one byte of a table entry and not the other is incoherent, and the tag is not
cosmetic: with `$8433 = $20` a NORTH shot's state byte is *exactly* `$20`,
which is the shot routine's own "exploding" sentinel (`$8C60 CP $20`), so it
is reaped at the top of the next pass and re-fired for ever without moving —
measured, one distinct record over eight passes
(`python tools/shotgate.py collide`) — and `$8DDC` sends every other facing
down the 8-wide OPAQUE blitter at `$DD58 + 32*slot`, where slots 4..7 are all
zero, so S/SW/W/NW punch a blank hole instead of drawing.

**Index 3 is corroborated three ways and proved by none** (nothing that writes
`$FFFF` has been found): the panel prints ELF, the character-3 sprite records
carry attribute `$44` = BRIGHT GREEN, and shot bank 3 (`$D680`) carries the
same `$44` and decodes into eight directional **arrows**. `seed({char:$2A})`
reproduces the capture exactly, and the four movement differentials still run
against the captured machine because none of this touches position.

### CORRECTION: the contact damage in this file was the ARMOUR-0 row

`$AB6F` LDIRs six bytes from `$7D34 + 8*(armour + 2*inventory bit 0)` into
`$8437..$843C` at level start, so *the damage a monster does depends on the
character*. This file's `10 20 30` is row 0. The elf is armour 1 and his row
is `09 18 27 05 07 09`. RE-MEASURED, the same 24 passes of the down run driven
twice on the real Z80 with the two stat bytes (`python tools/shotgate.py
contact`):

```
as captured ($8435=$20, armour 0)  $8437..$843C 10 20 30 05 08 0A  $1996 -> $1985
ELF         ($8435=$64, armour 1)  $8437..$843C 09 18 27 05 07 09  $1996 -> $1986
```

so the pass-24 ghost costs **9**, not 10, and the headless check now asserts 9
with that invocation beside it. `$843A..$843C` are the same thing for classes
1..4 and are now ported too, with `$AF49`'s BIT 3 before BIT 4 — tier 3
aliases tier 1 in both tables, so a tier-3 monster hurts LESS than a tier-2
one. The class-5 drain (`$AF26`: a flat 4 every pass in contact, no countdown
and no armour, into `$5B60 + (IXL>>1)`, self-destructing at `$C8`) is ported
with it, aliasing and all.

Fight power moves with the character as well: the elf's `$64` gives FIGHT 1,
`$A964` indexes `$7D70[6] = 2` and the damage is a flat 1 every odd pass
instead of the capture's alternating 0/1. In the headless generator scenario
that is **1/3/5** refused passes for `$20`/`$21`/`$22` where the capture gives
1/5/9 — both measured, same scenario, `python tools/shotgate.py genmelee`.

### FIRE is bit 4, and holding it FREEZES the player

```
$A57E  LD A,(IX+7) / BIT 4,A / JR z,$A58C
$A585  BIT 4,(IX+14) / JR nz,$A58C
$A58B  SUB A                      ; the whole direction byte
$A58C  AND 15 / RET z             ; and the MOVE ROUTINE RETURNS
```

`(IX+7)` is `$01` up `$02` down `$04` left `$08` right `$10` **FIRE** `$20`
potion; control method 3 is in force and the keys are 1/Q/S/D, **Z** and CAPS.
Bit 4 of `$842E` is the exemption and `$A48D` clears it every pass — and
`$A48D` is `RES 4,(IX+14)`, **not** "write 0 to `$842E`": that byte is the
walk phase and it cycles `40 40 80 80 C0 C0 00 00` while you walk (measured).
So in one-player play the freeze is unconditional — and now that the SHOVE is
ported (`$AB24` is the only writer of bit 4), a player who is being pushed by
his partner CAN fire and keep moving, which is the exemption's whole point. MEASURED, 12 passes each
(`python tools/shotgate.py freeze`):

```
Q alone (12,10)..(12,32)     Z+Q  (12,8) all twelve, $842D still 4
D alone (14,8) ..(36,8)      Z+D  (12,8) all twelve, $842D still 2
```

You turn but you do not move. The same `RET z` is why standing still does not
run the actor scan, and therefore does not melee a monster you are standing
next to — this engine used to run that scan unconditionally.

### A shot is three bytes of the player's own block

`$8430` x, `$8431` y, `$8432` state, `$8433` the character's tag — i.e. the
player block + `$10`, which is why `$8C5D` reaches the player through negative
displacements (`$8C74 BIT 4,(IX-9)` is `$8427`). **There is exactly one shot
per player, ever**, and no cooldown of any kind: the next one spawns on the
first pass the state byte is `$FF` again, so the fire rate is purely the
flight time. Measured in an open arena with the camera **settled first**, fire
held for 120 passes (`python tools/shotgate.py cadence`):

```
N NE SE S SW NW   24 fires   gaps {5: 23}
E W               15 fires   gaps {8: 14}
```

Taking that same measurement *before* the camera converges gives gaps of 1,
because the shot is culled on its first step while the camera is still 30
units away — that measures the camera, not the gun, and one of the four
investigations this port was built from reported exactly that artefact.

The six spawn gates (`$8C74`..`$8C8E`), the 2-units-per-step × 2-steps
movement (3 with SHOT SPEED, `$8434` bit 4), the eight `$7D7C` deltas, the
third map ladder at `$8F36`, the two 5×5 boxes (`$8EEB` actors, `$9009`
players) and the 61×37 viewport cull are all transcribed and all in the
differential below. `$8C90` also means **every shot resets the hurry-up timer
`$84B8`**, which this file listed as counted and never touched.

**One trap that cost the left and up columns of that differential.** `$8F36`
pushes BC, applies the diagonal probe offsets *in place*, and on any non-zero
cell pops the saved pair into **DE** instead of BC. So from a non-zero cell
onwards the register pair is not the record: the impact's `RES 1,B / RES 1,C`,
both collision scans, the cull **and** the draw all use it. A shot stopped at
x=2 with the camera at 2 becomes x=0, and 0−2 folds negative, so the original
culls it in the same pass and frees it to `$FF`; without that the port kept
`$20` and 155 rows disagreed.

`$AD37` **folds and does not ABS**, which is why the window is a rectangle
measured from the camera ORIGIN and one unit above or left of it is already
out of range. ENUMERATED on the real routine over a 140×140 grid: 2,257
offsets, `(x−camx)&$7F` in 0..60 and `(y−camy)&$7F` in 0..36.

### Damage, and the parity two reports got backwards

```
$90E7  LD A,8 / BIT 7,(IX+3) / CALL z,$9115   a MONSTER shot is a flat 8
$90F3  LD E,A / RRA                            carry = bit 0 of the table byte
$90F9  BIT 0,(IY+$12) / JR z                   ... and $8491 ODD
$90FF  LD A,8                                  the bonus is a WHOLE TIER
$9101  ADD A,E / AND $18                       and a hard 3-tier CAP
```

MEASURED because the reports disagreed: with the table byte `$09` (SHOT POWER
1) the tier drops by **one** on pass counters 0 and 2 and by **two** on 1 and
3, so the bonus is +8 and it lands on ODD `$8491`
(`python tools/shotgate.py parity`). The generator arm at `$8F8F` is the
opposite parity — `JR nz` there, so its +1 lands on EVEN passes.

ENUMERATED rather than read: the reachable shot damages are exactly
**{8, 16, 24}**. The `AND $18` is a cap, and a port that writes
`damage = byte + bonus` without it deals four tiers at `$18`.

Scores, all **per hit** and not per kill: 10 for a class 0, 5 for classes 1–4,
1 for a class 5 (plus its potion bounty roll into `$84B3`), 10 for a
generator, 25 for a melee hit, 100 for a pickup. Two of those constants are
encoded differently and it is a real trap: `$8D6F` is `LD E,$10` (already BCD)
and `$8F80` is `LD E,10` = `$0A` (decimal, fixed up by `$913C`'s DAA). Both
are worth ten. A port that treats them alike as raw bytes gets 10 and 16.

### CORRECTION: a class 4 CAN be shot

`$8F2D BIT 3,(HL) / JR z` skips a record whose INVISIBLE bit is set — and the
jump on Z goes to the *found* tail, so it is the bit that is tested and
nothing else. It is a per-record state, not a class property; `$ACA8` is
merely the only place that sets it, on class 4. MEASURED in the running game
with a class 4 pinned in the shot's path: a tier-0 dies to the FIRST shot
(score 000005) and a tier-3 is hit on passes 3 and 5 and then goes invisible
(`flags $C8`) and the next shots fly straight through it. "Class 4 cannot be
shot" — one of the four investigations' headline rules — is wrong; a port that
hard-codes it makes class 4 permanently shot-proof, which the original is not.
The blink's duty cycle is **not** characterised and nobody should quote a rate
for it.

### DEATH, `$93CD` — and there is no life counter

`$8540 CALL $93C2` runs last but two in the main loop. It fires when
`(IX+$14)` bit 7 is clear and the packed-BCD health is **exactly** `0000` —
not "≤ 0": `$93D2 LD A,(IX+2) / OR (IX+3)`, and `$B852` clamps at 0000, so
both bytes have to be zero together. MEASURED (`python tools/shotgate.py
death`, and `python tools/deathgate.py routes` for the three routes in):

```
health $0001  ->  nothing at all in four passes
health $0000  ->  pass 1: $8434=$80 (DEAD)  $842B=$C3  $842E=$80
                          the cell under him becomes $22 (0 keys) / $1F (1) /
                          $32 (2+, plus $5BE8 = 43 80 03 and $84C0 0 -> 1)
                  pass 2: $847D=$80 and THE MAIN LOOP RETURNS at $855C
```

Three things in that sequence are easy to miss and all three are ported:

* `$93F2` snaps the drop to the cell corner (`AND $7C`) — you drop where the
  cell is, not where you are.
* `$93FE CALL $B23B` runs the PLAYER'S OWN 7×7 scan at that position and
  swap-removes every actor in it, looping. **Dying clears the monsters
  standing on you.**
* `$94AE`, at `$8537`, is what actually ends the level: `LD A,($842B) / AND
  (IY-$34) / RLA / JR nc` — when BOTH players' `$842B` bit 7 is set it does
  `SET 7,(IY-2)`, and `$8556 BIT 7,(IY-2) / JR z,$8503 / RET` is the main loop
  testing that bit. Which ending it is comes off `$8434`/`$8454` bit 7 at the
  caller: both dead → `$B3B9` GAME OVER and the high-score entry, otherwise
  the next dungeon loads.

**Nothing resets on death.** The score, the health (which stays at 0000), the
keys and the map all survive; the dropped item stays on the map. There is no
life counter anywhere in this game — health IS the life. In a TWO-player game
a dead player rejoins with FIRE (`$944C BIT 4,(IX+7)`) and `$946E..$9488`
gives him health BCD **2000** and CLEARS his score, keys, potions and
inventory. MEASURED end to end (`python tools/deathgate.py rejoin`): score
`001234` → `000000`, keys 3 → 0, potions 2 → 0, `$8434` `$22` → `$00`, health
`$1999` (2000 less one drain tick), and the `$32` he dropped is still there.

A quirk from that path worth recording: `$9484` is `LD (IX+$10),$FF`, which
writes `$FF` to the shot's **X coordinate**. The shot's state is `(IX+$12)`.
The rejoin therefore does not free the shot it plainly meant to free.

**No longer provisional.** The engine now has 307 dungeons and the whole
post-death chain -- see *Level progression, the exit and the post-death loop*
below. The ranked high-score table ($8826) and its attract display ARE now
ported — `hsInsert` and `hsDrawPage`, gated byte for byte by
`python tools/rankgate.py`. This line used to say they were not.

## Rendering

* Playfield rows 0–19; **rows 20–23 are the HUD**. Measured by comparing the
  real screen against the shadow screen row by row: rows 0–19 agree byte for
  byte apart from the player sprite, rows 20–23 are entirely different. An
  earlier build drew all 24 rows from the shadow buffer and put four rows of
  unrelated data under the playfield — reported in play, then measured.
* Tiles are the **original's own pixels**, sampled from its shadow screen at
  the position the camera equations put them, taking the **modal** block per
  value across the swept views (a first-occurrence sample is contaminated
  wherever an actor happened to stand).
* **Closure test, and an honest reading of it.** Re-rendering the map from the
  extracted tiles and diffing against the original's shadow screen gives
  **95.53%** (264,129 of 276,480 bytes) across 64 swept views, with **17 of the
  19 map values** now having a tile.

  That is *worse* than an earlier 99.89% — and the earlier figure was the
  weaker gate, because it covered only 9 values. The sweep behind it never let
  the camera converge, so most views still showed the opening room. Widening
  the coverage is what lowered the percentage.

  **The remainder is attributed by value**, which is what makes it a gate
  rather than a number:

  | value | agreement | |
  |---|---|---|
  | `$06 $09 $0A $12 $36 $37 $38` | **100%** | clean |
  | `$00` (empty floor) | 95.7% | contested |
  | `$13` | 77.8% | 10 variants — animated |
  | `$01 $05 $11 $15 $1F $20 $21 $22` | 80–97% | contested |

  **Empty floor cannot disagree because of a wrong tile.** So the disagreement
  is not in the tile set: it is the shadow screen carrying live actors, plus
  regions left stale where the camera moved faster than the game redrew. The
  seven values at exactly 100% corroborate that the tiles are sound.

  Two sweep strategies were tried and rejected, both caught by this gate:
  poking the camera as well as the player jumped past the game's incremental
  redraw and scored 93.14%; hopping the player in small steps with a
  convergence filter sampled too few views and scored 93.23%.
* **Camera — corrected, and the correction mattered.** The first rule
  (`cam = max(2, coord − centre)`, applied instantly) matched every sample I
  had, because in normal play the player moves 2 units per pass and so does the
  camera, so a converged tracker and an instant clamp are indistinguishable.
  Poking the player to (100,100) exposed it: the camera went to (124,124), not
  (70,70). Measured properly:
  - it **steps ±2 units per pass** toward its target, it does not jump;
  - it takes the **short way round the wrapping axis** (2 → 0 → 126 → …);
  - the dead-zone offsets are **30 across and 18 down**;
  - it clamps to **[2, 66] across and [2, 90] down**.

  Settled offsets across a 4×4 grid of player positions were 6/30/38 across and
  6/18 down — the 6 and 38 being the two clamps, the 30 and 18 the dead zone.

  **Correction: the down clamp is 90, not 86.** This note said `[2, 86]` and
  that was wrong by 4. `$B5C3 CP $5A` is the instruction, and holding down on
  the original for 120 passes the camera reaches exactly `(2,90)` and holds.
  It is not cosmetic: the camera decides which actors are inside `$A1DA`'s
  window and therefore which ones are updated at all. `$B58C` is now
  transcribed literally in the engine (target from the player's coordinate + 2,
  clamped, then a ±2 step the short way round) rather than applied as an
  instant clamp — the two are indistinguishable while the camera is tracking,
  which is why the old rule matched every sample anyone had.
* `fillRect` only, so the headless pixel diff and draw-call capture stay
  buildable.

## The player sprite — closed

This section previously said the sprite encoding was not closed and that the
draw origin was offset `(-8, 0)`. **Both of those were wrong**, and they were
wrong for the same reason: the numbers were sampled at the wrong moment and
the bytes being decoded were not sprites at all. It is now closed end to end,
and the port's canvas is **pixel-identical to the original's real display**
over the player's 16×16 in all five directions (`tools/playercompare.py`,
0 differing pixels of 256 per direction, picture in
`build/player_vs_original.png`).

### Why he was a speckled blob: a BOOT bug, not a decode bug

The original itself draws the same blob in our captured state. From
`build/image.bin` (pre-relocation):

```
$BE20  LDIR $C000 -> $5F00, $1080 bytes   ; a MASTER TABLE of FOUR character
                                          ; sets, $420 = 32 records of 33 each
$BE53  LD A,($FFFF)                       ; player 1's character index, left
$BE5A  CALL $BEE5                         ;   there by the LOADER's menu
$BE64  LD A,($FFFE) / CALL $BEE5          ; player 2's
$BE74  LD DE,$5F00 / POP HL / LD BC,$0840 / LDIR    ; chosen sets -> $5F00
$BEE5  LD E,A / SUB A / LD HL,$5F00 / LD IX,$BF19 / LD BC,$0420
       CP E / JR z / INC A / ADD HL,BC / INC IX / INC IX / JR    ; HL += n*$420
```

The harness never runs the loader's menu, so `$FFFF`/`$FFFE`/`$FFFD` still hold
a stale `$2A`. `ADD HL,$420` then runs 42 times, `$5F00 + 42*$420 = $10C40`
wraps to **`$0C40`, inside the 48K ROM**, and 1,056 bytes of ROM code become
"the player's sprites". Verified: `mem[$5F00:$6320]` in `build/live_cs.bin` is
a byte-exact copy of ROM `$0C40`. Capturing frames off the screen captured the
original's own garbage — which is exactly what every "speckled figure" was.

`tools/fixchar.py` repairs it from the tape (block C, flag `$82`, offset
`$3C00`, `$1080` bytes = 4 × `$420`). Poking `$FFFF` before boot and letting
the game build the bank itself gives byte-identical results.

The chosen character is **3, the green Elf** — the HUD in the captured state
prints `ELF` in green ink and the record attribute is `$44` = BRIGHT green,
and `$BF19`'s pair for index 3 is `($18,$64)`, which is what `($8433,$8435)`
comes out as. Corroborated, not proved: nothing was found that *writes*
`$FFFF`, so which character the real loader would have chosen is still open.

### The geometry, read from the blitter and then measured

`$9DD2`..`$9E49`, disassembled to its terminating `JP (IX)`:

```
$9DD2  LD A,H / RRA x3 / AND 3 / ADD A,$D8   attribute address.  Note the
                                             AND 3: the base is ALWAYS $D800,
                                             whatever HL points at
$9DDD  LD (HL),C / INC L / LD (HL),C
$9DE0  LD A,L / ADD A,$1F / LD L,A / JP nc / INC H
$9DE8  LD (HL),C / INC L / LD (HL),C         => a 2x2 ATTRIBUTE BLOCK
$9DEC..$9E12  8 x (POP DE + two writes + INC H)     8 pixel rows
$9E13  LD A,H / SUB 7 / LD A,L / ADD A,$20 ...      next character row
$9E22..$9E48  8 x (POP DE + two writes + INC H)     8 more rows
$9E49  JP (IX)
```

**Sixteen `POP DE`, not eight.** `NOTES-render.md` stopped counting at the
`JP nc` at `$9E1B`, which is the mid-routine character-row step, got "8 rows =
16 bytes", and that miscount is the entire origin of "the encoding is not
closed". Both `POP` variants (`$9DEC LD (HL),E / INC L / LD (HL),D` and
`$9DF1 LD (HL),D / DEC L / LD (HL),E`) put `E` in the **left** column and `D`
in the right, so the byte order is plain.

The caller states the record layout outright:

```
$A23E  LD C,(HL)     ; record+0 is the ATTRIBUTE
$A23F  INC HL
$A241  LD SP,HL      ; record+1 is where the 32 bitmap bytes start
$A243  JP $9DD2
```

> **ONE RECORD = 33 BYTES (`$21`)**: `+0` attribute, `+1..+32` = 16 pixel rows
> × 2 bytes, row-major, top row first, LEFT byte first, MSB first.
> 16 × 16 pixels. The blit is **OPAQUE** — `LD (HL),E` replaces the
> background, there is no mask, no OR and not one shift instruction in the
> whole routine. The single attribute byte is written to all four cells of a
> 2×2 character-cell block.

The old "uniform `$42` (66-byte) stride" was **two records**. Every source
pointer anyone had sampled happened to land on an even-numbered record, which
made 66 look like the unit.

Records are reached through a 255-entry table of 16-bit pointers at
`$7B00..$7CFF`, indexed `(id-1)*2` (`$A231 DEC A / ADD A,A / LD L,A /
LD H,$7B`). All 248 non-zero entries lie on a 33-byte grid. `tools/
playersprite.py` walks that table rather than assuming the bank is contiguous.

### The frames, and how one is chosen

```
$A47B  LD A,(IX+7) / AND 15 / JR z,$A48D    ; direction bits; ZERO KEEPS the
$A480  LD L,A / LD H,0 / LD DE,$7D0C        ; PERSISTED (IX+13) -- standing
$A487  ADD HL,DE / LD A,(HL) / LD (IX+13),A ; still does not reset to slot 0
$A496  LD A,(IX+13)
$A49F  BIT 6,(IX+14) / JR z / ADD A,8
$A4A7  BIT 7,(IX+14) / JR z / ADD A,8
$A4AF  ADD A,(IX+15) / JP $A1DA

    sprite id = (IX+15) + (IX+13) + 8*phase
    (IX+15) = 208 for player 1 ($8420), 232 for player 2 ($8440)
```

`$7D0C..$7D1B` = `90 00 04 00 06 07 05 06 02 01 03 02 00 00 04 00`, indexed by
`(IX+7) & 15` with the measured key bits `1=up 2=down 4=left 8=right`, giving
eight compass **slots**: `0 N, 1 NE, 2 E, 3 SE, 4 S, 5 SW, 6 W, 7 NW`. It
solves cleanly — `9 = up|right -> NE`, `10 = down|right -> SE`, and
conflicting pairs cancel (`7 = up|down|left -> W`). Entry 0 is never read
because of the `JR z` above.

So a character set is **8 slots × 3 phases = 24 walk records**, plus 8
non-walk records (24 a distinct standing figure, 25 a dashed "materialise"
figure, 26–31 the player dissolving into the EXIT sign). 32 records × 33 =
`$420`, exactly one set. See `build/player_frames.png`.

The phase counter, `$A5D8`:

```
$A5D8  LD A,E / OR A / JR z,$A5F0        ; <-- E, NOT (IX+7)
$A5DC  BIT 0,(IY+$12) / JR z,$A5F0       ; IY=$847F, so $8491 = the PASS
                                         ; COUNTER: odd passes only
$A5E2  BIT 4,(IX+14) / JR nz,$A5F0       ; bit 4 is $AB24's, the SHOVE: a
                                         ; player being pushed does not walk.
                                         ; (Ported. This used to read "NOT
                                         ; PORTED: what sets bit 4 was not
                                         ; read" -- one opcode scan for
                                         ; DD CB 0E E6 finds the single site.)
$A5E8  LD A,(IX+14) / ADD A,$40 / LD (IX+14),A
```

decoded by `$A49F`/`$A4A7` as phase **0, 1, 0, 2** as the counter runs
`$00 $40 $80 $C0` — each phase held for two passes.

**The `E` gate is the subtle part, and a trace found it, not a reading.**
Holding *up* into the wall at y=4, the drawn record froze on the walk frame
instead of cycling. `E` starts the pass as the direction bits (`$A58F LD E,A`)
and **each direction handler clears its own bit on the undo path**:

```
$A85A  RES 3,E   (right)      $A888  RES 2,E   (left)
$A8B6  RES 1,E   (down)       $A8E4  RES 0,E   (up)
```

so `E` ends as the mask of directions that **actually moved**. The walk cycle
therefore stops dead against a wall while the *pose* still turns to face the
way you are pushing. Gating on the raw input instead animates a player who is
not moving; the first version of this port did exactly that and the pixel
comparison caught it. Note also that `E` is tested at `$A5D8` **before** the
actor scan at `$A5F0`, so a move rejected by the scan still animates.

### The draw origin: there is no `-8`

`$B557` is the whole coordinate transform, and it contains no fudge at all:

```
LD A,C / SUB (IY+12) / AND $7E / RRA / LD L,A     col = ((x - cam_x) & $7E)>>1
LD A,B / SUB (IY+13) / AND $7E / RRA / LD H,A     row = ((y - cam_y) & $7E)>>1
AND 7 / RRCA x3 / ADD A,L / LD L,A ; LD A,H / AND $18 / ADD A,$C0 / LD H,A
```

`screen_x = col*8`, `screen_y = row*8`. Sampling the player's coordinate **at
the instant PC reaches `$9DD2`** rather than at the end of the pass gives
delta `(0, 0)` on **120 of 120 draws** across five directions.

Where the phantom `-8` came from is now demonstrable rather than argued. One
harness "pass" is four video frames, and that window does not begin at the
game's main-loop top, so at the end of it the coordinate in RAM is one 2-unit
step ahead of the position that pass actually drew. `tools/playercompare.py`
prints it: holding right, the original blitted to `(96,24)` while its RAM said
`(104,24)`, and the port — drawing at its own `(104,24)` — is byte-identical
to the original's block at `(96,24)`. Sliding the comparison window over
−16/−8/0/+8/+16 matches at exactly one offset, −8, *for that sampling method*.
The same lag lands on **y** when holding down, which a constant −8 on x cannot
explain, and it vanishes once the camera starts tracking, because then
`coord − cam` is constant. Manual F2 cut the other way here: the frozen
`(-8, 0)` headless check was protecting an artefact.

The `AND $7E` is a real quantisation — the sprite is placed on whole character
cells, never sub-cell — but it is not an offset.

### What this is worth as a gate

| check | result |
|---|---|
| blit destination == `((x-cam)&$7E)>>1*8` | 120/120 draws |
| shadow-screen 16×16 == decoded record | 120/120 draws |
| 2×2 attribute cells == record byte 0 | 120/120 draws |
| `(IX+15)+(IX+13)+8*phase` == the record the game chose | 120/120 draws |
| port's canvas == the ORIGINAL's real display, per direction | 0/256 px differ |
| walk cycle vs the original's records, 12 passes right | exact |
| walk cycle frozen against a wall, 12 passes up | exact |

`python tools/playersprite.py` runs the first four and writes
`build/player_frames.json` + `build/player_frames.png`;
`python tools/playercompare.py` runs the fifth and writes
`build/player_vs_original.png`; the last two are headless checks.

### Still open on the sprite

* **Which character the real loader chooses.** `$FFFF`/`$FFFE`/`$FFFD` are
  read at `$BE53`/`$BE64`/`$BF21` but nothing was found that *writes* them —
  presumably the BASIC loader POKEs them, or a character-select screen we
  never drive into. Elf is corroborated by the HUD text and the ink, not
  proved -- see *Shooting, combat and death* above, where the same question
  decides the shot tag, the armour row and the fight power as well, and where
  the ELF is corroborated a third time by shot bank 3's own `$44` attribute.
  `$FFFD` patches a byte to `$C9` (RET) at `$BF21`, and this note used to add
  "almost certainly the 1-player/2-player switch". **It is not.** It is the
  48K-beeper / 128K-AY SOUND select, auto-detected at boot by the `$7FFD`
  paging probe and read a second time at runtime by `$9D0A`; there is no
  player-count byte anywhere in the image. See *Two players*.
* **Records 24–31** of a character set are not used by the player draw path
  (only slots 0–7 × phases 0–2 = records 0–23 were ever drawn in 120 blits).
  Their role is read off the artwork, not measured.
* **Bit 4 of `(IX+14)`** gates the animation at `$A5E2` and bit 2 skips the
  draw entirely at `$A491`. CLOSED for bit 4: it is set only at `$AB24`, the
  two-player SHOVE, cleared only at `$A48D`, and read at `$A475` (the pose
  freeze), `$A585` (the fire-freeze exemption) and `$A5E2` (the walk-phase
  tick) — so a shoved player SLIDES, facing and walk cycle frozen. All three
  are ported. Bit 2 is still unread. Neither fired in any
  logged pass.
* **The clipped blitters.** `$9E4B` (8×16, source starts at record+2 and
  writes only the RIGHT byte of each row into screen column 0) was observed
  and verified byte-for-byte at the left edge; `$9EA0` (16×8) and `$9ED7`
  (8×8) were only identified by `POP` count. A right-edge variant was never
  seen. The port does not clip — the player never reaches a viewport edge in
  the current level.
* **`$A31A`** (the global animation dispatcher, `$8491` RRA / AND 3, DE in
  `{0,$21,$42}` = 0/1/2 records) writes `$7B5C`/`$7B5E`. It is **not** the
  player's frame selector, and treating it as one is a dead end. It is not the
  monsters' frame selector either — those ids come from `$ACF5` — it patches
  the pointers for map sprite ids `$2F` and `$30` (the trap and the teleport
  pad), the only two animated tiles in the game.
* Player 2 is not drawn at all. Monsters now are — see *Actors*.

## Level progression, the exit and the post-death loop — ported

Tools: `python tools/levelgate.py` writes the closure file; `python
tools/overgate.py` and `python tools/deathgate.py` drive the real Z80 through
the game-over chain. None of them loads the engine.

### The exit, and a live bug this file had

```
$A681  LD (IX),C / LD (IX+1),B        the commit, uniquely here
$A687  SET 6,(IX+11)                  EXITING (also stops the drain)
$A68B  (IX+14)=0 / (IX+13)=0 / (IX+$16)=$18
$A697  BIT 6,(IY-1) / JR nz,$A6AA     A TREASURE ROOM SKIPS BOTH ARMS
$A69D  OR A / JR z,$A6A7
$A6A7  DD 34 0C   INC (IX+12)         A PLAIN BINARY INCREMENT
$A6A0  ADD A,A / ADD A,A              else (IX+12) = 4*A
```

**`$A6A7` is `DD 34 0C` and there is no `DAA` anywhere near it.** The engine
used to do `daaAdd(level,1,0)`. MEASURED by calling `$A681` in isolation with
`(IX+12)` poked: `$01→$02 $07→$08 $08→$09 $09→$0A $0F→$10 $19→$1A $63→$64
$99→$9A $FF→$00`. BCD would give `$09 → $10` and steal six dungeons. It was
latent while the engine had one level; it is not latent now, and it is a
headless check.

Tiles `$37`/`$38` are **warps**, to dungeons 4 and 8 (`A=1/2/3 → 4/8/$0C`).
In a **treasure room** neither arm runs: MEASURED with `$847E` bit 6 set,
`(IX+12)` comes back `$09 → $09` and `$63 → $63`, and `$94BD` does the same
for `$8403`, so the level number does not advance through one. `$94C3`
otherwise takes the unsigned **max** of the two players' `(IX+12)`.

The way out of a treasure room is its own clock: `$8527 BIT 6,(IY-1) / CALL
nz,$8ADA` runs once per pass, `$8AED` counts a divider of 12 passes down and
takes one BCD point off `$84B6` (seeded `$20..$30` by `$915E`), and at 00
`$8B1E/$8B22` set `$847D` bits 3 and 7 — the level is over. 384–576 passes,
30–46 seconds.

**What survives a level change:** the score, the health, the keys, the
potions, the inventory and the character. `$B3D0` writes none of them. What
does not: the map, the actors, the shot, the door animator, the hoard, the
drain accumulators, the pending interaction, and (`$B385`/`$B389`) the video
frame counter `$8497` and the drain phase `$849F`. The **pass** counter
`$8491` is not reset.

### Leaving the main loop

`$8556 BIT 7,(IY-2)` is the only exit, and `$847D` bit 7 is SET from exactly
two places in the image (enumerated over its 22 `(IY-2)` bit sites): `$94D1`
and `$8B22`. `$847D` bit 6, tested at `$B394` and worth `JP $0000`, is set
**nowhere** — that arm is dead code. Then:

```
$B39B  INC (IY+$12) / CALL $B6DA / loop while ($842B|$844B) & $3F   ~4 iters
$B3AB  ($8434 AND $8454) bit 7 -> $B3B9 GAME OVER, else JR $B381 NEXT DUNGEON
```

so a level ended by the exit goes straight into the next dungeon and one ended
by death goes to the name entry. MEASURED: the death pass, then the pass on
which `$94AE` sets the bit and the loop returns at `$855C` — two passes,
because `$8537 CALL $94AE` runs *before* `$8540 CALL $93C2`.

### `$B3B9` — the world stops, and the clock changes

**The loop is UNPACED.** MEASURED on the real Z80: 2,726 iterations in exactly
100 video frames = **27.26 per frame**, no `HALT` at all, and **`$8491` did
not move once** (72 → 72) while `$8497` advanced 100. So nothing in this loop
may be driven per pass. The engine ticks it once per **video frame**: within
one frame the input gate below is open on at most one iteration, so one tick
and 27 are indistinguishable except in sub-frame commit latency.

`$9354`, which every profile of a dead machine shows as the hot PC, is not a
loop of its own — it is the middle of `$930C`, the three-letter **high-score
name entry**. Five things a port has to get right:

1. **The repeat gate is 8 VIDEO FRAMES and it does not mask SHIFT.**
   `$930D LD A,($8497) / SUB (IX+$1A) / CP 8 / JR nc` then `$9317 LD A,(IX+7)
   / AND $20 / LD (IX+7),A` — the four direction bits are discarded, bit 5
   survives. So a held SHIFT commits instantly and a held UP steps at 6.25 Hz.
   MEASURED holding UP: gaps of 4.72, 8.00, 8.00, 7.97, 8.00 … video frames.
   The first one is short because `$92C1` set the stamp one pass earlier,
   from inside the last live pass (`$8509 CALL $A38A → $9432`); the engine
   backdates its stamp by one pass and reproduces it.
2. **The alphabet is 27 slots, not 26.** `$937B INC A / CP $5B → $40`,
   `$9388 DEC A / CP $3F → $5A`, `$9395 CP $40 → $20`. **SPACE sits between Z
   and A.**
3. **The cursor is an attribute swap of the cell one row BELOW.** `$9350`
   reads row 21 (static panel art), `$9358` swaps ink and paper and ORs `$40`,
   `$9369` writes it at row 20. Row 21 is `$44` all the way across so the
   swap is `$60` every time: a **stable inverse-video block**, not a flash.
   Toggling the attribute in place gives a 1.4 kHz flicker.
4. **Committing ends the loop on the same iteration** (`$93A3 BIT 5 / $93A8
   (IX+14)=0 / JP $948C`, and `$B3BC`'s `AND $FE` then fails), so in a
   one-player game the rejoin at `$9440` is unreachable. MEASURED: FIRE held
   for 400 frames does nothing at all. **An engine that polls FIRE after the
   commit invents a continue the original does not have.**
5. **The restart is a brand-new game at dungeon 1 with the score zeroed**
   (`$B3C6 → $B35A`), and it does **not** touch the tape (see the dungeons
   section).

There is **no life counter**: the full 64K diff over a death pass changes 17
bytes and not one of them is a counter a second death would decrement. Health
IS the life. What the game has instead is a JOIN-IN model — `$9440` gives a
dead player back BCD 2000 while **zeroing his score, keys, potions and
inventory**, which only reaches a second player.

**PORTED** (this heading used to read "NOT PORTED, deliberately", and reading
it instead of grepping once cost a whole duplicate renderer): the four 60-byte
ranked tables at `$8826`, their
insertion sort `$86ED` and the four-page attract display `$8767` (one page per
**256** video frames — `$B487` spins until `$8497` wraps, so the period is
exactly 256, not the 251.8 an earlier write-up gave, which is 256 minus the
page draw); and the REWIND TAPE prompt `$B48F`, a cold-boot-only path. The
committed name is kept and shown.

**PROVISIONAL:** the game-over loop runs one iteration per video frame rather
than 27; player 2 does not exist, so neither the rejoin nor his own name entry
(`$5097`, `(IY+$4A)`, `$84C9`) is exercised. And `$9689`'s refusal arm (`no
free cell → stay dead, sound 13`) is still unreachable, because `$945A`
short-circuits it on dungeon 1.

## Two players — ported

Tools: `python tools/p2gate.py all` prints every number in this section and
runs the two-player differential; it drives the real Z80 and never loads the
engine. `tools/playersprite.py --char 3 --char2 1` gates both sprite banks
against the original. Pictures: `build/twoplayer.png` (both players and both
panels), `build/player2_frames.png` (player 2's 24 walk records).

### There is no one-player/two-player switch. There never was.

The game always carries **two** player blocks and both ship marked *not in the
game*:

```
$8420: 00 00 00 00 00 00 00 00 00 00 00 C0 00 00 00 D0 00 00 00 00 80 ...
$8440: 00 00 00 00 00 00 00 00 00 00 00 C0 00 00 00 E8 00 00 00 08 80 ...
        ^x ^y  ^health  ^score          ^+$0B      ^+$0F        ^+$14
```

read off tape side 1's block `$82` at offsets `$20`/`$40`, and
`tools/extract.py` now carries the second one into the assets as
`player.block2` so that "he starts outside the game" is the **tape's**
statement and not this file's. `$9451 RES 7,(IX+$14)` is the only instruction
in the whole image that puts a player *in* one, and its only gate is
`$944C BIT 4,(IX+7)` — FIRE.

So one player or two is **emergent**: whoever presses FIRE is in, and the
other can join at any moment, through exactly the code that revives a dead
player. `$9432 → $9440` runs once per player per pass, in the title/attract
loop (`$B47B`) and in the main loop (`$8509 CALL $A38A`).

**CORRECTION, and it is one this file made:** `$BF21 READS $FFFD and patches a
byte to $C9 - suspected to be the one-player/two-player switch` is **wrong**.
`$FFFD` is the **48K-beeper / 128K-AY sound select**, auto-detected at boot by
the `$7FFD` paging probe block A copies to `$61A8`, and it is read a second
time at runtime by `$9D0A` to choose between `$B8B0`/`$B8B5` and the AY driver
`$BA2B`. Nothing in the image counts players. `tools/fixchar.py`'s docstring
carried the same error and now carries the correction.

### The join, measured

`python tools/p2gate.py join` — hold M for **one pass** from
`build/state_charsel.pkl`, player 1 at (12,8):

```
+$00 $00 -> $10   +$01 $00 -> $08     position (16,8), beside player 1
+$02 $00 -> $20                       health BCD 2000
+$07 $00 -> $10   the FIRE bit, still held
+$0B $C0 -> $00   $970D AND $3F -- in play, and participating
+$0E $00 -> $01   MATERIALISING
+$10 $00 -> $FF   $9484 -- see below
+$14 $80 -> $00   IN THE GAME
+$17..$1C  10 20 30 05 08 0A          $AB6F's contact-damage row
```

Four things a port has to get right and would not guess:

* `$9484 LD (IX+$10),$FF` writes the shot's **X**, not its state at `(IX+$12)`.
  The reset does not free the shot it meant to free. Reproduced, bug and all.
* `$9689` places him from **the other player's** cell (`$96B4`, `AND $7C`),
  falling back to `($8492)` — the level's own start — only if that player is
  at (0,0). Measured: player 1 at (12,8) puts him at (16,8); at (32,8) puts
  him at (36,8); at (40,40) puts him at (44,40). **It is not a constant.**
* The ring search is real, and its priority is **E, N, S, W**. `$96ED AND $55`
  keeps only the four cardinals of `$B2B6`'s eight probes and `$96F3 AND 4`
  prefers EAST before `$B315` takes the lowest set bit. Measured by walling
  them one at a time (`p2gate.py place`): nothing walled → (44,40); E → (40,36);
  E,N → (40,44); E,N,S → (36,40); **all four → (0,0), a FAILURE**.
* The failure arm is reachable and it matters: `$945A LD A,($8403) / DEC A /
  JR z` lets him join anyway **on dungeon 1** and refuses him anywhere else
  (`$9460` sets bit 7 back, zeroes `(IX+14)` and plays sound 13). Both
  measured.

### The materialise is SIX frames, and it happens at every level start too

`$9694` points his first six sprite ids at `$F45E + n*$21` (six shared
records, attribute `$06`, a growing swirl) and `$96AB` sets `(IX+14)` bit 0;
`$A4F9` then short-circuits the **whole** move routine while it is set.
Watching `$7CCE` through a join:

```
+0..+5   $F45E   (IX+13) = 00 01 02 03 04 05, (IX+14) bit 0 SET
+6       $6320   (IX+13) = 4 (SOUTH),         bit 0 CLEAR
```

**SIX passes, not five** — one report said five and its own text said six.
And it is not only a join: `$B458/$B463` call `$9689` for both players at
every level start, so **every level begins with six passes in which nobody can
move**. Measured on the real Z80 by walking into a planted `$36`: the level
reload leaves `(IX+13) = $FF` and `(IX+14) = 1`, the player is frozen for six
passes and moves on the seventh. This engine did not model it before.

### A correction that only two players could expose: the POSE is not part of the move

`$A47B` — `LD A,(IX+7) / AND 15 / JR z / LD (IX+13),$7D0C[bits]` — lives in
**`$A43B`, the draw dispatch at `$8521`**, not in `$A4DD`. Only the WALK
PHASE (`$A5D8`) is in the move. With one player the two are
indistinguishable: both run once a pass off the same `(IX+7)` with nothing
between them that reads `(IX+13)`. A **materialising** player shows the
difference — his move is short-circuited and his pose skipped (`$A451`), and
on the pass the materialise ENDS the move clears the bit and the draw then
sets the pose, so `(IX+13)` comes out of that pass as the held direction and
not as the 4 `$A4C0` wrote. Measured at a level start with D held:
`(IX+13)` reads `05`, then `02`, then `02` with the move. The engine's
`animate()` has been split accordingly.

### The camera is a TWO-STAGE tracker and it follows the MIDPOINT

Nothing in this file had named `$A3E6`. It writes a **target** at
`$848D/$848E` and `$850C CALL $B58C` then steps the camera two units toward
it; `$851B` calls it a second time, idempotently (both writes agree on 20/20
passes).

```
$A3E6  HL = ($8420); bit 7 of $842B -> use ($8440); both out -> RET, NO WRITE
$A3F7  INC H,INC H,INC L,INC L            both +2, the sprite centre
$A3FD  player 2 out -> he IS the target
$A403  DE = ($8440) + (2,2) ; ADD HL,DE ; SRL H ; SRL L
$A410  RES 0,L / RES 0,H                  round DOWN to even
$A414  |own - mid| >= $21  ->  mid ^= $40 the wrap fix, per axis
$A437  ($848D) = HL
```

Three things it is easy to get wrong, and all three are in the port:

* the add is **16-bit**, so an odd x-sum carries 1 into the y sum. Inert while
  both y are even, which they always are in play — but it is not two 8-bit
  averages.
* `RES 0` rounds the midpoint **down to even**. It is not the exact midpoint;
  on half of all even pairs the true midpoint is odd and the target sits one
  unit low.
* the `XOR $40` wrap fix is only the short way round **inside the leash**. At
  a separation of 66..126 it produces the antipode. Unreachable in play, but
  it is not a midpoint formula.

`python tools/p2gate.py camera` enumerates the real routine against an
independent transcription: **8,192/8,192** with both players present (a full
even sweep of x-pairs at one y and of y-pairs at one x), **384/384** with
player 2 absent, (40,60) → (42,62) with player 1 absent, and with both absent
`$848D/$848E` are **not written at all**.

### `$A924`/`$A944` are the LEASH, not a stray-distance test

**CORRECTION.** This file said they "turn out to be a stray-distance test
which can never fire for the player himself". They are the two-player
**separation limit**, they fire constantly in a two-player game, and the
reason they are inert with one player is `$A926`'s `AND $20` clearing carry
before the absent-partner `RET nz` — not the step size.

```
$A924  LD A,IXL / AND $20            -> the OTHER player's coordinate
$A92A  BIT 7,(IY-$54) / RET nz       partner not in play: no gate, carry 0
$A92F  LD A,(other.x) / SUB C / CALL $AD47 / CP $3D / CCF / RET
$A944  the same on y with $25
```

All four direction handlers call one of them on the STEPPED candidate,
**before** the `BIT 1` gate and before the map, and a refusal takes the same
undo path a wall does (`$A852`, which also throws away a pending interaction).
Enumerated on the real routine, both IX values, all 128 candidates with the
partner at 0 (`p2gate.py leash`):

| | allowed | REFUSED |
|---|---|---|
| `$A924` across | 0..60 and 68..127 | **61..67** |
| `$A944` down | 0..36 and 92..127 | **37..91** |

i.e. refused exactly when the **short-way** distance is ≥ `$3D` (61) across or
≥ `$25` (37) down. With the camera at midpoint−30/−18 that is screen x 0 and
240 and screen y 0 and 144: **the leash is exactly one playfield**. Driven in
play, player 1 walking down stops at a separation of 36 on empty floor and is
released the moment player 2 walks (`p2gate.py table leash`).

### `$AAC4` is a fourth move gate, and it decides who moves first

```
$AAC4  LD A,IXL / AND $20 -> the OTHER block
$AACA / $AAD5  BIT 6 of his +$0B / RET nz    exiting or dead -> NO GATE
$AADE  A = E+3-C & $7F / CP 7 / RET nc
$AAE7  A = D+3-B & $7F / CP 7 / RET nc
$AAF0  SET 3,(IX+14) / RET                   carry SET, move refused
```

Enumerated over the whole offset neighbourhood, both IX values: **49 hits,
dx and dy each in [−3..3], the full product**, and the carry is set on exactly
those 49. The other player's `+$0B` bit 6 disables it entirely, returning
carry CLEAR whether it was set or clear on entry.

Bit 3 of `(IX+$0E)` is what `$A39B` reads **next** pass:

```
$A39B  BIT 3,($842E) / JR nz,$A3BE
$A3A1  BIT 3,($844E) / CALL nz,$AB06 ; $A3A8 PLAYER 1 ; $A3B2 player 2
$A3BE  CALL $AAF5 ; $A3C1 PLAYER 2 FIRST ; $A3CB BIT 3 ; $A3CF CALL $AB06
       (UNCONDITIONAL, where its mirror $A3A5 is CALL nz -- an original bug:
       the dead BIT computes a condition the CALL then ignores) ; $A3D2 p1
```

so a pair that touched last pass runs in the **other order** this pass, which
is what lets the pushed player step out of the way before the pusher's own
gate is evaluated. Ported, including the asymmetric `CALL`.

### The shove, `$AB15`, and why a pair walks at half speed

```
$AB15  BIT 0,(IY+$12) / RET nz     EVEN pass counter only
$AB1A  the PUSHER must hold a direction (AND 15)
$AB1E  the PUSHED must hold NONE
$AB24  SET 4,(IX+14)
$AB28/$AB3A/$AB4C/$AB5E  if the pushed player is EXACTLY 4 units that way,
                         SET the matching bit in HIS OWN key byte
```

Each arm tests **only its own axis** — the perpendicular coordinate is never
consulted — and the pushed player walks himself; nothing moves him directly.
`(IX+14)` bit 4 is set only here and cleared only at `$A48D`, and its three
readers are `$A475` (the pose freeze), `$A585` (the fire-freeze exemption) and
`$A5E2` (the walk-phase tick): **a pushed player slides, facing frozen**. All
three are ported.

Measured, and reproduced row for row by the differential: player 1 walking
into player 2 makes the pair advance 2 units every **two** passes — half
speed — and two players walking head-on **deadlock**, because a player holding
a direction cannot be shoved.

### Friendly fire is per-DUNGEON data

```
$97CB  BIT 0,(IX+1) / SET 5,($847E)   "SHOTS NOW HURT"   $7F0C
$97D5  BIT 1,(IX+1) / SET 4,($847E)   "SHOTS NOW STUN"   $7EFD
```

```
$905E  BIT 4 -> SET 6,(IX+$14) / (IX+$1D) = $1E     STUN, 30 passes
$906E  BIT 5 -> LD D,5                              HURT, 5 BCD
```

| `$847E` | health | `+$14` | `+$1D` |
|---|---|---|---|
| neither | 2000 → 1998 (drain only) | 00 | 00 |
| bit 4 STUN | 2000 → 1998 (drain only) | **$40** | **$1E** |
| bit 5 HURT | 2000 → **1973** | 00 | 00 |

A partner **blocks and absorbs** your shot in every mode. Counted over all 307

### The frame clock, and a correction the two-player table forced

`$8497` is the ISR's video-frame counter and the drain at `$852E` reads it
part-way through the pass, not at the top. MEASURED by hooking both `$8503`
and `$B6DA` over 80 passes: `($8497 at $B6DA) − ($8497 at $8503)` is **1 on
79 of 79 samples** — a pass is four frames but only one frame boundary has
been crossed by the time the drain runs, the rest of the wait being the HALTs
around it. The engine now advances one frame there and the remaining three at
the bottom. Getting this wrong puts the drain tick one whole pass early,
which is invisible in a one-player position table and immediately visible in
a two-player one that prints health.

## Sound — BOTH drivers ported; the 48K BEEPER is the shipped one

`python tools/beepgate.py all` → **0 mismatching over 1,840** comparisons,
the SHIPPED branch, compared as a **speaker-edge** differential.
`python tools/soundgate.py all` → **0 mismatching ticks over 2,152**
(register, value) comparisons — the AY branch, now inert but kept and still
gated, because it is verified work and the game's own probe flag is what
selects between them.

**WHICH ONE RUNS IS NOT THIS PORT'S DECISION.** `SOUND_MODE` mirrors RAM
`$FFFD`, the byte `$C242` writes and `$BF21` reads. The tape is a 48K tape
and the owner's machine answers 0, so the beeper is the default and the one
every gate below is measured on.

### The game has TWO drivers and a boot-time probe picks one

There is no menu option and no runtime toggle. Block A copies a 100-byte
routine from `$CE50` to `$61A8` (`$C22D`) and calls it (`$C238`); it saves
`($C000)`, writes 0 there, `OUT ($7FFD),$D1` to page bank 1 in, writes `$D1`,
pages bank 0 back and reads `($C000)`. `$C23B CP $D1 / LD A,1 / JR nz /
SUB A / $C242 LD ($FFFD),A`. Reading `$D1` back means nothing paged, i.e. a
48K, and stores **0**; a 128K stores **1**. The probe relocates itself to
`$61A8` first because `$4000..$7FFF` is the one window a 128K never pages —
which is itself the evidence that it is a paging probe and not an AY probe.

`$BEB9 CALL $BF21` then rewrites nine bytes:

```
($FFFD) != 0   $B8B5 := C9   $B8CC := C9                    kill the BEEPER
($FFFD) == 0   $BADB $BA01 $BBA7 $BBBC := C9                kill the whole AY
               $BA2B := C3 2B B9  (JP $B92B)                 repoint the entry
```

**MEASURED, not read.** I booted the real game from `$8400` three times with
`($FFFD)` forced to `$00`, `$01` and the captured `$2A`, ran to `$BEBC` (the
instruction after `CALL $BF21`, about 3,880 instructions in) and diffed all of
`$4000..$FFFF`:

```
$00 vs $01 : 10 bytes differ
  $B8B5 21/C9   $B8CC ED/C9   $BA01 C9/3E   $BA2B C3/C5   $BA2C 2B/D5
  $BA2D B9/E5   $BADB C9/D5   $BBA7 C9/3E   $BBBC C9/3E   + $FFFD itself
$2A vs $01 : 1 byte differs -- only $FFFD.  The stale byte IS the 128K boot.
```

Independently, `build/blkC.bin` (the tape bytes) and `build/live_cs.bin` (the
live dump) differ over the whole `$B8B0..$BDB0` code region at exactly two
addresses — `$B8B5` and `$B8CC` — which is precisely the 128K arm and nothing
else.

**So every sound measurement this project made before now was on the AY branch
BY ACCIDENT**: the harness never runs block A, `$FFFD` holds the loader stub's
padding byte `$2A` (as do `$FFFE` and `$FFFF`), and `$2A` is non-zero. On the
tape owner's 48K the AY is never written at all and the beeper is the only
output. `NOTES-battery.md` Q17 is restated there.

**RAM `$FFFD` is not the AY register-select PORT of the same number.** The
port is written at `$BB9D` (`LD BC,$FFFD / OUT (C),A`); the RAM byte is read
at `$BF21` and at `$9D0A`. An earlier note in `web/template.html` guessed
`$BF21` was a one-player/two-player switch; it is not, and nothing in the
image counts players.

**WHICH PATH THIS PORT SHIPS: the AY.** It is a register dump, it is what the
whole measurement rig here is aimed at, and it is what a 128K owner hears. The
beeper path is *not* ported and is described below with its measured numbers.

### The AY driver, mirrored

| original | engine |
|---|---|
| `$BA2B` allocate-and-start, 23 call sites, ids 0..`$11` | `SfxDriver.trigger` |
| `$BADB` one video frame of the driver, from the ISR at `$A2A5` | `SfxDriver.tick` |
| `$BB35` one channel, one frame — the row decode | `SfxDriver.step` |
| `$BB21`/`$BB27` the R7 mixer, assembled and written last | inside `tick` |
| `$BB96` the single register writer (`$BB9D`/`$BBA2`, the only two OUTs) | `SfxDriver.w`, which logs `(frame, register, value)` |
| `$BA01` silence-everything | `SfxDriver.silence` |
| `$73DA` the 18-entry table of RELATIVE offsets | `build/sfx_data.json`, `tools/sfxdata.py` |

**The effect data.** `$73DA + 2*id` holds an OFFSET from `$73DA` (`$BABE
LD BC,$73DA / ADD HL,BC`, twice), so the whole thing is position independent.
A stream is two-byte rows to a `$00` terminator, **one row per 50 Hz video
frame**:

```
b0 == 0        END: write volume 0 to R(8+ch), release the channel
b0 bits 7..4   volume            -> R(8+ch)
b0 bits 3..0   n; R6 = 2*n       ($BB62 ADD A,A) and noise ENABLED for this
                                 channel iff n != 0 ($BB64 JR z)
b1             p; TP = ((p+1) & $FF) * 4   ->  R(2ch), R(2ch+1)
```

**The eight-bit `INC A` at `$BB71` is load-bearing** — the widening into HL
happens after it, so tone byte `$FF` gives period **0**, not 1024. That is
reachable, not theoretical: id `$11` uses `$FF` in all 8 of its rows and id
`$0F` in 6 of its 85. A decoder that writes `(p+1)*4` mismatches on exactly
those 14 frames.

The 18 streams **tile `$73FE..$77AF` with zero gaps and zero overlaps**, and
the lowest starts immediately after the table — which fixes the id space at
0..`$11` by construction rather than by argument. Row counts, walked out of
the game's own streams: 8, 8, 14, 20, 5, 25, 54, 28, 7, 30, 8, 51, 25, 15, 38,
85, 35, 8 = **464 frames**. `tools/sfxdata.py` asserts all of that and
`tools/build.py` refuses to build without it.

**The mixer.** R7 is built as `$38` with bit `(3+ch)` CLEARED for any channel
whose noise nibble is non-zero, then written as `value AND $38` (`$BB27`). The
three TONE-disable bits are therefore always 0: **all three tones are enabled
for ever and only noise routing varies**, and silence comes from volume 0, not
from the mixer. (`$BB77 RES 7` is dead code under that mask.) The enables are
inverted — 0 = on. **R11/R12/R13 are never written and no volume ever sets bit
4**: every ramp is the CPU writing a new level each frame. Asserted over all
464 frames in `headless.js`.

**Allocation — three tiers, all measured on the Z80 by calling `$BA2B` in
isolation and reading `$BDC0`/`$BDB3..`:**

1. a record already carrying this id → restart it in place at row 0
   (`$BA4F CP D`), so a repeated effect never doubles;
2. else the first record whose busy bit is clear (`$BA6B RRCA / JR nc`);
3. else STEAL the record with the LARGEST age (`$BA84 CP D / JR c` — it skips
   only on strictly-less, so **a tie goes to the highest index**).

Measured: three distinct ids give masks `$09 → $1B → $3F`; ages 27/7/2 steal
channel 0, 2/7/27 steal channel 2, 5/5/5 steal channel 2. Note tier 1 matches
on the **id field alone**, not on "still playing" — after `$BA01` all three
ids are 0, so the first request for id 0 or 1 reuses channel 0 without
searching (visible in the isolation timing, 501 T against 769 T).

**Two gates before any of that (`$BA31`), and this is the rule the earlier
write-ups missed:** `$BDE9` bit 1 (tune 2 playing) forces the request onto
channel 0 by writing the id into `$BDB6` first; `$BDE9` bit 0 (tune 1) aborts
the request **entirely**. Measured: with `$BDE9` = 1, three triggers in a row
leave the busy mask at `$00`; with `$BDE9` = 2 all three land on channel 0.

**The terminator releases only half the mask.** `$BB3F RES 7,(IY+1)` clears
the channel's ALLOCATED bit and leaves the step-enable bit `c+3` latched:
measured `$09 → $08`, and `$08` persists. The pointer is not advanced and the
age is not incremented on that frame.

**Id 0 is a coin.** `$BAB1 LD D,A / $BAB2 LD A,R / AND 1 / ADD A,D` turns a
request for effect 0 into effect **0 or 1**, which is why the static scan
finds no call site for id 1 and why a port must not drop it. Measured on the
Z80: 200 requests for id 0 gave exactly 100 of each; ids 2/4/15/17 never move
under a swept R. The DRAW is the refresh register (Q18's class) and is not
reproducible; the port uses a **separate substitute stream** from `rand8()`
so that sound can never perturb gameplay, and that is declared here rather
than hidden. Its seed is a constant, so the port's *first* coin after a reset
is always the same where the original's is arbitrary.

### The clock: one row is one VIDEO FRAME, not one pass

`$BADB` has exactly one call site — `$A2A5`, inside the IM2 handler
(`$DADA → JP $A29F`). Measured over 60 driven passes: **237 ticks, per pass
{3: 4, 4: 55, 5: 1}**, and on the interrupt's own frame grid every frame
carries exactly one tick except 3 frames in 240 that carry none. The pattern
is `$9CD8 DI` dropping one interrupt per pass and `$9CF8 CALL $A29F` paying it
back by hand at the bottom. Tick offsets inside an ordinary pass, in frames
from the loop top: **0.78, 1.78, 3.43, 3.78** — the one that would fall at
2.78 is the one the DI eats.

The engine ticks `FRAMES_PER_PASS` times a pass, **one before `hudPass()` and
three at the bottom**, which is the same split `frameCtr` already used and
which was measured at `$B6DA`. Every measured trigger fires at 0.09..0.68
frames into the pass, i.e. before the first tick, so an effect armed in a pass
starts on that pass's first tick — which is what this ordering gives.

### The blocking pause IS reproduced, and it is not the sound dispatcher

```
$9D01  BIT 2,(IY-2) / RET z        $847D bit 2, armed at $8996 and $8B98 only
$9D06  RES 2,(IY-2)
$9D0A  LD A,($FFFD) / OR A / JR nz          the sound mode, read AGAIN here
$9D10  (48K)  BIT 5 -> JP nz,$B8B5 : JP $B8B0    two blocking beeper tunes
$9D1A  (AY)   BIT 5 -> B=$82, no effect
$9D22         else  LD A,$10 / CALL $BA2B / B=$32
$9D2D  PUSH BC / CALL $9432 / HALT / HALT / POP BC / DJNZ
```

Measured three ways here on the real Z80:

* the routine in isolation costs **100.07 frames** with bit 5 clear (50
  iterations, one `$BA2B`) and **259.07** with it set (130 iterations, no
  `$BA2B`);
* planting a `$19` in the player's path makes that pass cost **104.82 frames**
  against an ordinary 3.97;
* a **T-state** histogram of that pass puts **90.4%** of it in the two HALTs

So `$BA2B` does not block (501..769 T-states over all 18 ids) and neither does

The LONG form (bit 5, 260 frames) is **not** ported: bit 5 is set only at

### The chip and the bridge

`AyChip` is a sample-level AY-3-8912: three tone counters, a 17-bit noise
LFSR (taps 0 and 3), the hardware envelope with all eight shapes, the inverted
mixer and the 16-level logarithmic volume table. Clock **1,773,400 Hz**
(128K CPU/2). It runs internally at clock/8 = 221,675 Hz and each output
sample is the **mean** of the internal steps it spans — deliberately, because
tone period 0 (the "noise only" rows) puts a 110 kHz square on the channel and
point sampling would alias it into the audible band as a whine that is not in
the original. The envelope and R11..R13 are implemented but **unexercised by
this game**; the differential proves the game never uses them.

**Why 1,773,400 and not the note table's own tuning.** `$6A4E`'s chromatic
table is equal tempered to about 0.02 semitone at 1,800,000 Hz — and equally
well at 1,700,000, because `round(K*2^(i/12))` fits every candidate clock with
a different implied reference pitch. The table pins the composer's assumption
modulo a semitone, not the hardware. The clock is settled by the **paging
probe** instead: the AY code only ever runs on a machine whose `$7FFD` pages,
i.e. a 128K-family machine, where the AY is clocked at CPU/2. The tunes
therefore sit about a quarter of a semitone flat of A440 on real hardware,
which is what the hardware does. Nothing here is tuned to make it sound right.

`SoundOut` is the bridge. **Every event carries the simulated video frame it
happened on**; `flush()` converts frame → AudioContext time as
`t0 + (f - base)/FRAME_HZ`, renders the closed frames into one buffer and
schedules it. Nothing is keyed to the display clock — which matters because
one animation frame drains several passes, and a banner pass drains 104 video
frames at once. It resyncs only on genuine drift (a hidden tab, a suspended
context). **The voice cap counts SCHEDULED END TIMES against
`ctx.currentTime`**; there is no `onended` bookkeeping anywhere, because that
callback may never fire and then the cap never releases. A drop still applies
the dropped events to the chip, so its register state stays correct.

Sound is **not** in `fingerprint()`: it never feeds back into gameplay. The
one thing that does — the 100-frame pause — is game state and reaches the
fingerprint through `frameCtr` like any other clock effect.

### The beeper — the shipped driver, and a different instrument

Not a different voicing of the AY one. Three independent mechanisms share one
bit (bit 4) of one port (`$FE`), and that bit is also the border's, so every
writer does `LD A,($84CA) / XOR $10 / LD ($84CA),A / OUT ($FE),A` and the
border colour survives untouched.

**TONE — `$B8FB`, one step per MAIN-LOOP PASS.** One call site, `$9CD9`,
inside `$9CD7 HALT / $9CD8 DI`. A stream is `n` then `n` rows of
`(C = speaker TOGGLES, E = a DELAY COUNT)`, and the half-period is

```
H(E) = 17*(E or 256) + 31  T-states       edges = C       cost = 152 + C*H
pitch = 3,500,000 / (2*H)                 duty  = exactly 50%
```

`E` is the delay count, **not** the half-period — the trap the first write-up
fell into. Fitted to the real Z80's own recorded port-`$FE` edge stamps and
gated: `python tools/beepgate.py fit` sweeps `E` over 0..255 at `C=4` and `C`
over 0..255 at `E=$17` (512 points, 0 mismatching on edge count, on the
half-period SET and on total cost) and checks all 50 shipped records plus
both 256-wraps, neither of which is reachable from the data.

**An effect is a train of chirps, one a pass, ~4% audible duty.** An AY row
is one VIDEO FRAME; a beeper row is one PASS. Eleven pitches exist in the
whole game (1,588 to 21,341 Hz); every `C` is even, so a chirp returns the
speaker to the level it started on and there is no DC step between chirps —
a property of the DATA, not to be normalised away.

**NOISE — `$B8CC`, one sample per DRAWN OBJECT.** Six call sites inside the
blitter. `LD A,R / CP (IY+$53)`, and `(IY+$53)` **is** `$84D2`: the threshold
and the ramp counter are one byte. `$B8E2` is self-modified to `INC A` or
`DEC A` (a 30th site for Q3's list). 127 ramp calls to silence in either
direction; toggle density exactly `level/128`, **enumerated** on the real Z80
over all 256 values of `R` (the image contains no `LD R,A`, so bit 7 is
always 0).

**Its DURATION is a live game value, and this is where two write-ups
disagreed.** The 127 calls come from the blitter, so a burst lasts exactly as
long as the blit takes to draw 127 more objects — and where in the pass it
was armed decides how much blit is left:

```
armed at 0.098 frames from the loop top  ->  127 ticks in 0.493 f =  9.8 ms
armed at 1.30..1.51                      ->  127 ticks in 4.10..4.37 = 82..87 ms
```

Both are real. `$8CAD` (FIRE) and `$A783` arm from the player's own move
(phase 0.005..0.052) and are the 10 ms case; `$AEFC` (ghost contact) arms
from the actor update and is the 85 ms one. The "~43 ms" a write-up reported
came from multiplying the whole-run mean `$B8CC` spacing by 127, and that
mean is dominated by the SILENT code path (`$B8DD OR A / RET z`, 68 T), which
by definition is not the one running during a burst.

**The port therefore models the blitter's own issue times, not a uniform
spread.** `build/beeper_data.json` carries a 21-point **measured tick curve**:
the offset, in video frames from `$8503`, of the call at fraction *q* of the
pass's own call count. It is strongly front-loaded — the median call is at
0.50 frames, not at the window's midpoint of 0.755 — and there are TWO
curves, picked by whether a player moved that pass:

```
q      0.00   0.25   0.50   0.75   1.00
walk   0.128  0.286  0.523  0.964  1.325
idle   0.067  0.230  0.462  0.938  1.274
```

The split is not a guess: at every *q* up to 0.50 the walk/idle gap
(0.056..0.065) is 2 to 18 times the spread *between* the four walking scenes
at the same *q*. Past *q*≈0.6 it stops winning — the tail moves with the
scroll state by up to 0.19 frames — and that is declared rather than
smoothed, because a 127-call burst out of ~249 objects only reaches *q*≈0.51.
Camera scrolling was tested as the discriminator first and rejected.

**And a burst stretches the blit it rides on.** The curve is measured on
silent passes where `$B8CC` costs 68 T; while the ramp is armed the routine
always takes a longer arm — 96 T when it does not toggle, 135 T when it does
— so every ramp call hands the rest of the blit 28 or 67 T. A full 127-call
ramp is ~63 toggles and ~64 not, i.e. `63*67 + 64*28 = 6,013 T = 0.086
frames`; the same pass measured loud against its own quiet neighbour
stretches by **+0.087**. That term is in the engine, and without it every
late-armed burst came out 0.18 frames short.

Gated by `python tools/beepgate.py ticks`: the curve is re-measured in a
scene `beepdata.py` does not pool over (holding LEFT) and agrees to ≤0.017
frames, and all **16 bursts** in driven play match the engine's span to
within the curve's own scene spread (worst 0.112 frames = 2.2 ms).

**Shipping the uniform spread instead made a burst armed at the top of a pass
0.61 frames long against the original's 0.49 — 24% long on id 4, which is
FIRE and the effect the player hears most.**

**THE DISPATCHER, `$B92B`** — what `$BA2B` becomes. A bare `CP` chain. No
allocator, no channels, no tiers, no tune gates: none of the AY allocator
survives. **Eleven ids handled** (0, 2, 4, 6, 7, **8**, `$0A`, `$0B`, `$0E`,
`$0F`, `$11`) and **seven a bare `RET` at `$B98A`** (1, 3, 5, 9, `$0C`,
`$0D`, `$10`). Ids 6 and `$0F` share one stream at `$B9E5`. The id→stream map
is **parsed out of the game's own bytes** by `tools/beepdata.py`, not
transcribed, because a hand transcription dropped id 8 once already. The
eight streams tile `$B995..$BA00` with no gaps and end exactly at `$BA01`,
the AY init entry this arm has patched to a `RET` — the region is closed by
construction.

Priority is four bytes of state and no policy: a new trigger overwrites
`$84CF`/`$84D0` and abandons the old stream mid-flight; the same id
retriggered restarts at step 0; a **silent** id over a playing tone is a
genuine no-op; tone and noise are independent state and sound together; and
`$BA01` is patched to `RET`, so **nothing silences the beeper** — an effect
in flight survives a level change, a death and a game over.

**TWO DECLARED DEFECTS OF THIS PORT DISAPPEAR HERE.** `$BAB2`'s `LD A,R`
id-0 coin never executes (the allocator body is dead), and id `$0C` — the
generator spawn — is one of the seven silent ids, so the substitute-RNG leak
described two sections below is an **AY-branch problem only**.

**THE TUNES — `$B8B0`/`$B8B5`.** A `$13E`-byte two-voice interleaved player
LDIR'd to `$C000` and executed with interrupts OFF, blocking 72.07 and 209.97
frames, and on this branch they **are** the banner pause. Two down-counters,
two speaker states swapped with `EX AF,AF'`, two OUTs per 96 T turn; a
voice's pitch is `3,500,000/(2*96*reload)`. Note byte `$29` is the REST and
indexes one PAST the 53-entry table at `$C0D4`, giving reload 1 = 18,229 Hz —
the code only mutes when BOTH voices rest, so a one-voice rest really does
put an ultrasonic square on the speaker. That is what the hardware does and
it is not tuned away. **You cannot read the notes off the combined edge
train** (48/144 T, an 18 kHz interleave carrier — manual 11.3(c)); the rows
are sampled at `$C081` on the running original, and the invariant that makes
the transcription safe is `2 * turns == writes to $FE`, exact at 79,872 and
292,864.

**WHAT IS STILL A DECLARED SUBSTITUTE: the noise, and only the noise.** Which
samples toggle is `LD A,R` — Q18's class. The port uses a separate stream
from `rand8()` so sound can never perturb the simulation.

### The edge-level differential

The AY has registers, so `soundgate.py` asks "the same registers with the
same values on the same frames?". **The beeper has no registers** — its
entire output is one bit — so the equivalent question is *"does your player
put the same edges on the speaker, at the same times?"*, and that is what
`tools/beepgate.py` asks. Both sides print one row per **speaker edge**:

```
pass   source   level   offset-into-the-pass (video frames)   dT
```

`source` is which mechanism wrote it, taken on the Z80 side from the
WRITER'S PC (`$B91E` tone, `$B8DB` noise, `$B4FC` the ISR's border write,
`$C089`/`$C095`/`$C0AB` tune) and on the engine side from the driver's own
tag. `dT` is the T-states since the previous edge of the same source in the
same pass — for a chirp that is the half-period, i.e. **the pitch** — so the
differential asserts the **edge count AND the periods**, which neither alone
would catch.

Three comparison rules, and they are deliberately not the same:

* **TONE** exactly — count per pass, level of every edge, every `dT`, and the
  first edge's offset to within 0.06 of a video frame.
* **NOISE** by **count per burst and burst span**, never edge for edge.
* **TUNE** as a **block** — which tune, when, how long it blocked, how many
  edges. The two OUT counts are compared and are exact.

**The one substitution, declared:** the engine charges a flat four frames a
pass, so `diff` hands it the original's own per-pass frame cost, exactly as
`soundgate.py` hands it the original's `$BADB` tick count. The unhelped
number is printed too, as "flat clock" — 10 mismatching against 0, and every
one of the ten is a five-frame pass. **It is the clock, not the driver.**

`simFrame`. The tone tick is `$9CD9`, once per pass whatever the pass costs.
(2) The three rendered WAVs could not have shown any of this: `tools/
soundwav.js` empties the stage, so `beep` and `beeptune` are byte-identical
with the clock pinned flat and `beepplay` differs only in the single
five-frame banner pass. That blind spot is why the round trip and the owner
disagreed, and `beeplive` (below) is the fix for it.

**ARTEFACT — the bridge did not tile the timeline, and that WAS a defect.**
`SoundOut` sized every buffer `Math.round(nf * sr/FRAME_HZ)` but scheduled it
at the exact real time `t0 + (f - base)/FRAME_HZ`. `FRAME_HZ` is 50.08, so a
video frame is **880.591 samples** and the length never equalled the slot:

```
nf = 1  (the FRONT END, one video frame a buffer)   880.591 vs 881   +0.409
nf = 4  (a quiet main-loop pass)                   3522.364 vs 3522  -0.364
nf = 5  (a loaded pass)                            4402.955 vs 4403  +0.045
```

An overlap makes two buffers **SUM** on a sample; a hole leaves a zero in the
middle of the wave. On the game path this was inaudible — a pass boundary is a
frame boundary and `$B4FC`'s border write holds the speaker low there, so the
64 one-sample holes in `beeper_effects.wav` all landed where the wave is under
0.002. **On the front end it was not**: the title tune hands the bridge ONE
frame per buffer, the worst case, and it emits no border write, so the seam
lands mid-wave. Measured over 584 buffers of tune: **238 joins summed two
buffers**, and the mixed peak reached **1.1094 against a largest
single-buffer sample of 0.9977** — arithmetic proof of summing, not an
inference. Injected noise **−7.5 dB** relative to the tune. The front end is
new this cycle, and it is the first thing the player hears.

The fix takes the two ENDS onto the sample grid instead of rounding the
length, so buffer *k*'s end and buffer *k+1*'s start are the same expression
of the same `(base, t0)` and they abut by construction for any `nf`. It is
`Math.floor`, not `Math.round`, so `start` is at or before the ideal time and
no event is ever pushed back into a buffer already handed to the context —
with `round`, an edge landing exactly on a frame boundary (which `$B4FC` does
once a frame and the tune does 50 times a second) was clamped to the next
buffer's first sample at 0.495 of full scale. A matching trim keeps an edge in
the window's last partial sample in the log for the next buffer rather than
splicing it away with only its level applied.

**The result is that the schedule IS the waveform.** Mixing what the bridge
scheduled and comparing it with ONE continuous render of the same edges on the
same sample grid:

| scenario | before | after |
|---|---|---|
| `beep` (178 buffers) | 3.3% of samples wrong, worst 0.48 | **0 wrong**, rms 3.5e−11 |
| `beepplay` | 0.26% wrong | **0 wrong** |
| live dungeon walk, variable clock | 5.3% wrong, worst 0.50 | **0 wrong** |
| FIRE held, variable clock | 7.0% wrong | **0 wrong** |
| the front end's title tune | −7.5 dB injected, 238 joins summed | **−177.2 dB, 0 joins wrong** |

**AND THE CLOCK CAN RESTART.** `game.reset()` puts `simFrame` back to 0 and is
reached from `feHandover()` — the menu handing over, `$FF38 JP $8400` — and
from `setMode()`. `SoundOut` still held the front end's numbering and
`if (nf <= 0) return` then swallowed every flush until the game's own counter
climbed back past it. Measured on the page's own `frame()` loop: after a
930-frame menu the first sound of play arrived **19.3 s late** (rms 0.034, 10%
non-zero over the game region); with the re-origin it arrives in **0.9 s**
(rms 0.113, 95% non-zero). It scales one-for-one with how long the player
spent in the menu. A backward jump is not drift — the map's origin is gone —
so both `flushBeeper` and `flushAy` now take it down the same path the first
flush uses, and count it as a resync so it stays visible.

Gated by `tools/headless.js` (17 new checks, at SAMPLE level because a
state-only test cannot hear a click): buffers abut exactly for `nf` in
{1,4,5,6,7}; the schedule reconstructs one continuous render sample for
sample; no sample is two buffers summed; an edge on a boundary and a dense
edge stream both stay exact; and a backward clock jump re-origins and
schedules again instead of going silent. All five fail on the pre-fix bridge.

The demonstration files are `node tools/sounddemo.js` → `build/demo_1..7`,
each pair written at ONE shared gain so an A/B is honest.

**STILL OPEN after this, declared rather than hidden.**

* **A resync that moves `t0` BACKWARD does not stop buffers already
  scheduled**, so the old stream plays under the new one. Reachable only
  through `when > now + SND_AHEAD`, which needs a single flush longer than
  3.0 s: the level tune (209.97 frames = 4.19 s) does it and is why
  `beeptune` double-covers 204,270 samples. The level tune is not reachable
  in play (`$847E` bit 6 is never set) and the banner tune at 72.07 frames =
  1.44 s stays inside the window, so this is latent. Closing it means keeping
  the node beside its end time in `this.live` and stopping the ones still in
  the future — more bookkeeping than the measured problem justifies today.
* **The startup resync.** `SND_LEAD` (0.080 s) is almost exactly one
  four-frame pass (0.0799 s) and the origin is taken before any pass has run,
  so the first buffer starts with ~13 ms of head start and bleeds to 5 ms
  before tripping. Exactly 1 per session in every scenario, flat clock or
  variable; it moves the stream FORWARD, so it costs ~78 ms of silence and
  never an overlap. Raising `SND_LEAD` would remove it at the cost of latency
  on every effect, which is the wrong trade for a game.
* **The browser's own scheduling.** Everything above is measured through a
  recorder stub that places a buffer at `round(when*sr)` and sums collisions,
  which is what Firefox and Safari do; Chrome starts a source sub-sample
  accurately. What is NOT implementation-dependent, and was the defect, is
  that 881 samples of audio were being generated for an 880.591-sample slot.
* **Loudness is still not modelled** (declared already) and the WAVs under
  `build/` are peak-normalised — except the `demo_*` set, which is written at
  a shared gain precisely so that an A/B means something.
* **Whether the owner's "slight noise" is the aperiodic chirp train, the
  front-end summing, or both, cannot be settled from here.** Both are real,
  both are measured, and only one is a defect. If he re-listened to
  `beeper_effects.wav` and `beeper_tune.wav` those two files are BYTE-
  IDENTICAL with the clock pinned flat, so nothing about the slowdown can
  explain them — and the front-end summing cannot either, because no rendered
  artifact runs the front end. In that case the report is about
  `beeper_play.wav` (one five-frame banner pass, 7.00 s → 6.98 s) or about
  playing the page, and the page is where the summing lives.

### The round trip (manual R9)

`node tools/soundwav.js` stubs the browser audio API with a recorder, drives
**the built artifact** through a scripted session, mixes what the page
actually scheduled onto one timeline and writes `build/sound_effects.wav`
(17.7 s, 218 scheduled buffers) and `build/sound_play.wav` (a walk into a key

most of them are, because these effects change the period every frame — and
compares it with `clock/(16*TP)` computed from the game's own data:

```
11 effects have a measurable pitch; 0 are outside 5%
worst 1.34% (id $0B), mean error under 0.5% on every effect
durations 160..1701 ms against the model's 160..1697
the other 7 are noise-only rows and are reported as such
```

**And the same round trip for the SHIPPED branch.** Three more WAVs under
`build/`, named so the owner can tell which driver he is listening to:

| file | what | measured back |
|---|---|---|
| `beeper_effects.wav` | all 18 ids one at a time, the seven silent ones included so the absence is audible | 8 effects with a measurable pitch, **0 outside 5%**, worst 1.1% |
| `beeper_play.wav` | a driven session on the beeper | 13 audible bursts |
| `beeper_live.wav` | the SAME walk on the dungeon **as shipped** — actors and generators left alone — because every other scenario here empties the stage and so cannot observe the pass clock at all. Pass histogram `{4:33, 5:31}` against `{4:66}` | the scene a play report is about |
| `beeper_tune.wav` | both blocking tunes | 28 voice-rows, **0 outside 5%** — every row **exact** |

Measured against `f = 3,500,000 / (2*(17E+31))` from the game's own stream
data, which is the model `beepgate.py` fitted to the real Z80's edges — never
anything the engine computed. The two **ultrasonic** steps in the game's data
(15,086 and 21,341 Hz, which ids 2 and `$0A` end on) are reported and
excluded from the fit: they are above what a 44.1 kHz measurement can resolve
and on real hardware they are clicks rather than pitches.

**Two things this round trip caught that the gates did not:**

* **The bridge's frame→time map is PIECEWISE and only its last piece was
  recorded.** `SoundOut` resyncs whenever the engine drains more simulated
  frames at once than the audio clock has room for — which a 72- or 210-frame
  blocking tune guarantees — and each resync starts a new `(base, t0)`. Using
  only the final pair placed the level tune's rows two rows (18.3 frames)
  early, so every row read back as its neighbour's pitch: a uniform-looking
  **29.8% error** that was entirely the lookup. `soundwav.js` now records
  every piece and `soundwav.py` picks the one in force. With that fixed all
  28 rows measure exact, which is a much stronger statement about the tune
  engine than the block gate alone makes.
* **An envelope detector cannot measure the noise.** It is a sparse random
  telegraph with toggle gaps from 223 T to ~1,900 T; a detector tuned to find
  a 3-5 ms chirp (1.5 ms smoothing, 10 ms gap-merge) reads a 10 ms burst as
  ~30. The catalogue now prints the **driver's own edge span** next to the
  WAV envelope and says which is the measurement — the span is what
  `beepgate.py ticks` gates against the real Z80.

The catalogue also arms each noise id **at its own trigger site's phase**,
and each of them twice (early, from the move; late, from the actor update),
because that phase is the whole of the duration. Driving `sfx()` from outside
`onePass()` gave an unrepresentative phase and an unrepresentative burst.

Loudness is not measured (the WAV is peak-normalised) and that is declared.
ULA memory contention **is** now modelled — `tools/harness.py` runs
`CMIOSimulator` by default. The beeper loops live above `$8000` and are
uncontended either way, so `17E+31` is exact there whichever simulator runs.
What changed is the frames-per-pass figures. Note carefully: every such
figure recorded in this file BEFORE that switch was taken on a plain
`Simulator` and is still a **lower bound** on real hardware until it is
re-measured. Only figures marked contended are the hardware's own.


## The front end — BLOCK A, and it is a different machine

`notes/NOTES-loader.md` §8 has the measurements; this section is what the port
does with them.

**MANUAL 0.4, IN THE FLESH.** The game's clock is the main-loop pass (`$8503`,
about four video frames). The front end has no passes at all: it HALTs once
per screen update in `$CC4E` (`EI / HALT / RET`) and each interactive loop
polls the keyboard after a fixed number of those HALTs. The tune is a THIRD
model again — `$C00C DI`, no HALT anywhere, tempo in loop counts. So the port
gives the front end **its own class, its own state and its own clock**:
`FrontEnd.frame()` is called once per VIDEO FRAME by the driver and
`Game.onePass()` is not called at all while it runs. `Game` gained two more
frame-clocked modes for `$B470` and `$B494`, alongside the existing `over`.

```
                 clock                       loop
  frontend       1 video frame               $C1F2 .. $C554   (block A)
  attract        1 video frame, 256 a page   $B470            (block C)
  rewind         1 video frame               $B494            (cold boot only)
  over           1 video frame               $B3B9            (name entry)
  play           1 PASS = ~4 video frames    $8503
```

### What the menu writes, and what the port does with it

| byte | written by | menu default | port |
|------|-----------|--------------|------|
| `$FFFF` | `$C42C`, from `($C7FD)` | **0, the WARRIOR** | the player picks; `FrontEnd.cursor` starts at `$C7FD`'s tape value |
| `$FFFE` | `$C4E3` (2P) / `$C449` (1P, `LD A,R`) | a DRAW, never player 1's | `feDrawP2()` applies `$C43F`'s real guard to a substitute counter |
| `$FFFD` | `$C242`, the `$7FFD` probe | 0, the 48K beeper | `SOUND_MODE`, unchanged |
| `$FFFC` | `$C508`, from `($C808)` | **0, SINCLAIR** | `Game.method1`, dispatched for real by `readKeys` |
| `$FFFB` | `$C51D`, from `($C808)` | **0, SINCLAIR** | `Game.method2` |

`Game`'s constructor takes exactly those, and **omitting them gives
`GATE_CONFIG` — char 3, the ELF, and method 3, the KEYBOARD**. That is the
configuration every differential in this project was measured against, it is a
reachable menu state (three presses of `5`, three of `6`), and it is named
rather than left as a bare literal so nobody mistakes it for the default
again. The shipped artifact never uses it: it boots through the menu.

### The keyboard is now a real keyboard

Porting all four control methods means the input can no longer be collapsed to
`{up, down, left, right, fire, potion}` — **which physical key moves you
depends on `($FFFC)`**, and the menu is read through a different scanner again
(`$C8EA`'s eight half-rows). The driver therefore keeps a `Keyboard`, and
`input.kb` is how `readKeys` is told to run `$855D` for real. The abstract
input object is still accepted and is byte-for-byte the path the five
differentials use, so nothing moved.

**The arrow keys are the Spectrum's own cursor keys.** On a 48K, cursor
left/down/up/right ARE 5/6/7/8 — which is exactly what PROTEK reads unshifted
and what the menu's own "USE CURSOR KEYS AND SPACE" means, since `5`/`8` step
the character picker and `6`/`7` the control picker. Mapping the arrows onto
those four keys is the machine, not a convenience layer.

### The screens are a display file, not a character grid

`$C895` prints inline text at an `LD HL,nn` **screen address**, `$C740` turns
one into an attribute address and `$C74A` steps a pixel row, so the port keeps
the 6,912-byte buffer and the same arithmetic (`SpecScreen`) and blits it with
the same fillRect spans the HUD uses. Consequences that fall out for free
rather than being special-cased:

* the text pages are 24 rows of **32 characters + ONE attribute byte**, which
  `$C877` stores 32 times (its `DJNZ` jumps to `$C88F`, not `$C88A`) — which is
  why every row of every page is a single colour, and why `$CE71 + $318` is
  exactly `$D189`;
* the page **fills in over 9.38 video frames** because the print has no HALT
  in it — measured, 24 rows, and reproduced rather than snapped on;
* the character picker's 2x2 highlight is painted with the quadrant paper ORed
  with the 14-step ramp at `$C80A`, and on the wrap frame **solid**
  (`$C7A5 A = paper>>3 | paper`) — which is what ERASES the old quadrant when
  the cursor moves, because a solid quadrant colour is invisible against the
  quadrant. Nothing in the port clears anything.

### The tune, and why it is trustworthy

`$C000` is a two-voice **pulse-density** driver: two down-counters, each
toggling bit 4 when it wraps, two `OUT ($FE)` a 96-T iteration, 6,656
iterations a tick. It is six lines, and the port's six lines were **diffed
against the running original** rather than transcribed and hoped for —
13,312 values a tick, identical (`python tools/fegate.py tune`). Every
published total then falls out of the model: 96 sounding ticks, 7 rests,
1,277,952 speaker writes, 18.75 s. The port plays it in 940 frames at ~723
speaker edges a frame, which the existing beeper bridge handles unchanged.

### The ranked table IS the title screen

`$B35A` → `$B374 CALL $B470` is reached at cold boot **and after every game
over**, and there is nothing else in it: four ranked pages, 256 video frames
each, silent, exited only by FIRE. The four 60-byte tables at `$8826` are
block C tape data (offset `$0426`) that no code initialises, so BIL / BOB /
KEV / ARP all on 010000 is what ships. The sort is ten slots, keyed
big-endian on (6-bit millions, 24-bit BCD score), **the letters never rank**,
a tie goes below its equal, and a score that beats nobody is discarded — so
the qualification rule is "strictly beat slot 9", not ">= 10,000". The port's
`hsInsert` reproduces `$8735`'s LDDR of `E` bytes, which is **two more than
the 54 that need to move**; the two extra reads come from below the table base
and land where the following LDIR covers them. It is reproduced rather than
"fixed", because 54 is not what the original does.

## The pass clock — the load-dependent slowdown, manual B2b

The mechanism, the constants and the accuracy are in `notes/NOTES-battery.md`
Q10; the model is `CLK` / `clockCost()` / `quantise()` in `web/template.html`
and the gate is `python tools/clockgate.py`. The short version:

* a 48K pass is **one `HALT`**, at `$9CD7`. Everything before it is work with
  interrupts on (W1); everything after it is a fixed 147,491 T of screen copy
  plus three interrupt handlers (W2). The `HALT` quantises the pass onto the
  video-frame grid, which is why the cost is always a whole number of frames
  and why it jumps rather than sliding.
* the engine keeps `clockPhaseT` in T-STATES and charges each pass
  `ceil((t + W1)/FRAME_T)*FRAME_T + W2 - t`. `passFrames` is the result and
  `advance()` debits `(passFrames - FRAMES_PER_PASS)` against the accumulator
  — the same debit the blocking pause already used, so the stall clamp and the
  simulation/display split (manual B6) are untouched.
* W1 is a per-CALL-site sum over censuses the engine already builds: the four
  map painters' non-empty cell counts, the actor cull classes, the generator
  window, the pass parity, the drain tick, the banner, the beeper's noise
  sampler. **94.8% of 1,620 held-out passes exact**, 280/280 exact in the
  scenes where the two simulations provably agree.
* the payoff is visible in the panel (`rate`) and in `clockgate.py hz`: the
  port runs 12.5 Hz in an empty room, 12.4 quiet, and **8.5 Hz at a generator
  cluster**, against the original's 12.5 / 12.1 / 9.0. It used to run 12.52 Hz
  everywhere, which was 43% fast exactly where the game is meant to bite.

### THE ONE-OFF COSTS, and where they are charged

`$891C`'s banner text render is 49,799–52,727 T against 77 T on an ordinary
pass, and it is charged in `clockCost()`. The blocking tune behind it (72.07
or 209.97 frames on this branch) is NOT — `blockingPause()` debits it
explicitly, as it always did, and does not advance `$8497` because the tune
runs with interrupts off. A level reload (271.8 frames) goes the same way. The
quantiser clamps at 24 frames so that a runaway W1 cannot silently become the
clock; that clamp is a headless check.

## The ranked tables — already ported; what was missing was a picture test

Asked to port the ranked high-score tables, I read the comment in
`web/template.html` saying the tables, the insertion sort and the four-page
display were "NOT PORTED, deliberately", and set about porting them. **All
three were already there** — `HS_TABLES`, `hsInsert()` and `hsDrawPage()` —
and `python tools/fegate.py hiscore` already drives the sort against `$86ED`
over ties, the shipped score exactly, a point either side of it and the
millions field. The comment was stale, and trusting it instead of grepping
the code cost a whole duplicate renderer before the mistake surfaced. The
comment is corrected in place.

### What genuinely was missing

**Nothing compared what `hsDrawPage` paints against what `$8767` paints.**
`tools/rankgate.py` now captures the four pages out of the real Z80 — bitmap
and attributes — and the suite compares them **byte for byte**. Six mutations
of the shipped renderer, six caught, including one that dropped the 640-byte
attribute flood and passed until the attributes were compared too.

### The format, and a thing I got wrong

Four tables of ten six-byte records, one per character, at `$8826` with a
`$3C` stride (`$8818` computes `$87EA + $3C*B`). A record is three packed name
bytes then three of packed BCD score. The shipped contents are the authors' —
**BIL, BOB, KEV, ARP**, ten rows each on 10000.

`$8757` packs a letter as `code − $40` and rotates two bits of `C` into the
top. I read `C` as the **character class**; it is the **millions count**
(`$86B1 SLA C / SLA C` on `($7F2B+7)`), which is how a score above 999999
sorts at all — and which the shipped `hsKey()` had right all along. `$86ED`
compares those top bits across all three name bytes before it compares
anything else.

### The page layout, measured

Heading on row 1 — the character's own name from the `$7E21` table, centred by
`$8A08`. Ten rows from `$C087` (row 4): the rank right-aligned to column 8, a
`$80` separator, a space, the three letters at 11..13, and the score from
column 17 with leading zeros suppressed.

## The level-entry screen — ported and gated

`$B38E CALL $8B27` sits immediately before `$B391 CALL $8503`, so this runs
**once per level**, between building the dungeon and starting the main loop.
The port drew none of it. Now it does, and `tools/introgate.py` compares
sixteen variants pixel for pixel. 17 mutations, 17 caught.

### What it draws, and where

`$B3D0` first clears the shadow bitmap's `$C000..$CFFF` — **character rows
0..15 only**; rows 16..23 keep whatever the previous screen left. Then:

| what | condition | row | source |
|---|---|---|---|
| FIND THE  POTION | `$847D` bit 4 | 2 | `$7EDD` |
| YOU HAVE FOUND A | `$847E` bit 6 | 8 | `$7EBD` |
| TREASURE  ROOM | `$847E` bit 6 | 10 | `$7ECE` |
| SHOTS NOW STUN | `$847E` bit 4 | 16 | `$7EFD` |
| SHOTS NOW HURT | bit 5 alone | 16 | `$7F0C` |
| OTHER  PLAYERS | either bit | 17 | `$7EEE` |
| eight objective icons | **not** a treasure room | 8 | `$8BAC` |
| the level number | always | 8 | `$8A84` |

`$8B4F` tests bit 4 **first**, so with both mode bits set STUN wins — measured,
the two pictures are byte-identical. `$8A08` centres by `(32 − length) >> 1`
added to the **low byte alone**, so a line cannot cross a third boundary.
`$8B84` then floods the whole attribute file with `$47` and arms the long
pause, which is what holds the screen up.

### The level number is drawn in SPRITES

This is the part that would have been guessed wrong. `$8B7E LD A,($8403) /
CALL $8A84` converts the level by repeated subtraction of 100 and 10 and
pushes each digit through **`$8AB0`, the same blitter the icons use** — so the
digits are 33-byte sprite records at `$BE32 + 33*d`, not font glyphs, and
entries 0..9 of that table are digits while `$0A`+ are objects. A level under
ten draws **one** digit with no leading zero.

It starts at the column the eight icon slots left the cursor on: `$8AAB` steps
two columns a slot from column 6, and a **zero** entry draws nothing but still
steps — so after eight slots the cursor is at column 22.

Finding this took a measurement I nearly skipped: the icon columns came out
6, 8, 10, 12, 14, 18 **and 22**, which is not a uniform step, and the ninth
draw logged an index of 1 that is in no table. It was the level number.

### What the gate compares, and what it cannot

Rows **0..15** are compared pixel for pixel across sixteen variants — that is
`$B3D0`'s own boundary, not a convenience. Rows 16 and 17 carry the previous
screen underneath the text, so they are checked by **decoding the engine's
render back through the font** instead. Without that second check two
mutations passed: one that let HURT win over STUN, and one that dropped the
OTHER PLAYERS line entirely.

The matrix also spans levels 7, 9, 10, 42, 99, 100 and 137, because a
single-level capture cannot see `$8A84` at one, two and three digits.

**DECLARED**: rows 18..19 of the original are leftover pixels from the
previous screen. Reproducing leftover pixels is neither possible nor
desirable; this engine blacks rows 0..19 and draws the same text on top.
Everything the routine actually writes is reproduced.

## The message banner — text and panel, ported and gated

The banner's STATE was already right — which code is raised and the pause it
arms — but nothing was drawn. Now it is, and `tools/bannergate.py` compares the
engine's panel against the original's **pixel for pixel** on all eight message
codes. 10 mutations, 10 caught.

### The measurement that made it portable

**The banner uses the HUD's font.** Not "a similar font" — the glyphs are
byte-identical, which is how the strings could be read straight off the
rendered panels instead of chasing a string table. The `A` of `ARMOUR` and the
HUD's `A` are the same eight bytes.

That also means the port needed no new font, no ROM character set, and no
plotter: `$8A28`'s border is *extracted* (the original is made to draw it and
the result read back, exactly as every other piece of this game's artwork is),
and the text is drawn with glyphs already shipped.

### Geometry, measured

`$8A28` fills `$D8C7` for 18 bytes × 7 rows, stride `$20`, value `$57`.
`$D8C7 − $D800 = $C7`, so the panel is **character row 6, column 7, 18 × 7**,
uniform attribute `$57`. It is painted into the SHADOW screen and reaches
`$4000` through `$9CD7`'s ordinary blit, so the capture is taken from the main
screen after the pass — which is what the player sees.

| `$08` | NOW HAS EXTRA | SHOT POWER |
| `$10` | NOW HAS EXTRA | SHOT SPEED |
| `$20` | NOW HAS EXTRA | FIGHT POWER |
| `$81` | JUST ATE SOME | POISONED FOOD |
| `$40` | *nnnn* BONUS | — |

Line 1 is the **character name** of the player the message is about
(`$A7B6 LD ($84B4),IX` names him, `$893E` reads it back), centred by `$B60A`'s
own arithmetic — the same expression the HUD centres its name with.

### How it stays on screen

`$891C` draws once and `$899A` clears `$84B9` in the same pass. What keeps the
panel up is the **blocking pause** at `$9D01`, which the port models as a
~72-frame debit of wall time the renderer keeps drawing through. So the panel
is raised where the original draws it and taken down at the top of the next
pass.

### The clock constants, corrected

Two claims in this file were overstated and are now qualified in place:
`passPhase = 1.77` is a **mean**, not a measurement — the phase at which
`$891C` is entered varies **1.580..1.932** frames over 75 armed passes. And
`CLK.bannerFire = 52650` is one constant for three jobs measured separately:
the item message **49,763 T**, the treasure pay-out **46,313 T**, the thief
**53,581 T** — and the pay-out is **54,360 T** when both players are paid,
which the captured state never does.

### Two checks that passed vacuously at first

* **The name line.** Every captured panel carries the captured machine's own
  character (tag `$20` falls through to ELF), so deleting the name
  substitution entirely still matched — the stored line said ELF too. It is
  now checked by rendering the same code as two different characters and
  requiring the first line to differ.
* **The teardown.** The gate set the flag directly and rendered once, so
  "never clear it" passed. Now a pass is run and the flag required to be null.

### Where the strings really live

The port draws them from extracted panels, but the table itself is now located,
and the port's old comment (`$7E3F..$7EAF`) was both wrong and incomplete:

```
$7DB8..$7DF3   60 bytes = 4 rows x 15 codes   the NOT-PLAYING HUD panel
$7DF4..$7E20   45 bytes = 3 rows x 15 codes   the PLAYING HUD panel
$7E21..$7F1A   TWENTY length-prefixed records: one length byte, then that
               many FONT CODES (not ASCII)
```

There is no terminator: `$7F1A` is the last byte of tape block B (dest `$73DA`,
length `$0B41`), and the zeros after it are a 16-byte scratch buffer `$B35B`
clears at runtime. A port must stop after 20 records, not scan for `$00`.
The consumer is `$8A08`, which uses the length byte as both the `DJNZ` count
and the centring width.

**The four character names are spelled in three different alphabets**:
`WARRIOR` and `ELF` are plain ASCII, `VALKYRIE` is codes `$81..$89` and
`WIZARD` is `$29..$2F` — proportional graphic cells, not letters. The HUD font
covers `$20..$89`, so all four draw correctly; a font extraction that stopped
at `$7F` would have given two characters a blank name, and the gate now
requires all four to be distinct and non-blank.

### `$40`'s bonus figure — now substituted

`$7EB0` is a **template**, not a string: `00`100 BONUS`, and `$89D4..$89E8`
patch its first two characters with the BCD digits of `A` before `$8A08`
prints it. `A` is `(IX+12)`, the player's own level — but only if `$89A8`'s
`BIT 6,(IX+11)` says he is **exiting**; otherwise `$89AE SUB A` zeroes it,
which is why every captured panel reads `00` and why the pixel comparison
cannot see this rule at all. It is checked separately, by rendering the line
at several levels and decoding it back through the font.

Four mutations, three caught. The fourth — dropping the `bannerShow === $40`
guard so every code substitutes — is **provably equivalent**: line index 1 is
empty for all seven other codes, and `search(/\S/)` returns −1 on an empty
string, so nothing is patched.

## The join was not a bug — and what it did turn up

The two-player join was on the open list as "the port kills more actors than
the original". **Measured properly, it does not.** Both remove exactly three
actors on the join pass (63 → 60) and both settle at 59; the port merely got
there two passes sooner. Decomposed, the difference was three things and none
of them is the join:

1. **One actor's facing.** At the end of the join pass the two engines differ
   in a single byte — actor index 4, state `$00` against `$06`. That is
   `$AC25 LD A,R`, the refresh register, and no port can reproduce it. It
   changes when that actor reaches the player, which is the whole two-pass gap.
2. **The animation phase** — a real difference, now fixed, below.
3. **Seed drift.** Seven of the 63 actors differ at `seed({})` in the top two
   bits of their flags byte alone. The capture is 66 passes into dungeon 1
   while the port builds the level fresh, so those are 66 passes of accumulated
   walk phase, not a build error.

### The animation tick is FRAME-clocked, and now the port is too

`$847E` bit 2 gates the actor walk cycle at `$ACCE`, and this file used to
raise it from `!(passCtr & 1)`. That is the right *pattern* and the wrong
*clock*:

```
$ABCE  LD (IY+$1A),7      the actor pass reloads $8499 with SEVEN
$A2DA  LD A,($8499) / OR A / JR z,$A2E6     the FRAME INTERRUPT counts it
$A2E0  DEC A / LD ($8499),A / JR nz         down, and sets bit 1 at zero
$ABC0  BIT 1 / RES 1 / SET 2                the actor pass consumes it
```

Seven interrupts at about four a pass is "every other pass" — **and it slips by
one wherever a pass costs five frames**. Measured, `$8499` reads
`00, 03, 00, 03 …` and then `04`: that fifth frame is the slip. The port now
counts the same seven interrupts in `soundTicks()`, so it slips where the
original slips.

The phase has to be seeded from the right instant, and that is not the raw
capture: it is anchored mid-pass at `PC=$ABA1`, before `$ABBC`, so its
`$8499 = 0` / bit 1 set describes a moment `seed({})` does not correspond to.
Every differential here settles with one `step_to_loop_top()` first, and that
settle consumes the pending flag. `extract.py` samples after the settle for
exactly that reason — taking the raw pair put the actor walk cycle a whole
pass late, which the shot differential caught immediately.

## Monster shots — ported and gated

Classes 2 and 3 shoot back, and the port had none of it. Class 2 first appears
on **level 5, twenty-three of them**, so an engine without this gets easier
exactly where the original gets harder.

`python tools/mshotgate.py` measures twelve scenes on the real Z80 and
`python tools/mshotgate.py grid` calls `$AF8F` directly over 2,704 probes;
`tools/headless.js` reproduces both. 24 mutations, **24 caught**.

### It is a two-stage system, and the middle stage is the rate limiter

An aligned monster does **not** create a shot. It claims one of sixteen slots
in a ring at `$5B90` — eight facings × two players, `$B049 SET 5,L` putting
player 2's at `$5BB0` — and `$8FC5` drains only **two slots a pass**, chosen by
`$8491 & 7`. `$AB94` refills all 64 bytes with `$FF` at the top of every actor
pass, so a claim lives for exactly one pass and everything not drained is
thrown away. However many monsters are lined up on you, at most two shots a
pass are born.

`$B056 CP (HL) / RET nc` never overwrites an occupied slot: the slot index is
also its priority, so the **first** actor to claim a facing keeps it.

### When a class 2 fires

`$ACC2 AND $E0 / CP $40 / JR c` then `$ACC9 CP $80 / CALL c` — classes 2 and 3
only. Then alignment, and which test depends on the low two bits of its facing:

| `facing AND 3` | test | at |
|---|---|---|
| 0 (up/down) | `|dx| < 3` | `$AFE7` |
| 2 (left/right) | `|dy| < 3` | `$B019` |
| 1, 3 (diagonals) | `|dy|-|dx|` in [-2,2] | `$AFA4` |

Player 1 is tried first and player 2 only if player 1 is dead or not lined up.
The distance `$AFC2` computes is **dead** — `$B04B`'s `LD A,E` overwrites it —
and only the range test's flags ever mattered.

### In the shared body a monster shot is a different animal

It skips the whole spawn block (`$8C6E`), never reads `(IX+4)` for the speed
bump so it always steps 2 (`$8CFB` guards the read), deals a **flat 8** rather
than consulting the power table (`$90E7`), scores nothing (`$8D67`), and costs
the player **10** health (`$908E`, or 3 if its flags carry bit 6).

`$8C69 BIT 7,(IX+3) / RET nz`, reached after `$8C60`'s `CP $20` matched, returns
with **carry clear** — and that is the only thing that ever removes a spent
shot from the array. Missing it filled the array to its cap of 16 with dead
`$FF` records, after which no monster could fire again.

### The sprite: `$90` aliases `$10`

`$8DD2` is three `ADD A,A` on an 8-bit register and only the **last** carry
survives, so tag `$90` lands on the same records as `$10`: a monster's fireball
is the wizard's shot sprite, bright yellow `$46`. `record_addr` in
`shotframes.py` had been transcribed as `idx * 32`, which agrees for the four
character tags (idx never exceeds `$1F`, the dropped carries are all zero) and
is wrong for `$90` — it says `$F480`, which is noise, where the machine says
`$D480`, which is a fireball. Corrected, and the aliasing is asserted so a
later tidy-up cannot "fix" it.

### What the scenes could not test, and why

Three rules are checked at **routine level** or as **units** instead, and each
is labelled in place:

* **The three alignment windows.** `$AF8F` is reached from `actorTail`, which
  runs *after* the actor has moved and turned, so the facing that fires is the
  post-turn facing and `$AC25` is `LD A,R`. Any scene on a window's edge flips
  with the coin. Grid mode calls `$AF8F` directly with the registers set —
  2,704 probes, 1,360 firing, no simulation around it.
* **The 16-shot cap.** It needs sixteen live shots and only two are born a pass
  against a life of about three, so playing cannot reach it. Prefilling `$84A8`
  would hand the Z80 sixteen records of whatever `$5B20` holds and the engine
  none. Checked as a unit.
* **Player 2's half of the ring.** He cannot be held alive across passes by
  poking `$844B` — something re-marks him — and while he materialises the two
  engines do not agree on where he is. Covered in grid mode, where the poke
  cannot be undone underneath the measurement.

Scenes are twelve passes because that is where the actor RNG has not yet taken
hold; `skew` is the negative control, chosen so that **no** facing satisfies
any of the three tests, and it fires nothing on either side.

### Class 3 — ported too, and it is the commoner shooter

I first wrote this section off as "two monsters on level 8". **That was wrong.**
Class 2 appears on level 5 and nowhere else; class 3 appears on **every level
from 8 onward**, two at a time — 66 of them across the first 40 levels against
class 2's 23. It is the standard high-level shooter.

It works nothing like class 2. There is no alignment and no ring:

```
$B060  LD A,R / CP 7 / RET nc     ~7 in 256, and it is the refresh register
$B065  RRA / JR c,$B076           the SAME coin picks who to aim at
$B068  the target must be alive AND his power-up timer ($842A) must be ZERO
       -- a flashing player is not aimed at
$B083  the two sign bits, then L = 2|dx| and H = 2|dy|
$B0A1  the LARGER goes in as H, and $B0A9 swaps H and D back afterwards
$B0B1  state = (H << 4) | D | signs,  flags = L | $C0
$B0C1  written STRAIGHT into the $5B20 array -- the ring is never touched
```

`$B0D6` is its divider, two rounds of repeated subtraction with the quotient
capped at 15, and it contains the one **stack unwind** in this subsystem:
`$B0DF JR z,$B0FC` is `POP AF / RET`, which throws away the return into
`$B0A4` and abandons the shot entirely.

Flags bit 6 then puts the shot on a different **movement**, a different
**lifetime** and a different **sprite**:

| | where | what |
|---|---|---|
| step | `$8CBC` | a sub-cell vector — magnitudes in state bits 1:2 and 5:6, signs in 3 and 7 — and **one** step a pass, not two |
| lifetime | `$90AD` | the flags byte *is* the counter; odd counters also **curve**, nudging the high nibble and the y with it |
| draw | `$8EB7` | not the record table at all: `HL*4 + $D958` → `$DD78`/`$DD98`/`$DDB8`, three sizes of a **growing** fireball in bright green |

### Two bugs the flight differential caught

* **`$8D45`**: a class-3 shot skips the born-bit test *and* `$8D4F`'s
  `RES 7,(IX+2)`. It must — for these shots bit 7 of the state is the **y
  sign**, not a born flag, and clearing it turns the vector upside down. The
  port did exactly that, and the gate caught it on the third pass of the first
  upward-aimed flight.
* **`$8D93`**: expiring drops flags bit 6 as well as setting the exploding
  state, so a class-3 shot stops being one the moment it lands.

### What is gated, and how

* `grid3` — `$B060` entered at `$B065` with the coin supplied, over **441
  offsets**: 440 fire, **176 distinct vectors**, all agreeing.
* `flight3` — twelve vectors planted in the array and flown by the main loop,
  up to 17 passes each, one of them reaching the player (which is `$908E`'s
  damage of **3** for a bit-6 shot).
* The dispatch, the coin and the timer are **units**, because `grid3` calls the
  body directly and cannot see how it is reached, and a live scene cannot see
  them either — the coin is `LD A,R`.
* The fireball's three sizes and its ink are checked through the draw-call
  recorder; a state-only test cannot see either.

22 mutations, 20 caught, one untestable by the harness's string match, and one
**proved equivalent**: `$B0D8`'s `RRCA x4` is a nibble swap, but `A << 4`
contributes only bits 4..7 and the following `+1` cannot carry from bit 3 into
bits 0..2, so the subsequent `AND 7` sees the same value for all 256 inputs.

## The exit sequence — the shrink, and records 24..31

Reported from play: the port rotates the character correctly but the original
**shrinks** it before it disappears. It does, and the mechanism is a second
sprite set the port was not shipping.

`python tools/exitgate.py` drives a real exit on the Z80 and dumps the
per-pass table; the suite reproduces all **24 passes** exactly.

### What the exit is

Stepping on a `$36` sets `(IX+11)` bit 6 and `(IX+$16) = $18` (`$A693`).
Thereafter `$94E1` runs once a pass: the player is nudged toward the centre of
the exit cell, `$9544 INC (IX+13)` rotates his slot, and `$954B` counts down.
The tail is the part that was missing:

```
$954B  DEC (IX+$16) / JR nz,$9555
$9550  SET 7,(IX+11)              the sequence is over
$9555  LD A,(IX+$16) / CP 7 / RET nz
$955B  LD DE,$6218 / JP $9595
```

`$9595` stamps **eight** pointers — `DE`, `DE+$21`, `DE+$42`, … — into the
master record table at `$7C9E` (player 1, id `$D0`) or `$7CCE` (player 2).

### `$6218` is not a separate bank

`$6218` = `$5F00 + $318` = **record 24 of the player's own 32-record set**. So
records 24..31 — which this file listed as "still unported" for a long time —
are the exit animation, and `$9691` installs the walk set (`$5F00`) exactly the
same way at level start. Nothing new is loaded; the pointers are re-aimed.

MEASURED, and this is the whole rule in one table: the pointer table at id
`$D0` reads `5F00 5F21 … 5FE7` while `(IX+$16)` runs `$17`→`$08`, and
`6218 6239 … 62FF` for `$07`→`$01`. So the swap is on the pass the countdown
reaches **exactly 7**, and the last **seven** passes draw records 25..31 as
`(IX+13)` keeps rotating 1..7 underneath.

Each exit frame carries its **own attribute**, unlike the walk set where all
three phases share one — the warrior's run `$42,$42,$42,$42,$42,$02,$03,$0D`,
so he changes colour as he goes. All four characters have their own eight.

### A test that could not see the screen

The first version of this gate checked the countdown, the slot, the flag and
that the frames had shipped — and **three mutations survived it**: never
drawing the exit set, ignoring the slot, and pinning the ink to frame 0. All
three are renderer bugs, and every one of them is invisible to a state-only
test (manual G6). The gate now renders through the draw-call recorder.

One of those checks was itself wrong at first: comparing two slots' draw lists
cannot test the *ink*, because their bitmaps differ too and the lists differ
either way. It asserts the actual colour string now. Eight mutations, eight
caught.

## The hurry-up — ported and gated

`$8531 CALL $971B` was a main-loop step the engine skipped entirely. Reported
from play before it was ported: *"after a certain amount of cycles all the
doors open... wait even longer and all the wall structures turn into exits."*
That is exactly what `$971B` does, in two stages.

`python tools/hurrygate.py` measures both on the real Z80 and dumps the full
1024-cell map after each; `tools/headless.js` drives the engine to the same
thresholds and compares **every cell**. All 1,024 agree at both stages.

### It is a limit on IDLENESS, not on elapsed time

`$84B8` counts drain ticks — one per 64 video frames at `$B6E9` — but every
shot (`$8C90`), every kill (`$AEE5`), every pickup (`$A7D0`) and `$9081` reset
it to zero. Playing delays it; standing still does not. That is why activity
appeared to slow it down, and the port already modelled every one of those
resets — it simply never read the counter.

### The two stages

| | threshold | sound | what changes |
|---|---|---|---|
| stage 1 `$975B` | `$84B8 >= $17` (23 ticks) | 14 | `$11`,`$12` (doors), `$1F` (floor keys) and `$32` → `0` |
| stage 2 `$972E` | `>= $8C` (140 ticks *after* stage 1 reset it) | 16 | walls `1..$10` and `$33..$35` → `$36`, an **exit** |

Each latches in its own bit of `$847D`, so each fires once a level, and
`$971B BIT 6,(IY-1) / RET nz` exempts a treasure room entirely.

**Stage 1 reads the RAW cell byte; stage 2 masks with `AND $7F`.** So a cell
with bit 7 set survives stage 1 and is still transformed by stage 2. That
asymmetry is in the original and is easy to miss — a mutation adding the mask
to stage 1 was caught by nothing until `$91`/`$9F`/`$B2` were planted.

The level does not kill you, it **evicts** you: first it stops the doors
mattering, then it turns the whole maze into a way out.

### Timing, measured

Unpoked from the captured state, stage 1 fires on **pass 305** (`$84B8` runs
`$04` → `$17`, i.e. 19 ticks × 64 frames = 1,216 frames at ~4 frames a pass).
Stage 2 would need 140 more ticks — about 2,240 passes — so the gate *drives*
`$84B8` to each threshold rather than simulating them. That tests the
thresholds and the transforms but **not the tick rate**, which is `$B6E9` and
is already gated by the drain in `p2gate`.

A trap worth recording, because it cost time: seeding `$84B8` with `$FF` makes
the stage appear not to fire, and the reason is nothing to do with the rule —
`$B6E9` is an `INC` and the drain runs at `$852E`, before `$8531`, so `$FF`
wraps to `0` first. The real Z80 wraps identically. The bug was in the test.

## The potion — ported and gated

`python tools/potiongate.py` is a 35-scenario, 426-pass differential against
the real Z80: **0 mismatching rows**. `tools/headless.js` re-runs it against
`build/potiongate.json` on every build. Mutation-tested with 24 broken rules,
**23 caught**; the 24th is proved equivalent below.

The potion is not an effect, it is a **global one-pass sweep** with a five-pass
re-arm timer, and it is spread across six places in the main loop — four that
do something and two that keep the books.

| | where | what |
|---|---|---|
| throw | `$A518`, inside the moves at `$8509` | arms `$847E` bit 3, sets `$84A1`=5 |
| actors | `$AC07`, inside the actor walk at `$851E` | `CALL nz,$AF5D` per actor |
| pay-out | `$8BCA`, its own step at `$8524` | pays the **thrower** |
| generators | `$A9EE`, inside the sweep at `$853D` | damages **map cells** |
| disarm | `$A38D`, top of the moves | `RES 3,(IY-1)` **every pass** |
| countdown | `$8546`, inline in the loop | `DEC ($84A1)` |

### Assumption → reality

| assumed | measured |
|---|---|
| `$A54B` reads `$842E` bit 2 (the teleport flight) | it reads **`(IX+$14)` = `$8434`**, the *inventory* byte. Different byte, different meaning, same plausible shape. This was a live bug: it picked the wrong `$7D1C` row. |
| the sweep kills everything on the level | it is reached only through `$A1DA`'s four `RET nc`, so the reach is the **actor cull window**. From the captured state all 63 actors are off camera and `$AF5D` is entered **zero** times. |
| the potion clears the screen over `$84A1`'s five passes | it kills for the **remainder of the throwing pass only**. `$84A1` gates the *re-throw*. |
| `$84B2` counts generators | it counts **actors with state ≥ `$A0`** (`$AF62`). Map generators are damaged at `$A9EE` and tallied nowhere. |
| `$84A3` is "the class the sweep reports" | it is the **generator tier damage**, `(IY+$24)`, consumed only at `$A9FD`/`$AA07`. |
| the re-throw interval is the countdown's 5 | it is **`max(P+5, Q+1)`** — P the throw pass, Q the pass on which `$B7B1` clears the debounce. Neither 5 nor 6 is the rule: measured gaps from one start are 6,5,5,6,5,7,5, and they shift with the phase of the HUD round robin when the first press is delayed. `$8BED` calls `$B807` *even with a zero tally* and `$B823` marks the score dirty; that one bit makes the HUD take its early return at `$B73E`, delaying the clear. |
| the debounce clear is only about the health/score dirty bits | `$B7B1` is **last** in `$B770`'s icon chain, so a key-gain or key-spend icon outranks it and delays it too. And `$B756` is a separate exit: with potion-gain *and* potion-spend both up the HUD clears **both** and draws nothing, releasing the debounce a pass earlier. |
| `$AF5D` is unreferenced | it is called from `$AC0B`. `grepbytes` rejected the hit because it confirms instruction boundaries **at the match position** — right for opcodes, wrong when the match is an address operand. A flaw in the instrument, not the game. |
| the `$7D1C` row is 3 bytes, so stride 3 | `AND 12` ⇒ **stride 4**, three bytes used. The 3-stride read produced plausible nonsense. |

### The call site is self-modifying code

`$ABB1` writes `CALL $ABFF` into `$A21E` for the duration of the actor walk and
`$ABF5` writes three zero bytes back over it. `$A1DA`'s other four callers run
the same routine with the hook absent — which is why `$A21E` executes four
times a pass while `$ABFF` executes none.

### The four characters get four different potions

`$8435` selects the row, so this is a real class difference and not decoration:

| char | `$8435` | row | `$84A3` gen tier | dmg &lt;`$20` | dmg ≥`$20` |
|---|---|---|---|---|---|
| 0 | `$8E` | 0 | 0 | `$10` | `$10` |
| 1 | `$D8` | 1 | 1 | `$10` | `$10` |
| 2 | `$32` | 3 | 3 | `$18` | `$18` |
| 3 | `$64` | 2 | 2 | `$18` | `$10` |

Row 0 has `$84A3` = 0, so the weakest potion cannot touch a generator at all
(`$A9FD` never destroys and `$AA06` subtracts nothing).

### `$AF7F`'s `CP $20` is dead code, given the shipped table

The one mutation the gate does not catch — moving the threshold to `$30` —
changes the outcome for **no actor state at all**, and that is proved rather
than assumed: for `E` in `$20..$2F` the mask at `$AF86` can only yield `$00` or
`$08`, while every damage byte in `$7D1C` is at least `$10`, so both branches
borrow and kill. `(IY+$26)` *is* observable, but only on row 2 (lo `$18`, hi
`$10`) and only for states `$30..$9F`.

### `$84B3` is never initialised

The class-5 bounty has exactly one writer, `$8D83`, and nothing sets it at
level start — a level inherits the previous roll. The captured machine holds
`$10`, which is now extracted into `assets.globals.potion_bounty` rather than
being a zero this port chose. Six class-5 kills pay `$6000`.

### Three divergences this work uncovered that are NOT the potion

Each is exempted from one column of one scenario, and each exemption is backed
by a control that is itself a scenario of the tool
(`python tools/potiongate.py controls`) — never by an argument.

* **Generators planted into a live grid spawn at different rates.**
  `gen-control` plants six cells with no potion anywhere and the live count
  parts company on pass 1.
* ~~**Player 2's join kills more actors in the port.**~~ **Investigated and
  it is not a bug** — see "The join was not a bug" below. Both engines remove
  exactly three on the join pass and both reach the same count; the port got
  there two passes sooner because one actor turned differently on an `LD A,R`
  coin.
* **State-`$08` actors diverge within five passes.** `weak-control` plants the
  state directly. No dungeon-1 actor is naturally `$08`; a row-0 potion is one
  of the few things that creates one, which is why nothing had exercised it.

None are fixed here.

### `$847E` bit 0 — established, and it is not the potion that sets it

This was open for a long time on the strength of a search that found the only
`SET 0,(IY-1)` in the image and never reached it. The path is a **shot landing
on a cell**, not anything the potion does:

```
$8F60  CP $16 / JR z,$8FAE            a potion on the floor
$8F68  CP $1F / JR c,$8FAE            $19..$1E, the six carried items
$8FAE  SET 0,(IY-1)                   the SUSTAIN arm
$8FB2  ($84A3)=0  ($84A4)=1  ($84A5)=1
$8FBE  sound 5, then $8FAA clears the cell
```

So **shooting a potion detonates it**: the next pass `$A391` re-arms the sweep,
which takes **one point** off every actor in the cull window and cannot touch a
generator at all (`$84A3` = 0). It sets neither `$84A6` nor `$84A1` and does
not zero the tallies, so it is not a throw — `$8BD4` sees bit 0 still up, skips
the pay-out entirely, and `$8C01` clears the bit. **The borrowed sweep lasts
exactly one pass and pays nothing.** `$14` (food) is cleared *without*
detonating, which is the gate's negative control.

Measured end to end in `deto-swarm`: pass 2 the shot clears a `$16`, `sus`=1,
row `00 01 01`, sound 5; pass 3 `armed`=1, all six on-camera actors removed,
`$84A2`=6, `sus` back to 0; nothing on any later pass.

### The white flash is the BORDER, and the port had no border

Reported from play: the original flashes the screen white when a potion goes
off. It is not the playfield — it is the Spectrum's **overscan border**, set
from the frame interrupt:

```
$A2A8  SUB A                     black
$A2A9  BIT 3,(IY-1) / JR z       ...unless the sweep is ARMED
$A2AF  LD A,7                    white
$A2B1  CALL $B4F9                LD ($84CA),A / OUT ($FE),A
```

Measured: `OUT ($FE)` at `$B4FC` carries 7 on exactly the throw passes, 0 on
every other pass, and never 7 at all when the player holds no potions. Because
it keys on the same `$847E` bit 3 that does the killing, it is up for the
remainder of the throwing pass and no longer — and a `$8FAE` detonation
flashes too, since that re-arms the same bit.

The port was missing it because **the port had no border at all**. The fix is
therefore not a special effect but the register: `g.border` is set in
`soundTicks()` (the `$BADB` call one instruction above `$A2A9`) and painted by
an `#overscan` frame around the canvas. Gated as the `bord` column, and the
three obvious ways to get it wrong — never flashing, always white, keying on
`$84A1` instead of the armed bit — are all caught by mutation.

Declared: the original re-evaluates per frame interrupt, so a real machine is
still black for the first ~0.03 of the throwing pass and still white for the
first ~0.03 of the next. This engine puts both transitions at the pass top —
at most one frame either way.

### The bug six actors could not show: a skipped swap-in

Reported from play: on level 2 a potion thrown into a crowd leaves a band of
ghosts standing, where the original clears them. **Reproduced and fixed.**

Parking a 6 x 8 grid of 48 actors on camera and throwing one potion:

| | live after | `$84A2` | score |
|---|---|---|---|
| real Z80 | 63 → **15** | 48 | `$0480` |
| port (before) | 63 → 31 | 32 | `$0320` |
| port (after) | 63 → **15** | 48 | `$0480` |

The scores are the tell, and they match what was reported from play: 10 points
an actor touched, so +500 on the original against +210 in the port.

The cause was one word. Removal in the actor loop is
`$AE9B SET 7,(IY-1)`, and `$ABE8 BIT 7,(IY-1) / JR nz,$ABF3` then **skips
`ADD IX,DE`** so the actor `$AE7E` swapped into the vacated slot is examined on
the next iteration. `actorPass()` models that as `if (this.actorUpdate(i))
continue;` — return true and the cursor stays put. Every other removal path
returned `true`; the potion path returned a bare `undefined`, so after each
potion kill the cursor advanced and **the swapped-in actor was stepped over**.

**Why 438 rows of gate did not catch it.** Every swarm scenario used six
actors out of 63. A removal swaps in an actor from the far END of the list —
one of the 57 that are off camera and would have been stepped over anyway — so
the skip had no observable effect. It only appears when the swapped-in actor is
itself in range, i.e. when the crowd is large. `swarm-big` (48 actors) and
`swarm-big-tough` are now permanent scenarios, and re-introducing the bare
`return` is a mutation the gate catches.

The lesson is about scenario *scale*, not about coverage: every rule was
exercised, and the one that broke was the interaction between a rule and the
loop that carries it.

### Walls do NOT gate the potion

Also from play: a suggestion that only mobs inside the player's own room die.
**Measured false.** Ringing the player in solid wall cells (`1..$10`) and
parking six actors outside the ring changes nothing: `$AF5D` is entered 6
times, `$84A2` = 6 and the live count drops 63 → 57, identical to open ground.
There is no room test, no flood fill and no line of sight anywhere in the
path. The only gate is `$A1DA`'s camera window, which in a room-filling view
happens to coincide with the room.

Nothing in the potion itself. The remaining gaps are the three non-potion

## Still open

### On the pass clock

* **Frame interrupts lost inside the blitter's `DI` windows.** Measured at 14%
  of W1 boundaries overall and 49% holding LEFT. The engine charges every
  boundary its mean cost and advances `$8497` once per boundary, so `left` is
  9.7% slow and `p2gate` still needs its `$8497` substitution. Closing this
  needs a cycle-exact model of `$9F86`/`$A00D`/`$A0C8`/`$A241`/`$A292`'s inner
  loops — emulating the CPU rather than porting the game — and it should not
  be attempted with an acceptance probability, which would be a fudge.
* **ULA contention — DONE, and the one-constant claim was right.** The
  harness now uses `CMIOSimulator` by default (`GAUNTLET_CONTENDED=0` opts
  out) and the engine's constants are contended to match. Measured per site
  at sixteen frame phases under both simulators: the `$9CD8` blit **+6,555 T**
  (mode-to-mode; max-to-max agrees within 1 T), `$AB94` **+421 T** fixed plus
  ~2.4/actor, `$B0FE` **+4.05/actor**, the four map painters +110 T all told,
  and the `$A29F` interrupt body **zero** — it lives above `$8000`. The first
  three are applied; the painters' 110 T and the per-actor 2.4 T are declared
  and not applied, because ~250 T against an `isrW1` carrying 1,520 T of
  declared uncertainty is false precision.

  W2 is the whole effect, because W2 sets the phase: p moves 0.1714..0.2051 →
  0.2654..0.2993 over 300 driven passes and idle dungeon 1 goes 4.300 → 4.999
  frames a pass. **This port used to run about a quarter too fast** (11.3 Hz
  against a real 48K's 10.0) and now does not.

  Mid-session I talked myself out of the "switching is one constant" note on
  the strength of a per-routine scan totalling 631 T, and that correction was
  wrong: the 631 T is real but it is not what moves the frame count. The
  original note was right and this is the record of it.

  It did not "move every gate's baseline". Every screen and table capture in
  `build/` is byte-identical either way (verified on `introgate`), and every
  logic gate substitutes the original's own `$8497`, so `potiongate` (438
  rows) and `p2gate` (289 rows) report 0 mismatching under both. Five checks
  in `headless.js` encoded the four-frame pass and were re-derived from the
  contended original, not nudged: see **the drain and the 61-pass counters**
  below. `clockgate.py score` is **769/780 = 98.6%** matched, against 92.8%
  for the old plain/plain pair — contention scores *higher*, because off the
  frame boundary there is less left to be ambiguous about.

  **WHAT IT COST, and it is not free.** Switching the harness re-rolls the
  Z80's own entropy. The actor update's two coins (`$AC25`, `$AC4C`) and the
  generator roll read `LD A,R`; R counts instruction FETCHES, and contention
  adds none by itself — but it makes a pass cost five video frames instead of
  four, which runs the interrupt handler an extra time. Measured at the loop
  top over eight passes: `66 74 108 101 122 118 15 8` uncontended against
  `15 63 4 4 59 68 6 6` contended. Not a shift — a different sequence. The
  port substitutes its own entropy for R and can follow neither.

  So two comparator gates report more than they used to, both in the
  already-declared actor-drift family and both left VISIBLE rather than
  exempted, because a hidden row cannot report a regression:

  | gate | uncontended | contended | what differs |
  |---|---|---|---|
  | `potiongate.py` | 0 of 438 | **8** of 438 | `nact` only, off by one, in swarm-big-tough and swarm-weak |
  | `shotgate.py diff` | 0 | **32** | one scenario of twelve, `down 60 rows walk 20`; the SHOT columns still agree, what differs is which ACTOR it meets |
  | `p2gate.py` | 0 of 289 | 0 of 289 | — |
  | `soundgate.py all` | 0 | 0 of 2,131 | — |
  | `headless.js` | 988/988 | 988/988 | — |

  That is the trade: the clock goes from 92.8% to 98.6% and the port stops
  running a quarter too fast, and in exchange two scenarios of forty-nine lose
  an actor to entropy nobody can reproduce. Both tools now print the expected
  number and its cause, so a real regression still shows.
  `GAUNTLET_CONTENDED=0` restores the old baseline exactly.
* **The AY arm is charged with the 48K branch's constants.** `$B8CC` is a bare
  `RET` there and W1 is ~7,000 T cheaper.
* **`$A9C2` is the worst-fitted site** (residual ~580 T): its 17x11-vs-16x10
  window is gated on `camX&3`/`camY&3` — a *different* pair of bits from the
  painters' `camX&2`/`camY&2` — and its expensive arms are not enumerated.
* **The banner surcharge is two measurements of two banners.** 49,799 T and
  52,727 T; whether it varies with the message length is unmeasured.
* **All of this is dungeon 1 plus two level-8 states.** The seam rule and the
  cull arithmetic are architectural, but the absolute figures are one map's
  furniture density.

### The corrupt colon in "LEVEL : 2" — and it was us, not the tape

Reported from play: the colon between "LEVEL" and the number is a broken
glyph, and it is broken in a third-party emulator too, so it looked like a
mastering fault on the tape. It is not. **The tape holds a clean colon and we
scribbled on it.**

The eight objective icons on `$8B27`'s screen are 33-byte sprite records from
`$BE32`, indexed by the table at `$8BAC` = `0A 0B 0C 0B 0A 00 0D 00` — L, E,
V, E, L, blank, **record 13**, blank, then `$8A84`'s digits. Record 13 is the
colon, and it is the LAST record in the bank: `$BE32 + 33*13 = $BFDF`, ending
at `$BFFF`, immediately below the shadow screen at `$C000`.

`$9CD7` blits with `LD SP,source`. With the wrong timing an interrupt is
accepted while SP is just above `$C000`, and the handler's own PUSHes land
inside the record. The bytes decode to what they are: return addresses.

| | bytes at `$BFF0..$BFFF` |
|---|---|
| the tape | `00 00 03 80 06 C0 04 40 06 C0 03 80 00 00 00 00` |
| our state | `00 00 03 80 06 C0 DA A2 80 D0 00 00 00 00 1D B5` |

`DA A2` is `$A2D2` and `1D B5` is `$B51D`; the writing PCs are `$A29F`,
`$A2A0`, `$A2A1` (the interrupt handler's entry), plus `$B4F9`, `$B51D`,
`$BADB`. It happens during the BOOT, not in play — 12 passes from the
state write nothing there.

**It is timing-dependent, and contention decides it.** Booted on a plain
uncontended `Simulator` the record is scribbled; booted on `CMIOSimulator` —
real 48K timing — it is clean, and stays clean over 300 driven passes with
zero writes into `$BFDF..$BFFF`. `build/state_48k.pkl` predates the switch to
contention, so it carried the damage, and `introart.py` extracted the art out
of it: the port was faithfully reproducing OUR OWN emulation artefact.

The repair is eight bytes, `python tools/bankrepair.py --write`, taken FROM
THE TAPE and reported byte by byte before writing. A full re-boot also fixes
it, but re-rolls the `$5C00` actor records, and `extract.py`'s tile sweep is
sensitive to where the actors stand: closure 95.53% on the tuned state
against 94.47% on a fresh one. Eight bytes are not worth 1% of tile fidelity.

`introart.py` now verifies every extracted icon against the tape and refuses
to write an asset that is not on it, so this cannot reach the screen again.
Checked against the old state it reports exactly the right thing:
`ICON(S) 13 ARE NOT ON THE TAPE`.

### The level tune going silent — a trap in the sound bridge

Self-inflicted, and worth recording because the shape of it will catch
anyone who moves work out of `onePass()`.

Fixing the level-entry screen meant serving its pause in `advance()`, before
the level's first pass, which is where the original serves it. That worked
— and killed the tune.

`edge()` does **not** publish anything. It appends to the bridge's `pending`
buffer, and **`endPass()` is the only thing that moves `pending` into the log
the renderer reads**. Inside a pass that happens at the bottom of `onePass()`;
served from `advance()` there was no pass to do it, so 140,023 tune edges sat
in `pending` until the *next* pass — 256 render frames and one whole 4.2 s
pause later. By then `flushBeeper()` had rendered past those frames and
cleared the log, so they were dropped. Silent.

The fix is `endPass(beepBase, 0)` right after the pause. **Zero frames** is
deliberate: `endPass`'s other job is synthesising the pass's own frame
boundaries for the ISR's border write, and none of those land inside a tune
— it runs under the `DI` at `$9CD8`, which is why `$8497` advances by zero
across it.

The invariant now checked in `headless.js`: the tune is logged in the **same
`advance()` call** that jumps `simFrame` across it. With the flush removed
that check reports `simFrame jumped on call 0, tune logged on 256`, which is
the bug stated as a number.

### Level 1's warp to level 8 doesn't land on `dungeon-08.png` — and it isn't supposed to

Reported from play: taking the level-1 portal tile to level 8 loads a
different dungeon than `build/dungeons/dungeon-08.png`, the reference render
from `tools/dungeonshot.js`. **Not a bug.** `selectAndBuild()`'s own comment
already says it: below level 8 the dungeon is a per-level lookup into the
tape's `$80` pack, but from 8 on it comes from a rotating stash whose PACK
MASK (`$84CC`) and TREASURE COUNTDOWN (`$84BA`) persist across every build,
warp or not — "calling `startLevel(20)` twice builds two DIFFERENT
dungeons." A warp (`doExit`'s `$37`/`$38`) skips straight to the target
level rather than replaying the levels in between, so it reaches level 8
having done far fewer builds than a player who walked 2..7 first, and
`dungeon-08.png` is specifically the **played-straight-through** one —
`jumpToLevel()`'s own canonicalization, not a claim about what a warp gets
you.

MEASURED on the real Z80 (`tools/warpgate.py`, built on `packseq.py`'s
machinery): warping 1→8 and playing 1..8 in order both reach level 8's
build with **identical** bookkeeping, `mask=$80 tcd=4` — levels 2..7 never
touch either byte, since they're all served from the one already-held `$80`
pack. So the persistent state is not what makes the two dungeons differ.
What differs is how many Z80 instructions ran first: the warp path built
one level before this one, the played-through path built seven, and the
stash draw at that point is `LD A,R` — the same irreducible, timing-sensitive
entropy source as the treasure room's (`$A31A`) and the potion's (`$AF7C`).
Different instruction counts, different R, different record: block 1 chunk 4
(189 bytes) warping in, block 1 chunk 3 (318 bytes) playing through, on this
build. The port matches: identical `tape.mask`/`tcd` entering level 8's
build along both histories, different dungeon out, the same as the real
machine.

**A test-methodology trap found along the way, worth its own line:**
`G.seed({})` resets and returns the PAGE'S OWN SINGLETON `game` — it does
not construct a new instance. A comparison script that called it twice to
hold "two dungeons" side by side was actually holding **one object twice**;
the second call's build retroactively changed what the first variable read,
because they were never different variables. It surfaced as a fingerprint
that was correct immediately after the first build and wrong by the time a
second build had happened elsewhere in the same process — nothing had
touched the first variable in between. Fixed by using `new G.Game({})`
(the class is exported for exactly this) wherever a tool needs more than
one dungeon alive at once; `dungeonshot.js` and friends never tripped over
this because they only ever keep one `g` alive at a time.

### The options screen — one screen instead of nine, and a real second boundary

Reported: the boot sequence — loading screen, credits, a controls blurb,
ONE OR TWO PLAYERS, up to two character pickers, a controls blurb, up to
two control-method pickers — is nine full screens end to end, most of them
asking questions in terms (SINCLAIR/KEMPSTON/PROTEK) nobody who hasn't
touched a 1985 joystick interface has a reason to know. Requested: fold
the configuration into one screen, in KEYBOARD/CONTROLLER terms.

This is the SECOND deliberate faithful/added boundary in this file, same
shape as the tape-prompt one: `STREAMLINED_FRONTEND`, a module `let`
defaulting `true`, redirects `FrontEnd`'s `'boxout'` phase to a new
`'options'` phase instead of `'players'`. The nine-phase graph — `players`
through `ctrl2` — is untouched and still fully reachable with the flag set
`false`, and `tools/headless.js`'s whole pre-existing front-end suite
(every byte measured against the real Z80 — `$FFFF`/`$FFFE`/`$FFFC`/`$FFFB`,
the picker's 14-frame poll, the control picker's 10-frame poll, the player
count's clamp) now runs explicitly on that arm, wrapped in
`G.streamlinedFrontend.set(false)`/`.set(true)`, so streamlining it did not
retire any of that fidelity work. The boundary holds for the same reason
the tape-prompt one does: `optFinish()` writes the identical five bytes
the faithful pickers write, and nothing past `'pressplay'` — which is to
say nothing in the whole simulation — reads how they were chosen, only
what they hold.

One new, genuinely ADDED capability rides along with it: **CONTROLLER +
CONTROLLER**, two players on two independent gamepads. The original has
exactly one Kempston port, and two Kempston-selected players share it
(`$856E`/`$8597` both `CALL $8680` — already ported, faithfully, before
this). A second gamepad has no address on the original hardware at all, so
it isn't a mode of `method`; it's `Keyboard.kempston2`, fed by a second
`Gamepad` object, read by `controlRead` for player 2 only when a new
module flag `indepGamepads` is true (default false, which is the faithful
shared-port case). The options screen only offers it when a SECOND,
genuinely distinct pad is connected — offering it with only one plugged in
would reproduce the exact "picked the option, nothing happens" failure the
level-select and joystick-status widgets have already hit twice this
project.

Folded away entirely: `PLAYERS`/character/`ctrl1`/`ctrl2` become rows on
one screen (`optRows()`), each with its own value that Left/Right or SPACE
cycles; a `REBIND` row per keyboard-using player walks the five directions
in order (`optCaptureFrame()`), with `SPACE`/`CAPS`/`SYM` reserved (menu
confirm, and both characters' MAGIC key in every control method) and
skipping the direction rather than binding it. The mid-game Escape-key
settings panel this project shipped one cycle ago is removed outright, not
just superseded — its widgets (`uiPanel`/`uiText`/`UI_FRAME`) survive and
are reused, but its own per-frame state and the keydown-listener wiring
that opened it are gone. Reconfiguring now means what the original always
meant: play again.

**A real bug caught by tracing the rebind state machine before running
it, not after**: the first cut of `optCaptureFrame()` gated its "ready for
the next key" check on SPACE's release, because SPACE is what starts a
capture. But SPACE only starts the FIRST direction's capture — the second
through fifth are each started by whichever key was just bound, which has
no reason to release in step with SPACE and often didn't in a short manual
trace. A bind key held one frame too long was captured for its own
direction AND silently carried into the next one. Fixed by gating on
`kb.held.size === 0` — a full release, of whatever is actually down — not
on any one named key; `tools/headless.js` now holds a key for five frames
on purpose and checks it only ever bound once.

**A second bug, this one only visible once two things were exercised
together**: `pollGamepads()` originally only RETURNED its result, with the
page's own `frame()` loop doing `padStatus = pollGamepads()` as a second
step. Every OTHER caller — this file's own new tests, and any future one —
had no way to know it had to repeat that second step, so the poll ran and
`padStatus`, which the options screen actually reads, kept showing the
previous one. Fixed by having `pollGamepads()` assign the module `padStatus`
itself and return it, so calling it is enough. Caught by the very first
headless check that called it directly instead of through `frame()`.

### The options screen, round two — sizing, per-player previews, and two more traps

Reported from looking at it: the title-screen-crop portrait "genuinely
looked awful" at the 2:1 downscale it needed to fit a corner, and the
single "whoever the cursor is near" preview, the small centred panel, and
the inverted-row selection all wanted rework. Landed on:

- **The preview is the in-game sprite, not title art.** `CHAR_FRAMES`
  already holds the 16x16 walk-cycle for real play; `drawCharPreview()`
  scales it up 2x (`PREVIEW_SCALE`) to a 4x4-cell picture and cycles its
  own `SLOTNAME` facings and walk phases off `frameCtr`. Upscaling flat
  pixel art tolerates a clean multiple fine — it was the downscale, fighting
  the source art's own dithered shading, that destroyed identity earlier.
- **One preview PER ACTIVE PLAYER, not one that follows the cursor.**
  `optLayout()` finds each active player's own `char` row and top-aligns
  that player's preview with it; with two players both sprites are on
  screen at once. The column is computed from panel width and the
  preview's own size ONLY — never from any row's text — so WARRIOR next to
  VALKYRIE cannot make it jump.
- **PLAYERS no longer persists.** Reported as a requirement: the screen
  starts on 1 every time. `settingsSave()`/`settingsLoad()` never touch it;
  `reset()`'s own default (1) is what ships.
- **The inverted row is gone.** Reported as cluttered on its own; a small
  hand-drawn triangle (`UI_ARROW`, an 8-row bit array through the same
  `uiBits()` the panel border pieces use) in the gutter column marks the
  selection instead, and only the VALUE half of a row (not the label,
  padded to the row's own width) takes that row's own colour — painting
  the whole row was a second, competing "this one is selected" block that
  half-buried the arrow next to it.

**A font trap, found by looking at the first arrow attempt and it not
looking like an arrow**: tried `'>'` first, reusing the HUD font `FONT`
already draws SCORE/HEALTH and character names with. It rendered as
noise. Dumped the raw 8-byte rows for `<`, `=`, `>`, `!`, and even `:` next
to `0` and `A` — the letters and digits are clean, unmistakable shapes,
and every one of those punctuation marks decodes to visual garbage. The
HUD font at `$77B0` is 96 CONSECUTIVE bytes extracted on the assumption of
full ASCII coverage, but the game's HUD only ever prints digits, letters
and space with it — punctuation was never exercised on the real machine
and the extraction has no way to know those slots are not real glyph data.
**Nothing outside digits/letters/space in this specific font may be
assumed to be a real character**, full stop; a font's declared range is
not evidence of what is actually drawn with it. Fixed by not using the
font for this at all — `UI_ARROW` is drawn as a raw bit array, the same
mechanism `UI_FRAME`'s border pieces already use, so there is nothing
about its shape this file did not choose itself.

**A second trap, in the test harness rather than the port**: a headless
check that `settingsLoad()` does not restore a saved `players` value kept
passing even with the restore code fully reintroduced by hand. `tools/
headless.js`'s sandbox never defined `localStorage` at all, and
`settingsSave()`/`settingsLoad()` guard every call in `try`/`catch` (a page
opened from `file://` can throw on it) — so the save wrote nowhere, the
load read nothing back, and the round trip silently no-opped in EVERY
headless run there has ever been, on this feature or any other that
touches storage. Grepping the suite found no other test doing a real
save-then-load round trip, so nothing else was quietly passing on the same
gap — but the gap itself was there for anything that might. Fixed with a
minimal in-memory `getItem`/`setItem`/`removeItem`/`clear` shim added to
the sandbox, which is what let the mutation test above actually fail
before the fix and pass after it.
